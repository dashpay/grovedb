# Test engines: the suites run once on every registered engine

LigninDB task SEAM-06 ([plan](https://github.com/dashpay/grovedb/issues/1052), [task register 1](https://github.com/dashpay/grovedb/issues/1052#issuecomment-6960582299)). MERK-08 registered LigninDB for Merk's suite ([Merk on LigninDB](#merk-on-lignindb)), and GROVE-10 for GroveDB's ([GroveDB on LigninDB](#grovedb-on-lignindb)). OPS-03 registered the engine that is chosen at the open for GroveDB's, once holding each engine ([GroveDB on the engine chosen at the open](#grovedb-on-the-engine-chosen-at-the-open)).

GroveDB's and Merk's test suites name no storage engine. Each is built for one engine at a time, and run once for every engine registered for it. This document says how an engine is selected, what a test may name, which tests are about one engine, and what registering an engine takes. It builds on [`engine.md`](engine.md) and [`node-store.md`](node-store.md).

## Running a suite

| Command | What runs |
| --- | --- |
| `cargo test -p grovedb` | GroveDB's suite on the first engine of `grovedb/test-engines.txt` |
| `GROVEDB_TEST_ENGINE=pinned-reads cargo test -p grovedb` | the same suite on the engine of that name |
| `GROVEDB_TEST_ENGINE=lignin cargo test -p grovedb --features lignin_storage --lib` | GroveDB's suite on LigninDB, whose feature is not among the crate's defaults |
| `GROVEDB_TEST_ENGINE=either-rocksdb cargo test -p grovedb --features lignin_storage --lib`, and the same with `either-lignin` | GroveDB's suite on the engine that is chosen at the open, holding RocksDB and holding LigninDB. It is compiled where both engines are, so the command has LigninDB's feature beside the defaults. |
| `cargo test -p grovedb-merk` | Merk's suite on the first engine of `merk/test-engines.txt` |
| `MERK_TEST_ENGINE=node-store-only cargo test -p grovedb-merk` | the same suite on the engine of that name |
| `MERK_TEST_ENGINE=lignin cargo test -p grovedb-merk --features lignin_storage --lib` | Merk's suite on LigninDB, whose feature is not among the crate's defaults |
| `.github/scripts/engine-suites.sh run` | both suites on every registered engine, one run after the other: every target on the first engine of a suite, the unit tests (`--lib`) on the others. Each run is given the Cargo feature its engine is registered with. Arguments follow `cargo test -p PACKAGE --features FEATURE`. |

A name that is not registered fails the build, and the message lists the names that are. So does a name whose engine is not compiled in: `GROVEDB_TEST_ENGINE=rocksdb` with the feature `rocksdb_storage` off is an error, not a run with no engine.

The engine is a property of the build, not of the run: one test binary holds the suite for one engine. A second engine is a second build of the crate's tests, and of nothing below the crate but what the Cargo feature of that engine compiles: `lignin_storage` brings the LigninDB crates.

`cargo nextest run` takes the same variables. CI uses it.

## The registry

A suite has a registry: a text file with one engine a line, the default first. A line is the engine's name and the Cargo feature of the crate that compiles the engine. In GroveDB's registry an engine that needs more than one feature names them with commas between them and no space (`rocksdb_storage,lignin_storage`), which is also what `cargo --features` takes.

| Suite | Registry | Variable | cfg | The type of a name |
| --- | --- | --- | --- | --- |
| GroveDB | `grovedb/test-engines.txt` | `GROVEDB_TEST_ENGINE` | `grovedb_test_engine` | `SuiteEngine` in `grovedb/src/tests/mod.rs` |
| Merk | `merk/test-engines.txt` | `MERK_TEST_ENGINE` | `merk_test_engine` | `SuiteEngine` in `merk/src/test_utils/engine/suite.rs` |

The crate's build script reads the registry and the variable. If the feature of the selected engine is on, and every one of them where it names several, it sets the cfg twice: with no value, which says that the suite has an engine, and with the selected name. It declares every registered name as a value of the cfg, so a `#[cfg(grovedb_test_engine = "..")]` with a name that is not registered is a warning, and an error under `-D warnings`.

If the feature is off and the variable is not set, the cfg is not set and the suite has no engine. A registry line whose feature the crate does not have fails every build of the crate, whichever engine is selected. That is the build with no engine compiled in ([`engine.md`](engine.md#features-and-engines)): `cargo test -p grovedb --no-default-features --features estimated_costs --lib --tests` and `cargo test -p grovedb-merk --no-default-features --features minimal --lib` run the tests that open no database. A test that opens one is under the cfg, not under the feature of an engine:

| Gate | What is under it |
| --- | --- |
| `#[cfg(all(test, grovedb_test_engine))]`, `#[cfg(grovedb_test_engine)]` on one test | a test of GroveDB that opens a database or takes a fixture. `grovedb/src/tests` as a whole is under it. |
| `#[cfg(all(test, merk_test_engine))]`, `#[cfg(merk_test_engine)]` | a test of Merk that opens a store, and the part of `merk::test_utils` that is the suite's engine |
| `#[cfg(grovedb_test_engine = "rocksdb")]` | a test of GroveDB that is about the records of RocksDB |
| `feature = "rocksdb_storage"` | code that names RocksDB: `RocksDbEngine`, Merk's two test engines, the tests of Merk's RocksDB adapter |

The two suites have registries of their own because an engine is a different thing at each level. To GroveDB it is an [`Engine`](engine.md). To Merk it is whatever hands out [`NodeStore`](node-store.md) handles, and Merk does not know `Engine`.

The engines registered today:

| Suite | Name | Engine |
| --- | --- | --- |
| GroveDB | `rocksdb` | `RocksDbEngine` |
| GroveDB | `pinned-reads` | `PinnedReads` (`grovedb/src/tests/pinned_reads.rs`): the RocksDB engine, except that the transaction of a read that was given none is a read-only snapshot, as on LigninDB (RD2 of [`transactions.md`](transactions.md)). A read that wrote would be refused, and a read that started a second transaction could read another state. The engine is a type of its own and gives no way to the storage underneath. |
| GroveDB | `lignin` | `LigninEngine` (feature `lignin_storage`): a database of `lignindb` ([GroveDB on LigninDB](#grovedb-on-lignindb)) |
| GroveDB | `either-rocksdb`, `either-lignin` | `EitherEngine` (features `rocksdb_storage` and `lignin_storage`), holding RocksDB and holding LigninDB ([GroveDB on the engine chosen at the open](#grovedb-on-the-engine-chosen-at-the-open)) |
| Merk | `rocksdb` | `RocksDbTestEngine`: a handle is the RocksDB storage context of its subtree |
| Merk | `node-store-only` | `NodeStoreOnlyEngine`: RocksDB behind handles that are a `NodeStore` and nothing else |
| Merk | `lignin` | `LigninTestEngine` (feature `lignin_storage`): a database of `lignindb`, whose handles are the store of `merk::store::lignin` on a write transaction ([Merk on LigninDB](#merk-on-lignindb)) |

The second engine of each suite is there so that the suite is run on an engine that is not `RocksDbEngine` whether or not LigninDB is registered for it. A test that reaches for RocksDB without saying so does not compile on it.

## GroveDB

In a test build of `grovedb`, the engine of the suite is the default engine of `GroveDb`:

```rust
// grovedb/src/engine/mod.rs
#[cfg(not(test))]
pub type DefaultEngine = RocksDbEngine;
#[cfg(test)]
pub type DefaultEngine = crate::tests::SuiteEngine;

// grovedb/src/lib.rs
pub struct GroveDb<E: Engine = DefaultEngine> { db: E }
```

`DefaultEngine` exists where an engine is compiled in. So the tests did not change. `GroveDb`, `Transaction`, `TransactionArg` and `MultiStateSyncSession` with no engine named, `GroveDb::open`, `GroveDb::open_checkpoint`, and the fixtures of `grovedb/src/tests/mod.rs` (`make_test_grovedb`, `make_empty_grovedb`, `make_deep_tree` and the rest, `TempGroveDb`) all mean the suite's engine. A test written upstream, which names no engine, runs on every engine the day it is merged.

Outside a test build nothing changed: `DefaultEngine` is `RocksDbEngine`, and a dependent of the crate sees `GroveDb<RocksDbEngine>`.

The functions of `impl GroveDb` that take no `self` (rule 2 of [`engine.md`](engine.md#grovedbe): the proof verifiers, the estimated-cost helpers, the constructors) are on the default engine, so in a test build they are on the suite's engine too, and `GroveDb::verify_query(..)` resolves on every engine.

### What a test may name

- **No engine.** That is every test of a GroveDB operation. It runs on every registered engine.
- **`Engine`, through `db.engine()` or `db.db`.** A test that opens a handle, a transaction or a batch itself calls the trait (`Engine::subtree`, `Engine::apply_batch`), as the ten tests of `parent_read_fault_tests.rs` do. It runs on every registered engine.
- **One engine, by name.** A test of that engine: `grovedb/src/engine/tests.rs` names `RocksDbEngine`, and `one_transaction_per_operation_tests.rs` names `PinnedReads`. It is the same test in every run, and it is under the feature that compiles its engine (`rocksdb_storage` for both), not under the cfg of the suite.
- **The records of one engine.** A test that reads or damages what is stored, or looks at an error or a file of one engine, is compiled for that engine alone: `#[cfg(grovedb_test_engine = "rocksdb")]`. On RocksDB it reaches the storage through `RocksDbEngine::storage()`.

The tests of the last kind are the ones a new engine has to answer for: each is a behaviour that was checked by looking under RocksDB. They are listed in [RocksDB-only tests](#rocksdb-only-tests-of-grovedb).

A test that only counts the records of a subtree, or asks whether a pending drop is recorded, goes through the seam and runs on every engine. Two helpers of the fixtures do it: `data_keyspace_len(db, prefix, transaction)` walks the node cursor and the flat cursor of `Engine::subtree_by_prefix` and returns the larger count, and `pending_prefix_drop_recorded(db, prefix)` asks `PendingPrefixDrops`. The tests of the flat drop, of moves and of the cleanup of nested indexed trees use them (about 100 call sites that read RocksDB contexts before).

In a test build for an engine other than RocksDB, what only the RocksDB-only tests import is unused, so `unused_imports` is allowed for the crate in that build, and in no other.

### Integration tests, doc tests and benches

The eight files of `grovedb/tests/` (80 tests) use the crate as a dependent does. They are not built with `cfg(test)` set on the library, so `GroveDb` is there what the crate exports for its features, whatever engine is selected for the suite: `GroveDb<RocksDbEngine>` in a build with `rocksdb_storage`. So it is for the doc tests and the benches. They are not part of what is run once for every engine: the engine of a suite is the engine of the crate's unit tests, and a run on an engine other than the first is of those (`--lib`). The run on the first engine, and CI's test shards, run the integration tests on the engine the crate exports by default. That engine is a property of the features of the build and not of a cfg of the tests: in a build with `lignin_storage` and without `rocksdb_storage` it is LigninDB, and the integration tests, which are under either feature, run on it ([GroveDB on LigninDB](#grovedb-on-lignindb)).

### RocksDB-only tests of GroveDB

77 tests are compiled for the RocksDB engine alone, with the 47 helpers only they call. Each carries `#[cfg(grovedb_test_engine = "rocksdb")]`, so `grep -rn 'grovedb_test_engine = "rocksdb"' grovedb/src` lists them. All of them write or remove a record under GroveDB, in RocksDB's layout, to see what GroveDB makes of a store it did not write:

| File | Tests | What they do under GroveDB |
| --- | --- | --- |
| `tests/verify_grovedb_aggregate_recompute_tests.rs` | 16 | plant an aggregate in a stored node or a secondary row, rebind a root key, and expect `verify_grovedb` to report it |
| `tests/coverage_lib_paths_tests.rs` | 16 | put raw and undecodable records into a subtree or an axis secondary |
| `tests/indexed_tree_secondary_drift_tests.rs` | 14 | make the secondary of a count-indexed tree drift from its primary, write a key over the ceiling, and put a record into a secondary's storage that no tree links (the last three came with GroveDB #1063) |
| `tests/verify_grovedb_indexed_tests.rs` | 12 | delete a secondary row, or insert an orphan one, behind the primary |
| `tests/indexed_reference_row_tests.rs` | 8 | overwrite a stored row |
| `tests/provable_sum_tree_tests.rs` | 4 | change a stored value without its hash, or a parent element with consistent hashes |
| `tests/flat_drop_tests.rs` | 2 | plant a root node record, and remove a tombstone's record between two steps of a drain |
| `tests/delete_indexed_tree_tests.rs` | 2 | seed a stale row in a secondary |
| `tests/coverage_round7_tests.rs` | 2 | delete rows from a secondary |
| `batch/move_element.rs` | 1 | bill a move against the stored size of each record, key prefix included |

Besides these, the tests of `grovedb/src/engine/tests.rs` name `RocksDbEngine` and run on it whatever engine the suite is on, as said above, and the tests of the hatches `raw_storage` and `ingest_subtree_sst` (feature `unsafe-dump-load`) are compiled for the RocksDB engine alone, as the hatches are. The dump and the load that every engine has (`grovedb/src/operations/dump_load`, GROVE-09) have their tests in two places: `operations/dump_load/tests.rs` runs on the engine of the suite, and `engine/lignin/tests/hatch.rs` names its engines and runs the flow on LigninDB, on RocksDB and from each to the other.

Thirteen tests that only read through RocksDB contexts, or committed a batch through the storage, go through `Engine` now (`Engine::subtree`, `Engine::apply_batch`, `NodeStore::cursor`, `NodeStore::has_node`) and run on every engine. So do four of the tests of the repair that came with GroveDB #1063: `drift_axis_secondary`, the helper that makes one axis's secondary drift, writes through a Merk of the secondary and the engine's batch. Three of the tests that use it alone check on every engine that each row the repair of grove version 5 removes leaves storage. The fourth, `the_repair_on_grove_v4_is_what_it_was`, pins the opposite for the repair of the released versions: its cost, its root hash, and the five records it leaves in storage that no tree links, each with its length. An engine has to hold such records, and show them to a cursor, to pass it.

One thing the second engine does not catch: `PinnedReads` is a type of its own, and its batch, transactions and handles are RocksDB's. A test that names `StorageBatch` (many write `StorageBatch::new()`), or calls a method of a storage context on a handle it opened through `Engine`, compiles on the two engines that are RocksDB's. On an engine with types of its own, as LigninDB is, it does not compile, so nothing can run on the wrong engine unseen, and `SuiteBatch` of the fixtures is the name to use instead.

What the suite still names of RocksDB is under the feature `rocksdb_storage`, so the suite builds for an engine that is compiled without it (GROVE-10): the storage type parameter of the estimated-cost helpers, `::<RocksDbStorage>`, in the tests that call those helpers by their public names (fourteen tests of `misc_coverage_tests.rs` and `automatic_backward_references_tests.rs`, and the two modules of `estimated_costs`, which are under `full`; the parameter is public API until OPS-10 folds it away); and `PinnedReads` itself. The prefix of a path is not among them: the tests derive it with `grovedb_storage::prefix::build_prefix` and `secondary_prefix_for`, which name no engine.

What the list means for LigninDB: the behaviour each of these checks, most of it `verify_grovedb` finding a damaged store, has no test on an engine that is not RocksDB. GROVE-10 decided that LigninDB needs none of them in this suite ([GroveDB on LigninDB](#grovedb-on-lignindb)).

### GroveDB on LigninDB

GROVE-10. `lignin` is the third engine of GroveDB's registry, and its type is `LigninEngine` ([`engine.md`](engine.md#the-lignindb-engine)). The fixtures open it as they open any engine, through `GroveDb::open`, so a database of the suite is a database of `lignindb` with the default options in a temporary directory.

- **A database a test closes is checked.** In a debug build `lignindb` checks a store when it is closed, with its physical invariant checker, and panics on a finding ("The check at a close" of `lignindb::db`). `LigninEngine` gives that check Merk's hash rules for every database it opens (`Db::check_hashes_by`), so the stored hashes of the nodes of every Merk in use are made again. A test that closes a store the checker calls unsound panics at the close, and so fails unless it catches that panic, whatever it asserted. The check is left out on a thread that is panicking, so a test that expects a panic and drops its fixture while it unwinds leaves a database that is not checked (two tests of `merk_cache` and one of `operations::delete` do), and for a database whose directory is gone, so a fixture closes its database before its directory is removed: the database is the first field of `TempGroveDb`, and a test hands `GroveDb::open` the path of its directory, not the directory. `suite_engine_tests::a_database_of_the_fixtures_is_checked_by_merks_rules_when_it_is_closed`, compiled for this engine, plants a key-value hash that is not its node's in a database of the fixtures and requires the close to panic.
- **A test writes a grove through GroveDB.** A test that writes the Merk of a tree by hand and does not tell the tree's element its root leaves what no operation of GroveDB leaves, and the check says so. Two tests of `element::query` did, and insert through `GroveDb::insert` now.
- **What a test may not name.** `StorageBatch`, a method of RocksDB's transaction (`commit`, `rollback`, `snapshot_age`) and a storage context type do not exist on this engine. 23 test modules named one of them and name `SuiteBatch`, `GroveDb::commit_transaction` and `GroveDb::rollback_transaction` now; a helper that takes a transaction states the lifetime of its database (`Transaction<'db>`, `TransactionArg<'db, '_>`), which the transaction of LigninDB is invariant in. Two tests ask what the seam does not and keep that part for the engines that answer it: how long a snapshot has been held (`snapshot_lifetime_is_observable`), and how many operations a storage batch holds (`merk_cache::tests::subtrees_are_propagated`, which also applies the batch and compares the root hash on every engine).
- **Between a flat drop and its drain** RocksDB keeps the records of the dropped tree under their prefix and LigninDB dropped them with the drop's commit ([`engine.md`](engine.md#flat-drops-and-their-drain)). Three tests of `flat_drop_tests.rs` assert what is under the dropped prefix there, and what `verify_grovedb` reports of a tree made again at the dropped path: they assert RocksDB's answer on the engines that keep the records and the opposite on LigninDB (`KEPT_UNTIL_THE_DRAIN`), and everything else of the drop and the drain alike.

What LigninDB needs of the tests that are not run once for every engine, and why:

| Tests | On LigninDB | Why |
| --- | --- | --- |
| The 77 [RocksDB-only tests](#rocksdb-only-tests-of-grovedb) | none | 76 damage a record under GroveDB in RocksDB's layout and expect code that names no engine (`verify_grovedb`, the reads of an axis, the repair) to find it. That code reads through the seam and is the same on every engine, and the reads it makes of a sound grove run on LigninDB with the rest of the suite. On LigninDB such damage is what the check at a close reports, which is tested where it lives (`lignindb::verify`, and `merk::store::lignin::hash` for Merk's rules): a test of this kind would have to write its damage through `lignindb` and then keep the close from checking it, for an answer the same code already gives on RocksDB. The other one (`batch/move_element.rs`) bills a move against the stored length of RocksDB's records, key prefix included, which is a length LigninDB does not store; the cost of a move on LigninDB is held beside RocksDB's by the engine's own tests of moves. |
| The integration tests (`grovedb/tests`, 80 tests in eight files) | all, in a build with LigninDB as the only engine | They use the crate as a dependent does, on the engine it exports. `cargo test -p grovedb --no-default-features --features lignin_storage,estimated_costs --tests` runs them on LigninDB, and they pass. `state_sync_serving_tree_type` derives its prefix with `grovedb_storage::prefix::build_prefix`. |
| The doc tests | all, in the same build | `cargo test -p grovedb --no-default-features --features lignin_storage,estimated_costs --doc`: they open the engine the crate exports. |
| The benches | none | Each has `required-features = ["rocksdb_storage"]` and measures RocksDB through GroveDB as it is released. LigninDB's numbers are the benchmark suite's (`lignin-bench`, PERF-01), on the reference machine. |
| The suite with LigninDB as the only engine | the unit tests build and run | `GROVEDB_TEST_ENGINE=lignin cargo test -p grovedb --no-default-features --features lignin_storage,estimated_costs --lib`: the build a node without RocksDB has. The tests that compare the two engines side by side (`engine/lignin/tests`) are written to run their LigninDB half there; the five of `side_by_side.rs` do. |

### GroveDB on the engine chosen at the open

OPS-03. `either-rocksdb` and `either-lignin` are the fourth and the fifth engine of GroveDB's registry. The type of both is `EitherEngine` ([`engine.md`](engine.md#an-engine-chosen-at-the-open)), which is compiled where both engines are, so each line names two features. The suite runs on the type twice so that the tests that take a fixture, or make a database with no engine named, go through the type to the engine the run is named for.

- **Which engine a run holds.** The fixtures open a database with `GroveDb::open`, which names no engine, in a directory they made. On this type that calls an engine to make the database where no entry of the directory says one: RocksDB, and in the unit tests built for `either-lignin` LigninDB (`WHERE_NONE_IS_SAID` in `grovedb/src/engine/either.rs`). So a database of a fixture is on the engine the run is named for. In either run, a successful unnamed open of a marked directory uses the detected engine. `suite_engine_tests::a_database_of_the_fixtures_holds_the_engine_the_run_is_named_for`, compiled for the two runs, holds a database of the fixtures to the engine of its run.
- **The two runs also differ** in the answers between a flat drop and its drain (`KEPT_UNTIL_THE_DRAIN`), in the test that plants a wrong hash through a handle of the suite's engine and requires the close to panic ([GroveDB on LigninDB](#grovedb-on-lignindb)), which is compiled for `lignin` and `either-lignin` in a debug build, and in the two tests of a checkpoint's log files of the next point.
- **Tests that are compiled for the engine `rocksdb` alone** ([RocksDB-only tests](#rocksdb-only-tests-of-grovedb)) take the storage of the suite's engine by `RocksDbEngine::storage()` or use RocksDB's own types on it, and are in neither run, as they are not in the run on `pinned-reads`. Two tests of `checkpoint_tests.rs` that look at the log files of a checkpoint RocksDB made go through `GroveDb` alone, and are compiled for `rocksdb` and `either-rocksdb`.
- **Two parts of tests ask RocksDB's own types what the seam does not** (how long a snapshot has been held, and how many operations a storage batch holds). They are compiled for `rocksdb` and `pinned-reads`, whose transaction and batch are RocksDB's, and for no other engine.
- **A test that names its engine runs on that engine in every run** whose build compiles it, whichever engine the suite is on. The tests of the type itself (`grovedb/src/engine/either/tests.rs`) are such tests: they are in every run of a build that has both engines, and the test of the one answer of RocksDB that the type changes ([`engine.md`](engine.md#the-write-scope-of-rocksdb)) is among them. No test asks the suite's engine for a write scope in the run on `either-rocksdb`: `GroveDb` asks only an engine that rolls a scope back.

Two runs are compared test for test only where they are built with the same features: a run of `cargo test -p grovedb` with the default features has no test that needs `lignin_storage`.

## Merk

Merk's tests are written against `merk::test_utils`:

```rust
pub trait TestEngine: Sized {
    type Transaction<'db>;
    type Batch: Default;
    type Subtree<'a>: NodeStore<'a>;           // deferred: writes go to a batch
    type ImmediateSubtree<'a>: NodeStore<'a>;  // writes at once

    fn open(path: &Path) -> Self;
    fn start_transaction(&self) -> Self::Transaction<'_>;
    fn commit_transaction(&self, transaction: Self::Transaction<'_>) -> CostResult<(), Error>;
    fn subtree(&self, path, batch: Option<&Self::Batch>, transaction) -> CostContext<Self::Subtree<'_>>;
    fn immediate_subtree(&self, path, transaction) -> CostContext<Self::ImmediateSubtree<'_>>;
    fn apply_batch(&self, batch: Self::Batch, transaction) -> CostResult<(), Error>;
}
```

It is the part of [`Engine`](engine.md) that a test of Merk uses, with the same names and the same two write modes. Merk cannot name `Engine`, which is GroveDB's.

| Name | What it is |
| --- | --- |
| `SuiteEngine` | the engine of this build |
| `SuiteTransaction<'db>`, `SuiteBatch`, `SuiteSubtree<'a>`, `SuiteImmediateSubtree<'a>` | its associated types |
| `TempEngine` | a database of `SuiteEngine` in a temporary directory |
| `TempMerk` | a Merk of the root subtree on a `TempEngine`, with `commit`. It is `Merk<SuiteSubtree<'static>>`. |
| `root_merk` | a Merk of the root subtree on any `TestEngine`, writing to a batch or read-only |
| `empty_path_merk`, `empty_path_merk_read_only` | as before: a Merk of the root subtree on a `Storage`, for callers outside the suite |

A test of Merk names these and no storage type. Before this task 13 calls in `test_utils` and the test modules of seven files opened RocksDB contexts themselves (`TempStorage`, `Storage::get_transactional_storage_context`, `commit_multi_context_batch`). They call the trait now.

`test_utils` is compiled in every test build of Merk that has `minimal`, and for other crates with the feature `test_utils`. The trait, `NodeStoreOnly` and the helpers that build trees in memory need no engine. `SuiteEngine`, its aliases, `TempEngine` and `TempMerk` are under `merk_test_engine`. With no engine compiled in, the test modules that open a store are left out and the others run.

The tests that still name RocksDB are tests of RocksDB:

- `merk/src/store/kv.rs`: the tests of the RocksDB adapter of `NodeStore`.
- `merk/src/store/tests.rs`: Merk on the in-memory store against Merk on RocksDB.
- A test that reads a handle as a storage context is compiled for the engine whose handle is one: `#[cfg(merk_test_engine = "rocksdb")]`.

### Merk on LigninDB

MERK-08. `LigninTestEngine` (`merk/src/test_utils/engine/lignin.rs`) is the third engine of Merk's registry. Its module documentation is the contract; in short:

- **The engine is a database of `lignindb`** in the directory it was opened for (`lignindb::Db`, with the default options). A transaction is a write transaction of it. A handle is a `LigninNodeStore` on that transaction: a deferred one with the batch it was opened with, which with no batch refuses every write, or an immediate one. A batch is a `LigninBatch`, applied to the transaction as one operation (`LigninBatch::apply`).
- **It enters the subtree of a handle that writes.** LigninDB reads nothing of a subtree that its directory does not hold and refuses every write to one ([node-store.md](node-store.md#opening-a-merk)). A test of Merk has no element above its Merk to enter the subtree with, so the engine does it: when a handle that writes is opened and the transaction shows no entry of its subtree, the subtree is entered in that transaction, if it is absent, as a Merk that stands alone. A handle that only reads enters nothing. The engine does not know what tree the Merk of a handle is, so the entry has the bytes `merk` in place of a tree type, until the conversion of a Merk that has a node states one and the statement is applied ([node-store.md](node-store.md#the-tree-type), `NodeStore::state_tree_type`). A batch is for the transaction its handles were opened in: another transaction may lack the entry of the subtree and can then refuse the batch.
- **In a debug build a database is checked when it is dropped**, but on a thread that is panicking and in the other cases that `lignindb::db` lists ("The check at a close"). `lignindb` then runs its physical invariant checker and panics on a finding. The engine gives that check Merk's rules for the key-value hash and the hash of a node, so each stored one of a Merk in use is made again and compared. A value hash is taken as stored: the values of Merk's tests are mostly no elements, and some are put with a value hash that their test states. The engine also gives the check the tree types that keep flat records (`keeps_flat_records`), by which it holds the data keyspace of each subtree to the tree type of its entry (`lignindb::verify`, "The data column by the tree type of the entry"): the bytes `merk` are no such type, so the check takes a record in the data keyspace of a subtree this engine entered for a node that no node links, and reports one that is not.

The tests of `merk/src/test_utils/engine.rs` hold the engine: with the two engines on RocksDB it stages, applies and commits a batch and writes at once through an immediate handle; two transactions that are the first to write into one subtree both commit where their keys differ, and of two that are the first to write one key of another subtree the second is refused; a history of handles, Merks, batches and commits, with a clear after writes that were made at once, costs on it what it costs on `RocksDbTestEngine`, call for call, and leaves the same root hashes; a subtree is entered for a handle that writes and for no other, and a transaction that has written nothing refuses a batch for a subtree that only another transaction has entered; and a handle that passes the seam on (`NodeStoreOnly`) passes on what a conversion states.

Two tests came with the registration. `merk::test::large_values_are_stored_and_read_back_under_every_tree_type` runs on every engine: it puts values on both sides of 256 bytes and of 4, 8, 16 and 32 KiB, and up to a megabyte, under twelve tree types, rewrites them with other lengths and reads them back by key and under the cursor. LigninDB keeps a value of more than 256 bytes out of its node's cell. `the_directory_names_the_tree_type_a_conversion_leaves` is compiled for LigninDB alone (`#[cfg(merk_test_engine = "lignin")]`): it reads the subtree directory.

The run of a suite on an engine is of the package's unit tests (`--lib`), as [above](#integration-tests-doc-tests-and-benches) for GroveDB. Among them, the tests that name a store run on the store they name whatever engine is selected: those of the RocksDB adapter and of `merk::store::lignin`, and the tests of `engine.rs` that name an engine. `grovedb-merk` has one integration test target, `merk/tests/restore_memory.rs`, which names the stores it measures and is ignored and run by hand ([node-store.md](node-store.md#chunks-and-restore)).

## The workloads and the differential fuzzer

`lignin-testkit` applies its workload streams to a database of any engine: `workload::apply`, `workload::Transactions` and the runner of the golden corpus (`golden::run::Runner`) are generic over `E: StreamEngine`. A `StreamEngine` is an `Engine` with one function more, `is_snapshot_read(&Transaction) -> bool`. A write transaction and a snapshot read transaction are one type of an engine, and the seam has no way to ask which a value is: whoever started it knows. `apply` is handed its transaction by its caller and refuses a step that is given the wrong kind, so it has to ask. `RocksDbEngine` answers in `lignin-testkit/src/workload/apply.rs`.

The crate is also built against the engine the golden corpus is pinned to, which is upstream's and has no seam (`lignin-testkit/corpus/README.md`). There the engine parameter is gone and the fuzzer is left out, by a cfg the crate's build script sets, `grovedb_engine_seam`.

The differential fuzzer (`lignin-testkit::diff`, VER-01) applies random operation streams to two engines and compares them after every step. The two are type aliases in `lignin-testkit/src/diff/engines.rs`:

| Alias | Engine |
| --- | --- |
| `Reference` | `RocksDbEngine` |
| `Candidate` | `LigninEngine` (GROVE-10) |

`StandIn` is RocksDB behind an `Engine` implementation of the test kit's own: the engine that stood in for LigninDB until it existed. Like `PinnedReads`, which lives in GroveDB's test build and cannot be named from another crate, it gives a read that was given no transaction a snapshot read transaction (RD2). It can also be opened with a planted defect (`Fault`), a cost that is one byte off for one size of write, which the fuzzer's own acceptance test has to find (`lignin-diff seeded`, `lignin-testkit/tests/diff.rs`). That test keeps planting its defect in `StandIn` whatever `Candidate` names.

Registering an engine with the fuzzer is two things: `impl StreamEngine` for it, and its name in `Candidate`.

Two engines report a failure of their own in their own variant of the storage error: RocksDB as `RocksDBError`, and a conflict as one of kind `Busy`; LigninDB as `StorageError`, and a conflict as `Commit(Conflict)`. So the name a step's error is compared by names no engine (`golden::run::error_name`): an engine's own failure is `StorageError`, what a write scope could not do is named with its reason, also where it came up through a Merk, and what the seam classes as an outcome of a commit (`grovedb::Error::commit_error`, also where the error came up through a Merk) is named by its class alone, as in `Commit::Conflict`. The corpus records no error under RocksDB's own name, which `tests/golden.rs` holds.

Four histories in which RocksDB keeps records where GroveDB changes an element and does not clear what hung under it are ruled as open differences that are put to the maintainer of GroveDB; in three LigninDB drops those records with their element, and in the fourth it refuses the write: an element written over a tree that held elements ([engine.md](engine.md#an-element-written-over-a-tree)), what is below a tree that was dropped flat while it held a tree, and the subtree of a tree that was dropped flat, itself, from the drop until a drain reclaims the record of the drop, which a tree that is made again at the path reads on RocksDB meanwhile ([engine.md](engine.md#flat-drops-and-their-drain)), and an indexed tree written over an indexed tree on grove versions 1 to 3, which LigninDB refuses (D-292, [engine.md](engine.md#an-element-written-over-a-tree)). The fuzzer names each a family (`diff::families`). The first three have a rule that is a path: the subtree of the tree that was written over and every subtree below it, every subtree below the dropped tree, and the dropped tree's own subtree while a record of its drop is pending. A case keeps the places it made so, from the operations both engines took: the trees an unconditional put was made over while the reference read them as holding elements, and the trees that were dropped flat, whatever they held. Which of the dropped trees have a pending record is read from the reference, as its block sees the records, after each operation that both engines answered alike, from the case's first flat drop on, and holds for every operation until it is read again, also for a read through a snapshot or with no transaction: the answers to an operation are held against the records as they were before it. The data, aux and meta records of a subtree at such a place are not compared: where they differ the case counts it for the family and goes on. An answer, a cost, a root hash and a proof are compared at every step; where one differs at an operation that names such a place (a query also names the subtrees below its own that it reads: one under a key its items select, where the branch of that key goes down by a subquery path or a subquery, and so on down each subquery; this is asked of the query as it is written and not of the grove, so whether such a key holds a tree and whether a limit ends the query before it comes there is not looked at), the case ends there, with its remaining operations not run, and is counted for the family, and the run goes on with the next case. The fourth family has no place and is of an answer alone: on grove versions 1 to 3, where the answers to an operation differ, the operation puts an indexed tree at a key at which the reference read an indexed tree before it, the reference took the operation and LigninDB answers `NotSupported`, the case ends there and is counted. All of it is required. The case ends before what is stored is compared again, so nothing stored is passed over for it. Of a batch the families count the operations by a rule about its lists, and not by what GroveDB applied: those that the caller of a partial batch adds last only where the batch has an operation of its own and the reference took it, and a put or a flat drop at a key that the batch names twice, where one operation can take the place of another, makes no place of a family, though the operations still name that key where an answer is compared. On grove versions 4 and 5 GroveDB removes the rows of an indexed tree that an operation which can replace is put over, and not under an insert that its caller knows not to replace (`insert_only_known_to_not_already_exist_op`), of which its own comment says "The caller asserts the key is new — no existence check is performed" (`grovedb/src/batch/mod.rs` at `e371a572`, lines 359 to 361 and 1359 to 1361). In that file, `op_could_overwrite` (lines 3750 to 3757) names the replacing operations and not that insert, only those are registered for the look at the old value (lines 3821 to 3843), and the look does nothing about the rows of a key that is not registered (lines 5180 to 5183). GroveDB does read the old element under such an insert, and removes no row for it: where the caller asks for `validate_insertion_does_not_override_tree` (lines 3786 to 3819), which the batches of the workloads do not; in the expansion of a whole batch for backward references on these grove versions, which reads the element at the key of a tree the batch writes, unless the key is in or below a tree that the batch makes where no tree stood, and keeps of it whether a tree stood there (`grovedb/src/batch/backward_references.rs`, lines 917 and 927 to 933); and in the look itself, which is handed the old value of every node the batch replaces, and in a partial batch deserialises it (lines 5126 to 5130). So a fifth family, of an answer alone and counted apart with its seed and step (D-354): on grove versions 4 and 5, where a batch lists such an insert of an indexed tree at a key at which the reference read, before the batch, an indexed tree a secondary of which held a row (D-358), the batch names no key in that tree or below it, so that it removes none of its rows, and no other operation of the batch names a key of the same bytes in any tree (the refusal names the key by its bytes), the reference took the batch, and LigninDB answers `NotSupported` in the words of its refusal of an empty indexed tree over an indexed tree whose rows the batch does not remove, for that key, the case ends there. Any other operation that LigninDB so refuses on those versions ends the run, and so does such an insert over anything else where the engines differ. On RocksDB the batch leaves an empty indexed tree whose secondaries still hold the old rows, which is the state of the fourth family reached on these versions; the unit that closes that family on every grove version takes this one with it. A difference at any other place or operation ends the run. The run prints, for each family, how many cases made such a place (for the fourth, in how many the reference took such a put, whatever LigninDB answered; for the kind of the next paragraph, how many ended there), how many had a stored difference passed over and how many ended at an answer (for the families at whose answers no case ends, below, how many had such an answer passed over), and for the last two the seed of one such case; and, of the cases it did not interrupt, how many were clean (they met no family at all, made no place of one, and were compared to their end), how many ended at an answer of a family and how many had something passed over, counted of the cases that neither were interrupted nor ended the run (the first whose tally reached the run's, which with several cases at once need not be the lowest).

One more kind of a step of the third family is counted apart, of an answer alone (D-348). A proof binds a tree it returns that is no Merk to the tree's own records, and RocksDB reads there the records it kept of the dropped tree, so its proof of a query that returns a tree made again at a dropped path before the drain is refused by its own verifier. A case ends at such a step, counted as "through a proof", only where all of this holds: the operation is a raw query of committed state; under a key that its items select, or those of a subquery it comes to, is a tree that the case dropped flat, whose record is pending and at whose path the reference reads a tree again; the engines differ in the proof or its cost and in nothing else, so the rows and the cost of the query are the same; and LigninDB's proof verifies to the root hash of its committed state and gives the rows LigninDB returned, path, key and bytes. The run prints the seed and the step of every such case. In a debug build GroveDB's own assertion fails there on RocksDB and the reference panics, which ends a run as a divergence: a debug run on grove versions 4 and 5 is made with `--keep-the-drop-contract` (`Shape::keeps_the_drop_contract`), which leaves out of every case each operation that makes an element again at the path of a tree that was dropped flat before a drain that follows a commit that follows the drop, so that no case comes to that history. The fuzzer's own test does so in a debug build. A release run is made without it.

One answer is of the third family by no place (D-420): the conflict that RocksDB alone answers to the commit of a block which wrote into the subtree of a dropped tree before a drain reclaimed the record of its drop. A drain is called outside any transaction and reads committed state, where the path of the dropped tree leads to no element while the block that made the tree again is open, so it reclaims the record. RocksDB's drain then deletes the range of the dropped prefix in every column family, beside the block and over the keys the block wrote under that prefix, and the block's commit is refused as a conflict; LigninDB dropped the subtree with the commit of the drop, its drain writes no key of the block, and the commit is taken. A case ends at such a commit, counted for the family, only where all of this holds: the operation is a commit, the reference answers `Commit::Conflict` and LigninDB takes it; in the block that this commit ends, an operation that the reference took wrote into the subtree at the path of a tree that the case dropped flat (the subtree a direct write names, or the path of an operation of a batch; the put of the tree's own element is a write into the tree above and is none), and after it a drain was called before which that tree's drop had a pending record and after which it has none, with no rollback to a savepoint since that write; and no operation that the reference took in the block drops a tree flat, since such a block writes a pending record itself, under a key that a drain may remove, which is a conflict on both engines. A difference at any other commit ends the run. With `--keep-the-drop-contract` no case comes to such a block, since the operation that makes the tree again is left out (`Known::family_of_commit`; the test `a_commit_that_rocksdb_refuses_after_a_drain_beside_a_tree_made_again_ends_the_case` of `lignin-testkit/tests/diff.rs` runs the shape on every grove version: it comes about on 4 and 5, which have the flat drop).

One family is of no answer that differs (GROVE-04-F3, D-422). A dedicated insert into an indexed tree whose key holds a tree makes two writes of its transaction: it removes what the tree held, and then puts the element ([engine.md](engine.md#a-dedicated-insert-over-a-tree-that-is-refused-after-its-removal)). Where the put is refused, both engines answer alike, with the same error, cost and root hash; RocksDB keeps the removal in the caller's transaction, with the old element over a subtree that holds nothing, and LigninDB rolls it back and keeps the tree as it was. A case ends at such an insert, counted, only where all of this holds: the operation is an insert through the method of an indexed tree (`Write::IndexedInsert`); before it, each engine's block read under its key a tree that holds elements; the engines' answers to it differ in nothing, and it failed; after it, the reference's block reads that tree as empty (`is_empty_tree`) and LigninDB's reads it as holding elements; and the next operation of the stream is neither a rollback of the block nor one that gives the block up. Where the next operation is one of those two, the engines hold the same again: the case is counted as having come to such an insert and goes on, what the engines store is not compared at that one step, and every later answer and stored record is compared. A tree under such an insert that holds values in flat records alone is not asked for, and a difference after it ends the run (`Known::swept_by_a_refused_insert`; the test `a_dedicated_insert_refused_after_its_removal_ends_the_case_unless_the_block_is_given_up` of `lignin-testkit/tests/diff.rs` runs the insert that leaves a sum out of range on every grove version).

**Below a tree that a batch's plain delete removed while it held elements** (D-378; a shape recorded from real blocks). A plain delete of a batch (`QualifiedGroveDbOp::delete_op`) removes the element under its key and nothing below it. Where the element is a tree that holds elements, RocksDB keeps the records of the tree under their prefix, which no element leads to, and LigninDB drops the subtree with its element ([engine.md](engine.md#a-subtree-leaves-with-its-element)). A read that takes the records under a prefix as they are then answers differently at or below the path of that tree: from the delete on, and once a tree is made at the path again, for the keys that the new tree has not written. It is a stated difference, and a family (`Family::BelowPlainDelete`) with a rule that is a path, as the first has: the subtree at the path of the removed tree and every subtree below it, to the end of the case, also where a rollback takes the delete back. A case makes such a place where a batch that both engines took with the same answer lists a plain delete of a key that the batch names once, the reference read at that key, before the batch, a tree that held an element, and the reference still holds a record under the tree's path once the batch is applied, as its block sees it (a node, an aux record or a meta record; `diff::state::a_record_is_under`): a batch that deletes what the tree holds before the tree makes none, unless a record of an earlier tree at the path is still there. The records of the subtrees at such a place are not compared, as for the first three families. Of an answer the family has less than they have. An answer is of it only where the operation is a read, also one in the block or through a snapshot, of a subtree at such a place, and the engines differ in the result, the error or the cost of the read and in no other part. A read of one key is of the subtree it reads in, so a read of the removed tree's own element in the tree above is none; a query is of its own subtree and of those below it that it reads. A read that returns a proof, or the root of an append-only tree, as its result (`Read::Prove`, and the typed reads of an MMR root, a dense root and a commitment anchor) is none either: those stay compared, and a difference in one ends the run. **A read that is of the family ends no case: it is counted and passed over**, since a read changes nothing, and the case goes on to the tree that is made again and to the writes into it. A write that names such a place (the tree made again, an element put into it) with its cost and the root hash after it, and the proof of a read with its cost and what the verifier makes of it, are compared as anywhere else, and a difference there ends the run, but for the three kinds of a write in the next three paragraphs. Where a place is also one of an element written over a tree, that family has every operation there. The reads that differ, at GroveDB's level, are `has_raw` of a key the removed tree held, a range query of the tree's path, which returns the kept element on RocksDB alone, beside what a tree made again there holds, and, while a tree that was made again at the path has not written the key, a range query of the tree above that goes down into it; and `is_empty_tree` of a tree made again there while it holds nothing. `verify_grovedb` differs there too: while a tree made again there holds nothing, it fails on RocksDB over the kept element (`tests/plain_delete.rs`); once the tree made again holds elements, what it answers on RocksDB depends on the kind of the tree, on what the kept record is and on where the old key falls among the new ones: in those histories of the test below whose store has no other kept record (a tree that counts and sums nothing, an empty sum tree kept under a key between two items; the check is asked after the write through the old key) it finds nothing, since it reads the kept record by its key and the record's own hashes hold; with an element on one side of the old key alone, or in a tree that counts its elements, it can fail, and it fails over another kept record in an empty tree made again elsewhere in the store, as one history of that test has it. The fuzzer's streams do not call it. The check at the end of a case calls it on the reference only on grove versions 1 to 3, and only where LigninDB's checker named a value hash that a delete left (below); a reference whose own check fails there ends the run, also in a case that made such a place. The one other call is in the reference's block right after a write that the reference alone took (below), on every grove version, and no case is held to what it answers. No case of the fuzzer has left such a hash so far. `grovedb/src/engine/lignin/tests/plain_delete.rs` holds the recorded sequence on both engines on every grove version, with each read that differs written out for each engine ([engine.md](engine.md#how-the-lignindb-engine-is-checked)).

**A write that both engines refuse at or below such a place** (D-386). A write of elements into a subtree whose tree a plain delete removed, and that no tree was made again for, is refused by both engines and writes nothing. RocksDB gets further before it refuses, because it finds the records it kept, so the cost of the refusal differs (seeks, bytes loaded, hash calls), and on grove versions 4 and 5 the error (`PathKeyNotFound` where LigninDB answers `InvalidPath`). A damaged stream asks for it. A family of its own (`Family::RefusedBelowPlainDelete`), counted apart with the seed and the first such step of each case, and passed over. A step is of it where all of this holds: the operation is a write of elements (a direct write other than of an aux record, or a batch); one at least of the subtrees it writes into is at or below such a place, and every other is the subtree a removed tree was in (for a batch the subtree of each operation it lists, and of a partial batch those of its own and of what its caller adds, since how far a refused batch came is not known), so a batch that also writes elsewhere is none by this; both engines failed it; they differ in the cost or the error and in no other part; and each engine has the root hash that it had before the write. A batch that also writes elsewhere is of the family in one shape, in which the order of its opens is known. The grove version is one of the first three, on which a batch of plain deletes opens its subtrees from the deepest level up and opens nothing before (a batch that puts a tree opens that tree first, and is not of this shape). The batch (`Op::Batch`, `Op::FlagsBatch`) lists plain deletes and nothing else, so it puts no tree, follows no reference and opens no path but those of its operations and the ones above them. Its deepest subtree, alone at its depth and so the first it opens, is under a record that a plain delete of the case left and that the case has not forgotten (below), which the reference holds as the element of a tree that keeps a Merk and LigninDB does not hold. Both engines failed it with `InvalidPath`, differently in the cost alone and with their root hashes as they were. **The check at the end of a case** (VER-07-F1, D-343). A run that found no divergence, wherever it ended (at the last operation of its case, at a named open difference, cut short, interrupted, or with no operation), ends with LigninDB's physical checker reading the candidate's store beside the engine's threads (`Db::verify`; `lignin-testkit/src/diff/close.rs`), in a debug and in a release build, with Merk's rules for a check on the grove version of the case (`MerkHashRules::for_check`) for the stored hashes of the nodes of every Merk. The engine gave the database the tree types when it opened it. A finding is a divergence of the part "close check" at the last step that was compared, or at step 0 where none was, and is shrunk as any other. The fuzzer does not drop it with a run that it interrupted: it is a finding of that case, and the run reports the finding of its earliest case. It reads committed state: what a case left in a transaction it did not commit is not read. On grove versions 4 and 5 the rules name no hash, so the value hash that a delete of a tree with elements leaves on grove versions 1 to 3 is a finding there, and the close of a debug build is told the same (`LigninEngine::check_closes_with_no_left_hashes`). On grove versions 1 to 3 the rules name that hash (`naming_left_hashes`) and the checker counts it apart. Each such hash has to be at a place, the prefix of its Merk and its key, that `verify_grovedb` reports on the reference's committed state, whatever the run came to before; `verify_grovedb` also reports hashes that the checker rightly does not name, so the comparison is "a subset of". A hash at another place is a divergence of the same part, and so are a reference whose `verify_grovedb` fails and a store in which the checker counts more such hashes than the 16 it lists, which are then to be counted by hand. A run in which a store was checked sound prints how many were, and how many such hashes were at the reference's places. A candidate that is not LigninDB's engine is not checked.

The streams of the golden corpus of the standard scale (430 traces; the five of the reference scale are not run here) are also applied to both engines side by side (`lignin-testkit/tests/pair_replay.rs`): each trace's stream is generated again and run through the fuzzer's pair runner on a fresh database of each engine, every step compared up to the first that differs, and what the two databases store compared at the end. The comparison is strict: a trace that comes to an open difference the fuzzer passes over fails. LigninDB's store is read by its physical checker at the end of each trace, in any build, as above, so a trace that leaves a store the checker calls unsound fails the test although every answer was RocksDB's. Every trace has to be the same to its last step: the test excuses none.

**A recorded history** (`lignin-testkit::diff::history`, VER-08-P0). The streams above are generated. `lignin-history` replays one that was recorded: the calls a caller of GroveDB made on `GroveDb`, written down as each call returned by a recorder inside the GroveDB revision the caller is built against. One line is one call: the method, its arguments, the number of its transaction or none, its grove version, what its callbacks were asked and what they answered in the order they ran, and what the call returned with its cost. Marks of the caller give the block a call belongs to and the root hash after the block.

The replay makes the calls on a fresh database of `Reference` and of `Candidate`, in the order of the stream and through the stream's transactions, with the caller's own options, the recorded answers of its callbacks and the grove version of the call. Of every call it makes it compares the outcome (a value by its `Debug` text, an error by the name of `golden::run::error_name`), the cost, and what the callbacks were asked. After every block it compares the two root hashes, which are alike only where both engines gave one. At the end LigninDB's physical checker reads the candidate's store as at the end of a case of the fuzzer, by the rules of the first grove version of the stream: what a delete on an early version left is still there under a later one. The first call the engines answer differently ends the replay unless it is told to go on (`--keep-going`); the calls after a first difference are made on states that may differ, and the report says how many were made before it. It is not `diff::pair::run`, whose case is a list of the test kit's operations applied with the test kit's options and callbacks on one grove version.

"Alike" is said of the calls a replay made, and the report counts what it did not make as the stream has it:

- The replay ends, and is not alike, at a line that is no whole record, a method that is in none of its lists, a write it cannot make, an argument it does not read, a batch that lists another number of operations than it names, a call made inside a callback of another call, and a call of a second thread. The stream has the order in which calls returned, and for the last two that is not the order of what they did to the database.
- A read in `calls::READS_NOT_MADE` is not made. It is counted by method.
- A call for which the stream lacks an argument is made with a stand-in and counted apart. There are two kinds: `put_aux` of a value longer than 256 bytes, which the recorder writes as a hash and a length and the replay writes as other bytes of that length; and the two reads that build delete operations (`delete_operation_for_delete_internal`, `delete_operations_for_delete_up_tree_while_empty`), which are made with none of the operations their caller was building.
- A call given no transaction has none in the stream. A transaction GroveDB started for it is there as a start and an end that no call names, and the replay starts only the transactions that a call names. A transaction that is open when the replay ends is dropped and the report says so: the store that is checked holds what was committed.

Apart from the comparison of the engines, the reference's answers are held against the recording's, by method: a value by its text, an error by its variant, a cost by its values. That says where the revision of this workspace answers a call otherwise than the recorded revision did, and it is no divergence. What is not held is counted too: the outcome and cost of the two reads that build delete operations, the value of a `get_aux` of a key, or of a `get_aux_by_key_prefix` of a prefix of a key, that a call wrote a stand-in under (its cost is held), and a value of a type the recorder does not write.

A stream may be written by hand in the same form (a range query as `path_query=range:/aa/bb`, a batch with `callbacks=storage-flags` for the callbacks of `grovedb-epoch-based-storage-flags` in place of recorded answers): `tests/history.rs` does, and holds one difference of the engines by it: a batch that removes a tree with a plain delete while the tree holds an element leaves the tree's records under its prefix on RocksDB, where a read that goes by the prefix and asks for no element on the way (`has_raw`) finds them, and LigninDB drops the subtree with its element. It is the difference [engine.md](engine.md#a-subtree-leaves-with-its-element) states for a clear that is told to look for no tree, reached by a delete.

| `cargo test -p lignin-testkit --test history` | hand-written streams through the same replay |

## CI

`.github/workflows/grovedb.yml`:

- The three test shards run the whole workspace, each suite on its first engine, with coverage. This is unchanged.
- The job `test-engines` runs each suite on each of its other engines: `cargo nextest run -p PACKAGE --all-features --lib` with the suite's variable set. Its matrix is what `.github/scripts/engine-suites.sh matrix` prints, which the job `detect-changes` puts in an output. No engine is named in the workflow, so registering an engine adds its run.
- A change to a registry or to the script runs the tests.

[`ci.md`](ci.md) lists every job that checks the engines and the LigninDB crates, and the platforms each runs on.

## Registering an engine

1. Add its name to the registry of the suite, with the Cargo feature of the crate that compiles it, or in GroveDB's registry its features with commas between them. The first line stays the default.
2. Give the name its type: a `#[cfg(grovedb_test_engine = "name")] pub type SuiteEngine = ..;` in `grovedb/src/tests/mod.rs`, or the same with `merk_test_engine` in `merk/src/test_utils/engine/suite.rs`, where the type implements `TestEngine`.
3. Run the suite on it. A test that does not compile, or fails, either found a difference the engine has to remove, or is about the records of another engine and gets that engine's `#[cfg]`.

Nothing else names the engine: the build scripts, the script and the workflow read the registry.

To add a suite of another crate, give the crate a registry and a build script like Merk's, and add its line to `suites` in `.github/scripts/engine-suites.sh`.
