# Engine: the seam between GroveDB and its storage engine

LigninDB task SEAM-04 ([plan](https://github.com/dashpay/grovedb/issues/1052), [task register 1](https://github.com/dashpay/grovedb/issues/1052#issuecomment-6960582299)).

`Engine` is everything `GroveDb` asks of a storage engine. It lives in `grovedb/src/engine/mod.rs`. `GroveDb<E: Engine = RocksDbEngine>` is generic over it. It has two implementations: `RocksDbEngine` (`grovedb/src/engine/rocksdb.rs`), which is `grovedb-storage` behind the trait, and `LigninEngine` (`grovedb/src/engine/lignin`, GROVE-01), which is `lignindb` behind it: [The LigninDB engine](#the-lignindb-engine). GroveDB builds with no engine at all: [Features and engines](#features-and-engines) (SEAM-07).

This document states the contract of the trait, how the RocksDB engine meets it, what `GroveDb<E>` looks like to its callers, and the choices the plan left to this task. It builds on the two seams below it, [`NodeStore`](node-store.md) and [`FlatStore`](flat-store.md), and on the transaction rules of [`transactions.md`](transactions.md).

## The shape of the seam

```text
GroveDb<E: Engine>           operations, batches, proofs, references, state sync
---------------------------- Engine --------------------------------------------
  E::Transaction<'db>        a write transaction, or a snapshot read transaction
  E::Batch                   the writes of one operation, staged across subtrees
  E::Subtree<'a>             a deferred handle of one subtree
  E::ImmediateSubtree<'a>    an immediate handle of one subtree
      NodeStore              the Merk of the subtree runs on it (SEAM-01)
      FlatStore              its data keyspace, and aux() and meta() (SEAM-03)
---------------------------- engines -------------------------------------------
RocksDbEngine                RocksDbStorage, Tx, StorageBatch, the storage contexts
LigninEngine                 lignindb::Db, LigninTransaction, LigninBatch, LigninNodeStore
```

An engine is `Send + Sync + 'static`: it is a database handle that every thread of a node shares. Everything else is an associated type, so no call through the seam is dispatched dynamically.

## Contract

### Transactions

The read rules are those of [`transactions.md`, section 4](transactions.md#4-what-each-handle-reads):

- A write transaction reads its own writes, and for everything else the latest committed state at the moment of the read (RD3). It has no snapshot of its own.
- A snapshot read transaction reads the state that was committed when it started (RD1). A write through it, the application of a batch, a write scope and its commit are refused with `Error::SnapshotReadOnlyTransaction`. Rolling it back is allowed and does nothing.
- Both are the same associated type, `Transaction<'db>`, as they are one type on RocksDB today. `GroveDb` takes either wherever it takes a transaction.
- A read with no transaction and a write with no transaction are made by `GroveDb`, not by the engine: an operation that is given no transaction starts one (`TxRef` in `grovedb/src/util.rs`). An engine sees a transaction in every call.
  - An operation that writes starts it with `start_transaction` and commits it when it is done (RD7). These are the operations that call `TxRef::new`.
  - An operation that only reads starts it with `start_read_transaction` and never commits it. These are the operations that call `TxRef::for_read`. An engine may pin that transaction to the state committed when it starts, which is RD2 on LigninDB. The RocksDB engine starts a write transaction for it, as before the seam, so each of its reads sees the latest committed state.
  - A read hands its one transaction to everything it calls, so the whole operation reads through it: a query in every frame it walks, a `get` in every hop of the reference it follows, a read of an append-only tree in the read of the element that owns the tree. Before the seam such a read started a transaction for each of these. RocksDB cannot tell the difference, because none of them is pinned. An engine that pins would have read a different state in each.
  - What still starts more than one transaction is more than one operation, as it was before the seam. `bulk_append`, `commitment_tree_insert_raw`, `dense_tree_insert`, `mmr_tree_append` and `private_document_store_insert` read the element of their tree as a read of its own and then start the transaction they write through. `insert_if_not_exists`, `insert_if_not_exists_return_existing_element`, `insert_if_changed_value` and `delete_up_tree_while_empty` are a read followed by a write. `apply_operations_without_batching` is one write for each operation it is given.
  - A proof does not start its transaction through `TxRef`. The prover starts a snapshot read transaction itself (`start_snapshot_read_transaction`) and reads every layer through it, the second proof of a layer it cuts under a per-instance cap included. The references it follows are read in three ways, as upstream has them:
    - A reference in an ordinary row is followed with no transaction: `prove_subqueries_v1` calls `rewrite_reference_row_v1` without one. Each such row starts a read transaction of its own, outside the snapshot.
    - A page that is skipped to by count over the whole query (`prove_count_offset_layer_v1`) rewrites its reference rows with no transaction either. It starts one read transaction for all of them before it looks at a row, whether or not the page holds a reference.
    - A page that is skipped to by count within a branch (`prove_local_count_offset_layer_v1`) hands the snapshot on, and its references are read in it.

    On RocksDB a read transaction reads the latest committed state, so the first two can read a target that was committed after the snapshot was taken.
- `commit_transaction` takes the transaction by value: a commit ends it whether it succeeds or not (CM6). The two commits CM1 refuses with the transaction left open do not reach the trait as it is. A scope borrows its transaction, so a transaction with an open scope cannot be handed to a commit. Pending marks and `NotFinalized` (SC9) belong to iteration two, and GROVE-11 adds them with whatever lets the caller keep the transaction.
- Savepoints form a stack. `rollback_to_savepoint` undoes every write since the newest savepoint and removes it. There is no operation that removes a savepoint without undoing.

### Commit errors

Every operation of `Engine` returns `grovedb_storage::Error`, the error type of all three seams (`FlatStore` returns it, and `NodeStore` wraps it). `GroveDb` hands it on as `grovedb::Error::StorageError`, as before the seam. There are two exceptions, which return `grovedb::Error`: `SubtreeMove::move_next`, because it hands back the error of GroveDB's own inspection of a record, and `delete_checkpoint`, because the removal the trait provides fails with the errors `GroveDb::delete_checkpoint` had before the call was in the seam.

A commit can end in more ways than success and failure ([CM5](transactions.md#81-sequence)). The engine-neutral outcomes are `grovedb_storage::error::CommitError`:

| Outcome | The transaction | The database |
| --- | --- | --- |
| `Conflict` | over, its writes discarded | unchanged |
| `NotDurable` | over | the commit happened and is visible; it is not known to survive a crash |
| `Unsettled` | over | unchanged in this session, which accepts no further commit; the next open settles it |

Any other error of a commit means the transaction is over and the database unchanged.

`Error::commit_error()` classes an error a commit returned, and `Error::is_commit_conflict()` asks for the one case Platform acts on. `grovedb::Error` has the same two methods, and classes a storage error that it holds as it is (`Error::StorageError`) or as the error of a Merk (`Error::MerkError` of `grovedb_merk::Error::StorageError`), which is what a write through a handle that writes at once returns. An error that was turned into text on its way has no class.

- An engine with outcomes of its own returns them as `Error::Commit(CommitError)`. That is what GROVE-01 maps LigninDB's `Conflict`, `NotDurable` and unsettled commit to.
- The RocksDB engine returns what it returned before the seam: `Error::RocksDBError` with the kind `Busy`. `commit_error()` classes exactly that value as `CommitError::Conflict`. So a caller that matches `rocksdb::ErrorKind::Busy` keeps working, and a caller that asks `is_commit_conflict()` gets the same answer on both engines.
- `Conflict` is reported for a conflict and for nothing else (CF6). A RocksDB `TryAgain` is therefore not classed: RocksDB returns it when its memtable history no longer reaches back far enough to tell whether there was a conflict. LigninDB always decides (CF9), so it has no such error.

An engine can also return `Conflict` from the application of a batch, for a batch that keeps the value of a node which another commit took away after the batch's handle read it ([`transactions.md`](transactions.md) CF2a, CF6). The batch changed nothing: its transaction is open and holds the writes it held before the batch, and a write scope of the caller's keeps what the application claimed in it. LigninDB returns it ([Errors](#errors)). RocksDB takes such a batch and its commit: the transaction wrote the node's record after the other commit, which is no conflict there, and what the other commit did to the node is lost (case A19).

The classification is of an error that a commit returned, and of that refusal of a batch. RocksDB does not return `Busy` from the other calls GroveDB makes.

State sync commits inside GroveDB, and wraps a failed commit in `Error::InternalError` with the error's text (`replication/state_sync_session.rs`). That was so before the seam, and an outcome cannot be classified there until it stops.

### Handles

A subtree handle lives inside one transaction, in one of two write modes ([flat-store.md](flat-store.md#transactions-and-visibility)):

- A **deferred** handle (`Subtree<'a>`) stages its writes in the batch it was opened with. Neither it nor any other handle reads them until the batch is applied. Opened with no batch, it is read-only.
- An **immediate** handle (`ImmediateSubtree<'a>`) writes to the transaction at once and reads its own writes. GroveDB uses it in state-sync restore only.

Both are a `SubtreeHandle<'a>`:

```rust
pub trait SubtreeHandle<'db>: NodeStore<'db> + FlatStore {
    type Aux<'a>: FlatStore where Self: 'a;
    type Meta<'a>: FlatStore where Self: 'a;
    fn aux(&self) -> Self::Aux<'_>;
    fn meta(&self) -> Self::Meta<'_>;
}
```

- As a `NodeStore` it is the handle a Merk of the subtree runs on: `Merk<E::Subtree<'a>>`.
- As a `FlatStore` it is the subtree's data keyspace, for the append-only trees.
- `aux()` and `meta()` are the handles of the subtree's two other keyspaces, in the same transaction and write mode.

An element can host more than one subtree: an indexed tree hosts its primary Merk, at the prefix of its path, and a secondary Merk for each axis, at a prefix derived from that one. `subtree_beside(path, prefix, batch, &tx)` is the deferred handle of such a secondary, opened by a caller that says whose it is. The trait provides it as `subtree_by_prefix(prefix, batch, &tx)`: to an engine for which a subtree is its prefix the element says nothing, and the RocksDB engine does not override it. LigninDB does, because it keeps the subtrees of an element together ([An indexed tree hosts several Merks](#an-indexed-tree-hosts-several-merks)).

The data keyspace of a subtree holds Merk nodes or flat records, and the element that owns the subtree decides which. It holds both in one case: under a tree that keeps flat records and was given a keyed child, which grove versions 1 to 3 take ([What differs on grove versions 1 to 3 under a tree that keeps flat records](#what-differs-on-grove-versions-1-to-3-under-a-tree-that-keeps-flat-records)). A handle does not know. The code that holds it does, and says so by the trait it calls: both traits have a `cursor`, so GroveDB writes `NodeStore::cursor(&handle)` for a walk over Merk nodes and `FlatStore::cursor(&handle)` for a walk over flat records. On RocksDB the two are the same raw iterator. On LigninDB they read different structures.

Outside `grovedb::engine` and the tests, GroveDB's code names `StorageContext` nowhere any more. The places where it called a storage context directly now go through one of the two traits:

| Site | Before | Now |
| --- | --- | --- |
| `has_raw` | `StorageContext::get`, then `is_some` | `NodeStore::has_node`, added to the trait for this. A record that does not decode counts as held, as before. |
| The deletion visitor's raw delete (`delete_internal_on_transaction/v2.rs`) | `StorageContext::delete(key, None)` | one `NodeChangeSet::delete_node(key, None)`, committed with `NodeStore::commit`, as [node-store.md](node-store.md#call-sites-outside-merk) names it. On a transactional context both stage the same delete in the shared batch. |
| Walks of Merk records (`Element::iterator`, `find_subtrees`, replication, verification, the visitor) | `StorageContext::raw_iter` | `NodeStore::cursor` |
| The append-only trees, the commitment frontier, the dense value read, `clear` of a subtree | `FlatStore` methods, since SEAM-03 | unchanged |
| Aux records, the pending-drop record, the restore marker | `aux()` and `meta()` of the RocksDB contexts | `SubtreeHandle::aux` and `meta` |

`grovedb::engine::node_store_error` keeps the error of the first two as it was: a storage error stays `Error::StorageError`.

Nothing in the seam takes an unchanged hash to mean an unchanged record. Since GroveDB #1059 the referrer list of an element that takes backward references is in no hash, so a stored record can change while every hash stays what it was. A batch stages every write it is given, a move carries every record, and no operation of the trait skips a write, or answers a read from what it read before, because a hash is the same.

### The batch across subtrees

`Batch` is the batch that stages the writes of one GroveDB operation across subtrees, `StorageBatch` on RocksDB. Its trait, `EngineBatch`, has what GroveDB calls on it besides creating one: `next_operation`, `take_pending` and `merge_overwriting`. The rules a batch keeps (one outcome per key, a put wins inside one operation, the later operation wins across a boundary) are those of [flat-store.md](flat-store.md#transactions-and-visibility) and TXN-08.

Applying a batch has two steps, because the partial batch needs them apart ([finding 8 of the storage surface](storage-surface.md#findings-for-the-seams)):

1. `settle_batch(&mut group, batch)` works out what the batch's writes cost and adds them to a `WriteGroup`, after what the group already holds. Nothing is visible yet. The cost it returns, the seeks and the bytes loaded for deletes that carry no cost, is charged whether or not the group is ever applied. The storage cost of the writes stays in the group as its pending cost (`WriteGroup::pending_cost`).
2. `apply_write_group(group, &tx)` applies everything in the group to the transaction, in the order it was settled, all of it or nothing, and charges the pending cost if it succeeds.

`apply_batch` does both. The partial batch settles what is staged so far (`batch.take_pending()`), reports the cost to its caller, lets the caller add operations that are staged into the same batch, settles those, and applies the group once.

`apply_write_group` and `apply_batch` return `Applied`. An engine that places nodes when their batch is applied (LigninDB, [P5 of the tree layout](tree-layout.md)) reports the locations of the written nodes there, for Merks that stay open. On RocksDB it is `()`. GroveDB drops it today: no Merk outlives the batch it wrote into. PERF-03 is the first user.

### Write scopes

DEC-03: inside one write transaction, several threads may write different Merks at once. The rules are [section 9 of `transactions.md`](transactions.md#9-write-scopes-several-threads-in-one-transaction). The trait has:

- `open_write_scope(&tx)` opens a scope, one writer's part of the transaction. A scope that needs what another open scope holds fails with `WriteScopeError::Overlap`. It never waits.
- `scope_transaction(&scope)` is the transaction as the scope sees it: its own writes, then what is merged into the transaction, then the committed state. It has the type of a transaction, so every operation of `GroveDb` that takes a transaction runs in a scope when it is given this view. Nothing in GroveDB has to be written a second time for scopes.
- `merge_write_scope(scope)` ends the scope and makes its writes the transaction's.
- `rollback_write_scope(scope)` ends the scope and removes its writes.
- A scope that is dropped is rolled back, as a transaction that is dropped is. The one exception is an engine that cannot roll a scope back at all and says so with `WriteScopeError::RollbackUnsupported`: there the writes of a dropped scope stay in the transaction, as they do after the refused rollback.
- Setting a savepoint on a transaction and rolling back to one need every scope of that transaction closed, and fail with `WriteScopeError::ScopesOpen` otherwise (SC8). The check is in `Engine::set_savepoint` and `rollback_to_savepoint`, which `GroveDb::set_savepoint` and `rollback_to_savepoint` call. Platform calls the methods of `Tx` itself, which know no scope. Nothing opens a scope on RocksDB, so nothing is missed there, and OPS-03 moves Platform to the methods of `GroveDb`.
- A commit needs every scope closed as well (SC8). The types see to it: a scope borrows its transaction, and a commit takes the transaction by value.

On existing GroveVersions GroveDB opens no scope: one thread writes the transaction, as the plan says of iteration one. How LigninDB maps those writes to its scopes is GROVE-01's choice (SC1).

The RocksDB engine allows one scope at a time, for the whole engine:

- A second scope, on any transaction, is refused with `Overlap`. The engine remembers which transaction the open scope belongs to, so the savepoints of every other transaction stay usable.
- The scope's view is its transaction, and its writes go there directly, so merging is closing.
- A scope on a snapshot read transaction is refused with `SnapshotReadOnlyTransaction`.
- `rollback_write_scope` fails with `WriteScopeError::RollbackUnsupported`, closes the scope, and leaves its writes in the transaction. A scope that is dropped leaves them there too. A caller that has to undo a scope on this engine sets a savepoint before it opens the scope and rolls back to it after the scope is closed, which is what Platform does for a state transition today. RocksDB can undo back to a savepoint, but it cannot remove a savepoint without undoing, in its Rust binding or its C API. A scope that set a savepoint would leave it on the transaction's stack when it merged, and the caller's next `rollback_to_savepoint` would stop there. Platform sets a savepoint for every state transition (P-12), so the engine does not touch the stack. Nothing needs the rollback on RocksDB: scopes are used from iteration two, when RocksDB is gone.

### One state across subtrees

A cursor reads the committed state as it was when the cursor was opened, under the transaction's own writes (RD6). `retarget_cursor(cursor, prefix)` points a cursor at another subtree and keeps that state, so one cursor can read an element in one subtree and then the tree it names in another without a commit landing in between. GroveDB uses it for local count offsets (`element/local_offset_read.rs`) and for the paginated reads of an indexed tree's secondary (`operations/indexed_tree.rs`).

It is a function of the engine and not of the cursor because the cursor trait, `RawIterator`, is shared with `grovedb-query` and names no subtree. On RocksDB it is the iterator's own `retarget`. On LigninDB a cursor holds a version pin, and retargeting keeps the pin.

**A retargeted cursor is sought before it is read or stepped.** Where it stands after the call is the engine's own: RocksDB's iterator keeps its place on the line of every subtree's records, and LigninDB's cursor stands on no record. GroveDB's callers seek before they read: the reads of a pinned view seek to a key (`read_value_from_view`, `local_count_offset_page_from_view`, `snapshot_fetch_node`). A step from no key of a cursor that was sought is defined on both engines ([flat-store.md](flat-store.md#a-step-from-no-key)).

### Moving a subtree

A batch `Move` renames a key and keeps what is under it. `move_subtree(from, to, batch, &tx)` starts the move of one subtree's data keyspace to another prefix and returns a `SubtreeMove`. The move is made by calling `move_next(inspect, bill)` until it returns `None`:

- Each call moves one record. It is shown to `inspect` first, as its key and its bytes. GroveDB classifies it there: it refuses a record the move must not carry, and it finds the trees nested under the moved key, which it moves next. If `inspect` fails, the record stays and the error is returned.
- `bill` gives what the record is charged where it lands. Its removal from the old prefix is charged as a delete that frees nothing.
- The steps are GroveDB's to order. It moves a nested tree as soon as it finds it, before the rest of the tree above, as before the seam.

On RocksDB a move is a copy, and `RocksDbSubtreeMove` makes the storage calls `move_subtree_storage` and `move_namespace` made: two contexts by prefix, one raw iterator on the source, and for each record a `put` under the new prefix and a `delete` under the old one. LigninDB re-hosts the subtree instead and moves no cell ([D5 of the tree layout](tree-layout.md)). What a move charges on existing GroveVersions is the same on both, and is BASE-06's and SEAM-05's.

### Outside the transaction

`wipe`, `flush`, the checkpoints and the three operations of `PendingPrefixDrops` take no transaction. Their contracts are in [flat-store.md](flat-store.md#other-paths-that-bypass-the-transaction) and [platform-requirements.md](platform-requirements.md) (P-05, P-14, P-23, P-24). `PendingPrefixDrops` is a supertrait of `Engine`, so the drain of `flush_pending_prefix_drops` is written for any engine.

Two things stay with the RocksDB engine: the hatches `GroveDb::raw_storage` and `GroveDb::ingest_subtree_sst` (feature `unsafe-dump-load`), which are on `GroveDb<RocksDbEngine>` by name. What they were used for has a form that every engine serves, and that takes a transaction: [Dump and load](#dump-and-load) (GROVE-09). `GroveDb::start_visualizer` (feature `grovedbg`) is on `GroveDb<E>`: [Inspection](#inspection).

### Dump and load

GROVE-09, feature `unsafe-dump-load`, `grovedb/src/operations/dump_load`. A snapshot of one subtree is baked on one grove and applied to another: Platform seeds the shielded pool of a devnet so ([P-30](platform-requirements.md)). On RocksDB that was a read of the subtree's records through `raw_storage()`, a RocksDB SST file, `ingest_subtree_sst` and `replace_subtree_root`. A RocksDB file and a RocksDB handle mean nothing to another engine, so the flow has four calls on `GroveDb<E>` and a stream of a stated format between them. Each takes the path of a Merk and the key of a tree in it, as `replace_subtree_root` does.

| Call | What it does |
| --- | --- |
| `dump_subtree(path, key, out, transaction, version)` | Writes the records of the subtree under `key` to `out`, with the element that hosts it and the root its records give. With no transaction it reads through a snapshot read transaction of its own, the state that was committed when it began, on both engines. Through a transaction it reads as that transaction does. |
| `load_subtree(path, key, input, transaction, version)` | Reads one dump from `input`, and no byte after it, and writes its records into the subtree under `key`. It writes no element. |
| `subtree_root_as(path, key, element, transaction, version)` | The root that the records under `key` give when they are read as the subtree of `element`: the root hash of the Merk whose root key and tree type `element` names, or the state root of the append-only tree that `element` is, as `verify_grovedb` makes it (`compute_non_merk_state_root`). The element the grove holds under `key` is not read. The call is an error where the element names a root key that no node has, and where Merk does not hash the root node under that tree type, as it does not hash a node that carries no count under a tree type with a provable count. It reads the records the root is made from, which need not be all the records of the subtree: the root node of a Merk, and the stored peaks of an MMR and not the leaves under them. It is no check of every record. |
| `replace_subtree_root(path, key, element, root, transaction, version)` | As before GROVE-09: writes `element` with `root` as the root of its subtree into the parent Merk and carries the change to the root of the grove. |

An apply is three steps: the load, the comparison of `subtree_root_as` with the root the dump states (`DumpedSubtree::root`), and the replacement. After a load that wrote nodes or flat records under the element of an empty tree, and until the replacement, that element commits to an empty tree: the records are there, and no hash above them says so. On LigninDB, where such a load handed over a Merk with nodes, the physical checker reports the value hash of the element in that state; a debug build runs that checker when a database is closed, with the one exception that [State sync](#state-sync) names. A caller that gives the three steps one transaction commits no such state, and a caller that commits such a load by itself, as a load with no transaction does, has such a grove until the replacement is committed. `dump_subtree` and `load_subtree` return `DumpLoadError`: `Io` for a stream that cannot be written or read, which a stream that ends inside a dump is (`UnexpectedEof`); `Malformed` for bytes that are not a dump this version reads; `Refused` for a subtree that is not dumped or does not take the dump; and `Grove` for an error of the grove. Neither returns a cost: the hatches are outside the cost model, as the ingestion of a file is.

**What a dump holds** is what the seams show of one subtree, the subtree of the element's own path:

| Keyspace | Read with | Written with |
| --- | --- | --- |
| data, for a tree whose data is a Merk | `NodeStore::cursor`: every node, as the record Merk encodes of it | one change set that is the whole Merk (`NodeChangeSet::state_whole_merk`), a child before its parent |
| data, for a tree that keeps its data flat (`uses_non_merk_data_storage`) | `FlatStore::cursor` | `FlatStore::put` |
| aux, meta | the cursors of `SubtreeHandle::aux` and `meta` | their `put` |
| roots | `NodeStore::root_key` of the subtree's handle: the record of a root key, where the handle reads one | `NodeChangeSet::put_root_key`, through a handle of the subtree |

The record of a root key is the one that the handle of the subtree reads and writes, wherever the engine keeps it ([The root-key record of a subtree](#the-root-key-record-of-a-subtree)): the dump and the load name no namespace.

The element decides which of the two the data keyspace is, on the grove that dumps and on the one that loads. It has to name what the subtree holds, and each side asks what it can see of that:

- The load asks it of the stream: for a tree of nodes, the element names the key of the one node that no link names, or no key where the stream has no node; for a tree that keeps its data flat, the element counts something where the stream has data records.
- The dump asks less of the subtree: for a tree of nodes, that the key the element names holds a node, or that there is no node where it names none; for a tree that keeps its data flat, the same as the load. It does not walk the links, so an element that names a node which is not the root of all of them is dumped, and the stream is one that a load refuses.

A subtree that a load wrote nodes or flat records into under the element of an empty tree, and whose element is not replaced yet, is refused by the dump on these grounds. The replacement of an element that names no root key over a Merk that has nodes would drop the Merk on LigninDB ([An element written over a tree](#an-element-written-over-a-tree)) and leave nodes that nothing reaches on RocksDB.

A dump **does not carry**:

- **what is under the subtree**: the subtrees of the trees that a dumped Merk holds, each of which is a subtree of its own, with its own prefix.
- **the secondary Merks of an indexed tree**, which its element hosts beside the Merk of its path ([An indexed tree hosts several Merks](#an-indexed-tree-hosts-several-merks)). An indexed tree is refused, by the dump, by the load and by `subtree_root_as`.
- **a Merk under the prefix of a tree that keeps its data flat**, which an append-only tree with a keyed child under it has on grove versions 1 to 3 (D-282). On RocksDB the flat cursor is the cursor of every record under the prefix, so such node records are dumped as flat records. The pair is not for such a tree.
- **the entry of the subtree directory**, which LigninDB keeps of a subtree beside its records.
- **the root Merk**, which no element hosts.

**The stream.** All integers are big-endian.

| Part | Bytes |
| --- | --- |
| magic | 8: `GRVSUBT\0` |
| format version | 4: `1` |
| element | a length of 4 and that many bytes: the element that hosted the subtree, as GroveDB serializes it |
| root | 32: what `subtree_root_as` gave for that element when the subtree was dumped |
| records | each: its keyspace in 1 byte (1 data, 2 aux, 3 roots, 4 meta), the length of its key in 4, the key, the length of its value in 4, the value |
| end | 1: `0` |
| record count | 8 |
| checksum | 32: Blake3 of every byte before it |

The records stand in the order of their keyspaces and, inside one, in the ascending order of their keys, each key once. The roots keyspace holds at most one record, under the empty key. A reader refuses a stream that is anything else. The format names no engine, no prefix and no path: in the tests below the same subtree gives the same bytes on both engines.

**What a load refuses, before it writes.** It reads one dump to its end, and what it reads has to be as the table above says. Each node record has to be the bytes Merk encodes of the node it decodes to, so that the record a store keeps is the record of the dump. The nodes of a Merk have to be one tree: every link names a node of the dump, no node is named twice, and one node is named by none. The element of the dump has to name what the records hold, as above. The element under `key` has to be a tree of the tree type of the dumped element. Its subtree has to hold no record, as the transaction reads it: no node or flat record, no aux record and no meta record, and its handle has to read no record of a root key. A load makes no hash of a node, and does not ask whether the keys of a Merk stand as the keys of a search tree do: the element in the parent commits to none of what is loaded until the replacement.

**A load is a write of its transaction.** It is read through that transaction alone until the commit and leaves with a rollback. With no transaction it is a transaction of its own, committed at its end. That is the same on both engines, and it is not what `ingest_subtree_sst` does:

| | `ingest_subtree_sst` (RocksDB engine) | `load_subtree`, RocksDB engine | `load_subtree`, LigninDB engine |
| --- | --- | --- | --- |
| Who reads the records | every reader, at once | the transaction; after its commit, every read of the state it left | the same |
| A rollback of the open transaction | the records stay ([P-30](platform-requirements.md): Platform probes for them before it ingests again) | the records leave | the same |
| A target that holds records, as the transaction reads it | Platform's module records that RocksDB refuses a file that overlaps keys it holds | `Refused` | `Refused` |

**Beside other writers.** A load looks at its target and then writes, and the look is no lock. Four sequences are held by tests on both engines ([How the LigninDB engine is checked](#how-the-lignindb-engine-is-checked)); in each the tree is an empty count tree and a dump holds nodes and no other record:

| Sequence | RocksDB engine | LigninDB engine |
| --- | --- | --- |
| A transaction inserts an item into the tree. A load with no transaction, of three other nodes, commits, with no replacement. The transaction commits. | commits; the tree holds four nodes under an element that names one | `Conflict`; the tree holds the three of the load |
| Two transactions each load a dump, with no key in common, and replace nothing. The first commits, then the second. | both commit; the tree holds the nodes of both | the second commit is `Conflict` |
| Two transactions each load a dump and replace the element, both before either commits. The first commits, then the second. | the second commit is a conflict | the second commit is `Conflict` |
| Two transactions each load a dump, with no key in common. The first replaces the element and commits. Then the second replaces the element and commits. | both commit; the tree holds the nodes of both under the element of the second | the second commit is `Conflict`; the tree holds the nodes and the element of the first |

On LigninDB a Merk with nodes that is handed over whole is a load of `transactions.md` LD6: to the conflict rule it is the puts of its nodes and a range over the data keyspace of its subtree (CF5), and its hand-over puts the node of the element again, to name the Merk (below). A load that hands over no node, of flat records or of a dump with no data, states no such range and puts no node of the element: it is the puts of its records. On RocksDB the conflict rule is of the keys a transaction wrote (`transactions.md`, cases A13 and A13b), a load writes its records and no other key, and the ingestion of a file is invisible to the rule (case A18). So on the RocksDB engine a caller lets no other writer into the subtree from a load until its replacement is committed, as the caller of `ingest_subtree_sst` answers for an empty target. Platform's flow has one writer: once it is ported, the load is given the transaction that makes the trees of the pool.

**How a load reaches the engine.** It goes through the seam as it is, with no call added:

- A Merk with nodes is handed over through an immediate handle (`Engine::immediate_subtree`), as the Merk of a state-sync restore is ([State sync](#state-sync)): on LigninDB a change set that says it is the whole Merk is refused by a handle that stages its writes, because a batch keeps one outcome for each key and no change set. The load calls `Engine::adopt_restored_subtrees` with the path of the subtree before the hand-over, which enters the subtree where it is not entered, and after it, which puts the node of the element again so that it names the Merk. On LigninDB the transaction lays such a change set out with the bulk loader where it has frames to lay it out in (TXN-10, `transactions.md` LD1 to LD4). On RocksDB the two calls do nothing and each node is one record.
- Flat records, aux records, meta records and the record of the root key are staged through a deferred handle and applied as one batch, by the engine's rules for a batch ([Subtrees are entered by the first batch that writes into them](#subtrees-are-entered-by-the-first-batch-that-writes-into-them), [The root-key record of a subtree](#the-root-key-record-of-a-subtree)). They are not laid out by the loader.
- So a load writes in steps, and each step is a write of its transaction: for a Merk with nodes on LigninDB the enter of the subtree where it is not entered, the hand-over, and the put of the element's node; then, where the dump has such records, the batch of the others. A dump with no record writes nothing. In a transaction of the caller's, a step that the engine refuses leaves the steps before it in the transaction: the caller rolls back, or back to a savepoint it set before the load. A load with no transaction is a transaction of its own, which is given up where a step is refused.
- No batch of a load drops or clears a subtree, which a transaction that serves its writes by key refuses beside a load (`BatchError::LoadBeside`).
- A Merk is one change set: it does not span two loads (TXN-10). The records of the whole dump are in memory from the read of the stream until they are written.

After the load and before the replacement the element still says what it said: for a tree of nodes, that its Merk has no root key. `subtree_root_as` therefore takes the element from its caller and not from the grove, and `replace_subtree_root` writes a tree over a tree whose subtree stays ([An element written over a tree](#an-element-written-over-a-tree), the rows of a tree that keeps its data flat and of any other tree).

**What Platform's port calls** (OPS-03; `packages/rs-drive-abci/src/shielded_snapshot/mod.rs`):

- `dump_shielded_subtree`: `grove.dump_subtree(pool_path, &[SHIELDED_NOTES_KEY], out, transaction, version)` in the place of the storage context, the raw iterator and the `SstFileWriter`. The `DumpedSubtree` it returns has the element (count, chunk power and flags) and the root, which the module reads from the parent and computes with `CommitmentTree::open` today.
- `apply_shielded_snapshot`: `grove.load_subtree(pool_path, &[SHIELDED_NOTES_KEY], input, transaction, version)` with the transaction of `InitChain`, in the place of the temporary file and `ingest_subtree_sst`; then `grove.subtree_root_as(.., &loaded.element, transaction, ..)`, compared with `loaded.root`, in the place of `CommitmentTree::open` on a storage context; then `replace_subtree_root(.., loaded.element, loaded.root, transaction, ..)` as today.
- `shielded_subtree_has_committed_keys` has nothing left to probe for: a load leaves with the rollback of its transaction. A subtree that does hold records is `DumpLoadError::Refused`.
- The module then names no item of the `rocksdb` crate and no `RocksDbStorage`. Its own header can stay around the stream, since a reader reads one dump and no byte after it, or go: the stream has the element, the root and a checksum.

### Threads

- An `Engine` is `Send + Sync`. So is `GroveDb<E>`.
- `Transaction`, `Batch`, the handles and `WriteScope` have no `Send` bound, and neither have `NodeStore` and `FlatStore`. On RocksDB a transaction is `Send`, and a storage context and a scope are not (a context holds `&StorageBatch`, whose operations sit in a `RefCell`). Nothing on RocksDB needs them to be: one thread at a time writes a transaction.
- `Send` is asked for where something crosses threads. That is GROVE-12, which sends a scope to a worker: it asks `E::WriteScope<'a>: Send`, and for the handles opened in it. LigninDB's types meet that (MERK-01: `LigninNodeStore` and a Merk on it are `Send`). A Merk is `Send` whenever its store is (SEAM-01).

## GroveDb<E>

```rust
pub type DefaultEngine = RocksDbEngine;
pub struct GroveDb<E: Engine = DefaultEngine> { db: E }
pub type Transaction<'db, E = DefaultEngine> = <E as Engine>::Transaction<'db>;
pub type TransactionArg<'db, 'a, E = DefaultEngine> = Option<&'a Transaction<'db, E>>;
```

`GroveDb`, `Transaction<'db>` and `TransactionArg<'db, 'a>` with no engine named are what they were: `GroveDb<RocksDbEngine>`, `Tx<'db>` and `Option<&'a Tx<'db>>`. Platform builds against this branch with no change to its source.

`grovedb::engine::DefaultEngine` is the one place that says which engine that is. In GroveDB's own unit tests it is the engine the suite was built for instead, which is how the tests, naming no engine, run on every registered engine ([`test-engines.md`](test-engines.md), SEAM-06).

Three rules decide where a function of `GroveDb` lives:

1. **A method that takes `self` is generic**: `impl<E: Engine> GroveDb<E>`. That is every operation: reads, writes, batches, queries, proofs, state sync, checkpoints, aux, the append-only trees.
2. **An associated function with no `self` and no engine type in its signature is on the default engine**: `impl GroveDb`. `GroveDb::verify_query(..)`, `GroveDb::open(path)` or `GroveDb::estimated_case_operations_for_batch(..)` name no engine, and Rust does not use the default of a type parameter to infer one, so such a call resolves only if exactly one `impl` has the function. This is how `HashMap::new()` works. It covers the proof verifiers, the estimated-cost helpers, and the constructors `open`, `open_checkpoint` and `delete_checkpoint`.
3. **The constructors have a generic twin**: `GroveDb::<E>::open_with_engine(path)`, `open_checkpoint_with_engine(path)`, `delete_checkpoint_with_engine(path)`, and `GroveDb::from_engine(engine)` for an engine opened with options of its own. `delete_checkpoint_with_engine` refuses a path of fewer than two components and then calls `Engine::delete_checkpoint`. `GroveDb::engine()` gives the engine back. `open_with_cidx_integrity_check` has none: it is `open`, then `verify_grovedb`, and an error if that reports an issue, which a caller with another engine writes out.

Without the `engine_generic` feature there is no `GroveDb<E>`, and `GroveDb` is a plain struct that names the proof verifiers, as before.

The type default of `GroveDb` is there where an engine is compiled in: with `rocksdb_storage` it is the RocksDB engine, and with `lignin_storage` and without `rocksdb_storage` it is the LigninDB engine. ### Lifetimes

`E::Transaction<'db>` is an associated type with a lifetime parameter. The compiler cannot shorten that lifetime in generic code, as it does for the concrete `Tx<'db>`. Three conventions in GroveDB's generic code follow from it. A caller that names a concrete engine sees none of them: for it `Tx<'db>` still shortens.

- A method that takes a transaction ties it to `self`: `fn get<'db>(&'db self, .., transaction: TransactionArg<'db, '_, E>, ..)`. A transaction the method starts itself borrows `self`, so both must be one type.
- A function that returns a handle or a Merk has a lifetime of its own for the borrow: `fn open<'a, 'db: 'a>(&'db self, tx: &'a Transaction<'db, E>, batch: Option<&'a E::Batch>) -> Merk<E::Subtree<'a>>`. The methods of `Engine` that open handles have this shape.
- A handle of an engine may have a destructor, so GroveDB drops a handle, or a Merk on one, before it moves the batch or the transaction the handle borrows.

One change outside GroveDB follows from the same fact: `ChunkProducer::new` in Merk took `&'db Merk<S>` with `S: NodeStore<'db>`, one lifetime for the borrow of the Merk and for what its store borrows. A generic handle cannot meet that. The two are separate lifetimes now.

### Engine-independent helpers

Ten associated functions of `GroveDb` that name no engine are free functions of the crate now. They are called from types that know no engine, the batch's Merk cache among them, or with a store of a test's own:

- on a `Merk<S>`, generic over `S: NodeStore`: `update_tree_item_preserve_flag` and its two batch variants, `get_element_from_subtree`, `capture_indexed_entry_state`, and from the verification `verify_indexed_axis_content` and `element_for_reciprocity_audit`
- on batch operations or plain values: `insert_indexed_tree_item_into_batch_operations`, `indexed_tree_item_with_root_state_into_batch_operations`, and `axis_label`

Functions that take a `Merk<S>` are bounded by `S: NodeStore<'db>` and not by an engine, so a test can run them on a store of its own. `FaultableReads` (`grovedb/src/tests/faultable_reads.rs`) is such a store: it wraps any `NodeStore` and fails the node reads of an armed key with a storage error. `open_merk` reads a subtree's parent element through it in test builds, on every engine. The ten tests of `parent_read_fault_tests.rs` (GroveDB #1056) open their handles with `Engine::subtree` and read them as a `NodeStore` or a `FlatStore`, so they name no storage context. The fixture that opens their database opens the engine of the suite ([`test-engines.md`](test-engines.md)), so they run on every registered engine. `a_failed_parent_read_is_a_storage_error_on_a_second_engine` names its engine, `PinnedReads`, and runs on it in every run.

## How the RocksDB engine is checked

`RocksDbEngine` keeps one piece of state, the flag for the open write scope. Everything else forwards. What can go wrong is a call that is missing, made twice or made with other arguments, and a cost that is dropped or added. `grovedb/src/engine/tests.rs` runs the same history on two databases, one through the engine and one with the calls on `RocksDbStorage` that GroveDB made before the seam, and compares:

## The LigninDB engine

`LigninEngine` (`grovedb/src/engine/lignin`, GROVE-01, Cargo feature `lignin_storage`) is one open LigninDB database, `lignindb::Db`. `LigninEngine::open_with(path, &Options)` opens one with options of the caller's, `LigninEngine::new(db)` takes one that is open, and `database()` gives it back. Its handles are the node store of Merk on LigninDB ([node-store.md](node-store.md#the-lignindb-store)), and its batch is that store's batch.

### What a transaction is

- **A write transaction has no writer of its own.** Its handles read it from outside every scope (`transactions.md` RD3), and each write, the application of a batch or one write of an immediate handle, goes through a scope that is opened for it and merged when it is made, or rolled back if the transaction refuses it (SC1). So no scope is open between two calls, and a savepoint, a rollback and the commit find every scope closed (SC8). A scope that is opened while no other is open has its writes laid out as it makes them, so this is the path of one writer.
- **A read with no transaction is a snapshot** held for the operation (RD2), and so is a snapshot read transaction (RD1). The subtree directory is asked for a subtree by the first read of it through the snapshot, and the entry is kept for the later ones.
- **A write with no transaction** is made by `GroveDb` as a write transaction of its own, committed at once (RD7). It waits for no open write transaction. An open one reads it wherever it has not written the key itself, and its commit then fails with `Error::Commit(CommitError::Conflict)` exactly where the two wrote a key (CF2): the rule of RocksDB's optimistic transactions. On existing GroveVersions any two tree changes share the root node of the root Merk (GM1), so a transaction that has changed the tree conflicts with every tree change committed beside it, and not with an aux record.
- **A write scope's view** reads as the scope does and writes through it. A group of more than one settled batch is refused through a view: a scope that lives on cannot take a part of them back.

### Subtrees are entered by the first batch that writes into them

LigninDB reads and writes no record of a subtree that its subtree directory has no entry for (`transactions.md` CV9). On RocksDB a subtree is its prefix, and GroveDB says of no operation which subtrees it makes. So the engine says it, where a group is applied (`grovedb/src/engine/lignin/enter.rs`):

- A subtree that a batch holds a write for, in any column, and that neither the transaction nor a batch of the group has entered, is entered with the group: by the batch that enters the subtree its host is in, whether that batch enters it itself or the engine enters it with that batch by this rule, and by the first batch where the subtree its host is in is entered already or the subtree has no host. A batch knows the subtrees it writes into from the handles that staged the writes (`LigninSettled::written`); a write that a later operation of the batch took back is none. A batch that enters a subtree itself (`LigninBatch::enter`) has said its host and its tree type, and the engine looks at neither. What the engine adds is an enter of a subtree **if it is absent** (`lignindb::txn::SubtreeWrite::EnterIfAbsent`): the look says which subtrees the transaction does not hold as entered, and the transaction judges the enter where the write is laid out, when the batch is applied and again over every commit that lands beside it. A subtree that such a commit entered is found, and stays as that commit left it.
- Its host is the element its handle named: the last segment of the path it was opened by, or what the directory holds for a handle by prefix, which is none for a subtree that is not entered. A subtree is entered after the one its host is in. Under a key that holds no element once the group is applied, the first write that puts a node or a record is refused with `Error::NotSupported` and nothing of the group is applied: the directory would name a host that is no node, or none for a subtree that an element inserted later points at. RocksDB takes such a write and keeps records that no element leads to. Removals alone, for a subtree that is not entered, are not handed to the transaction, but for the removal of a root-key record that the engine keeps outside the subtree ([The root-key record of a subtree](#the-root-key-record-of-a-subtree)), and no enter is stated on their account, in a group no batch of which enters, drops or clears a subtree itself, or states one anew ([A subtree leaves with its element](#a-subtree-leaves-with-its-element)).
- Its tree type is the one of that element: from the value that the last batch of the group to state one states for it, and from the transaction where no batch of the group states a value, because none writes the element or those that do keep the value it has. With an element that is no tree, and for a subtree with no host, the directory keeps no tree type, and `Merk::open_from_directory` refuses the subtree as it refuses any other bytes. Nothing in GroveDB opens a Merk from the directory yet.
- The root Merk has no element, and is entered as a tree of the normal type. The namespace of the pending-drop records has none either, and keeps no tree. The engine enters both when it opens a database that does not have them, and its wipe enters them in the commit of the wipe; a batch that finds one gone enters it as any other subtree.
- The look can be stale when the group is applied: the look is several reads of the transaction and the application an operation after them, and a commit beside the transaction can be published between any two of them. A subtree whose entry the look reads more than once is as the last of those reads found it: no enter is stated for one that was entered then. A Merk of an indexed tree is judged by that read too: one that was not entered then is entered if it is absent, also where the look found another Merk of the tree entered, as it does where a first writer's commit is published between its reads of the two; one that was entered then under its element stays, and is stated anew where the element names it otherwise; and one that was entered then under another element, or under none, refuses the group. So a transaction that lays the group out refuses a write into one that a wipe took since (`BatchError::NotEntered`), and it refuses an enter that was stated for a subtree which is entered otherwise by now (`BatchError::EnteredOtherwise`). The engine looks again, and applies the group with what that look states, where all of these hold. The transaction refused the group for the entry of a subtree, and found it otherwise than the look had: no entry, for a subtree that the look stated no enter for, and that it found entered or that holds the element of an enter it stated; or another entry than the one the look stated an enter for; or no entry, for a subtree that the look found entered and stated anew, or stated the drop of as a secondary its element hosts no more, or found entered under a removed node and stated the drop of ([A subtree leaves with its element](#a-subtree-leaves-with-its-element)). A subtree that the look stated an enter for and that has no entry where it is needed waits for an enter of the group itself, as one that is named as the subtree of its own element does: no commit made that so. No batch of the group enters, drops or clears a subtree itself, or states one anew, so that what the look states of subtrees, which is enters, drops, clears and statements anew, is all that the group writes of them: where a batch makes one itself, the group can be refused for an entry by its own doing, with nothing published beside it, and the engine does not tell that from a stale look, so such a group is not looked for again. One operation of GroveDB makes such a group: the conversion of a tree to its 128-bit counterpart, in whose batch Merk states the converted Merk anew where the Merk has a node ([A converted tree is stated anew](#a-converted-tree-is-stated-anew)). And a commit was published since before that look: the latest version of the database is another than it was then. Every other refusal is the caller's answer as it is, and nothing is looked for after it: a refusal of the look, as the one of a first write under a key that holds no element; a refusal of the transaction that names no entry, or the entry of a subtree the look decided nothing of; and a refusal for an entry where no commit was published since before the look. The seam has one thread at a time write through a transaction, and what that thread's own calls do to the transaction is no commit. An application that the transaction refused left no write of the group in it; a write scope of the caller's keeps what the application claimed in it. So a record that is written into a keyspace which a wipe took after the look is taken into the keyspace entered again, as RocksDB takes it, also where another writer entered it again before the next look. A record that is written into the subtree of a tree which a wipe took is taken where the tree is inserted again by then, and is refused as a first write under a key that holds no element where it is not. A record that is written into a subtree which another writer entered after the look is taken into that one. A transaction that serves its records by key lays nothing out, so the checks that the frames make of entries are not made where it takes a group: what it holds is judged at its commit. What it checks with no layout can still refuse the group where it is applied.

So a tree that was inserted and never written into is in no directory, and is read as the empty tree it is: an open of it costs what it costs on RocksDB and finds no node. The enter is charged nothing and is a write of its transaction: it is rolled back with it. It is no key of the conflict rule, and it is made only where the subtree is absent: two transactions that each make the first write into one subtree meet by the keys they wrote, and by nothing else (below).

A group of more than one settled batch, which the two segments of a partial batch are, can write the nodes of a tree's Merk in one batch and the node of the tree's element in a later one. The first batch then stops below the element and leaves the root of the Merk for the element's node to name ([T3 of the tree layout](tree-layout.md)). So in such a group the engine says of each tree whose data is one Merk, and that the group has a named write for, that its element hosts that Merk, in every batch (`LigninSettled::host`): the batch that puts the element's node names the Merk in it, and the cell points at the root the Merk has by then. A tree that keeps its data flat has no Merk to name. The last batch of the group that writes nodes of the Merk has to put the element's node, or a later batch has to: a group in which a batch writes nodes of the Merk after the last batch that puts the element's node is refused with `Error::NotSupported`, and nothing of it is applied, because no node would name a root that such a batch moves. One such group is taken: where the element as the group leaves it names no root, no batch up to the last one that puts the element's node writes nodes of the Merk, that later batch states no root for the Merk (`LigninSettled::empties`), and every secondary of an indexed tree that is entered under the key is without a node once the group is applied. No root is left for a node to name then, and the node of the element is written as one that hosts nothing ([An empty tree written before the Merks under its key are emptied](#an-empty-tree-written-before-the-merks-under-its-key-are-emptied)). Every other such group is refused. GroveDB's batches make no other such group: a segment of a partial batch that changes a Merk writes the element above it, or leaves that to the segment after it.

What this leaves to later tasks:

- **A subtree that is entered under no element takes no write by the path of an element** (`GROVE-04-F1`, D-277). A write through a handle by prefix into a subtree that is not entered enters it under no element, and no statement of the directory gives an entered subtree a host. A write into such a subtree through a handle that names an element, by the path of a tree or beside the primary of an indexed tree, is refused with `Error::NotSupported` where the key that the handle names holds an element once the group is applied, and nothing of its group is applied. RocksDB takes the write. Where that key holds no element then, the engine does not refuse on this account: a record written by the path of such a key goes into the subtree as it is entered, under no element, as on RocksDB (`a_record_by_the_path_of_a_key_with_no_element_goes_into_the_subtree_under_no_element`). No operation of GroveDB writes by prefix into the subtree of a tree's path before the tree is written into by its path: its handles by prefix are of the secondaries of an indexed tree, which are entered with their primary, of the namespace of pending drops, and of a restore. See [An indexed tree hosts several Merks](#an-indexed-tree-hosts-several-merks).
- **The entry of a tree of one Merk keeps the tree type it names, but for a subtree that a conversion states anew** (MERK-09, MERK-08). A tree of one Merk whose element is written again as a tree of another type with a root key, or whose subtree the same group writes through a handle that loaded nodes of it, keeps the tree type and the host of its entry, and `Merk::open_from_directory` opens the subtree with the tree type that entry names. The conversion of a tree to its 128-bit counterpart is the exception, for the Merk it converts where that Merk has a node: the entry then names the wide tree type ([A converted tree is stated anew](#a-converted-tree-is-stated-anew)). The Merks of an indexed tree are stated anew wherever a group writes one of them by name and its element ([An indexed tree hosts several Merks](#an-indexed-tree-hosts-several-merks)). GroveDB's own opens take the root key and the tree type from the parent element and are not affected.
- **Two transactions that both write first into one subtree**: the second to commit finds the entry of the first, whether the first committed before the second looked, between its look and its application, or after both were applied. The enter is no conflict. The second commit is a conflict (CF2) where the second had written a key, before the first committed, that the first wrote too, as on RocksDB. On existing GroveVersions that is every pair of writes that change a tree and are both applied before either commits, since both changed the root Merk (GM1). Where the second had written no such key, as with two writers of different aux or meta records of one subtree nothing has entered, both commit, as on RocksDB. One difference is left, at the seam only: the commit of the second is refused by the directory, with `Error::StorageError` and the engine's words (`BatchError::EnteredOtherwise`, which names both), where both were applied before either committed and the two state one subtree as two. That takes two first writers of which one names the element that hosts the subtree and the other, through a handle by prefix, names none, or two that hold different tree types for that element because one of them wrote it. Where the first had committed before the second was applied, both are taken: the second finds the subtree entered and states nothing, at its first look or at the look after its group was refused (above).
- **A group reads the element that a handle of a subtree it writes into names, where none of its batches enters that subtree itself, none states a value for the element's node or removes it, and the subtree is not entered as the one Merk of a tree** (GROVE-12): for a subtree that is not entered, whose tree type is the element's, and for a Merk of an indexed tree, whose place is the element's to say. The read is of a node of the Merk that holds the element. Through the view of a write scope, while another open scope holds that Merk, the read is refused and with it the group (`WriteScopeError::Overlap`). A record of a subtree that is entered as the one Merk of a tree is written with no such read: a subtree leaves the directory with its element, so its entry stands for the element. GroveDB opens no write scope before GROVE-12.
- **A write scope's flat cursor does not keep the committed state it was opened on** (RD6): it reads the committed state of each move (`node-store.md`, "Flat records"). GroveDB opens no write scope before GROVE-12.
- **An immediate handle enters nothing.** A write through one into a subtree that is not entered is refused by the transaction, but for a write of a root-key record that the engine keeps outside the subtree, which is no write into it ([The root-key record of a subtree](#the-root-key-record-of-a-subtree)). A restore writes through immediate handles, and says which subtrees it writes with `Engine::adopt_restored_subtrees`: [State sync](#state-sync).

### An element written over a tree

GROVE-03, D-133. On RocksDB an element that is written over a tree changes one record. The records under the tree's prefix stay, and so do those of the trees it held under theirs. The prefix of a subtree is its path's, so a tree that is made at that path later stands on them. On LigninDB the cell of a node hosts the Merk of its element, and no more Merks than its element has ([D1 of the tree layout](tree-layout.md)). So the engine says what leaves, where a group is applied (`grovedb/src/engine/lignin/over.rs`), after it has worked out what the group enters.

It looks at each write over a tree: a node that a batch of the group puts with a stated value, through a handle that had loaded the node with the element of a tree as its value (`LigninSettled::over_trees`), in a subtree whose path the engine knows. It knows the path of a subtree that a handle by path wrote into with the group: the engine tells such a handle its path (`LigninNodeStore::at_path`), and the batch keeps it for the subtree (`LigninSettled::path`). A handle keeps the keys of the nodes it loaded so, and reads nothing for it. The subtree in question is the one of the element's own path. The engine derives its prefix from that path and the node's key, and looks at it where the directory has it under that element. The element as the group leaves it is the one that the last batch of the group to state a value for the node states.

The table is read for an element that is no tree or a tree that hosts one subtree. What becomes of the subtrees under an indexed tree is said in [An empty indexed tree written over a tree](#an-empty-indexed-tree-written-over-a-tree).

| The element as the group leaves it | The subtree |
| --- | --- |
| no tree | is dropped |
| a tree with no root key, whose subtree the group does not write | is dropped if it has a node or was entered as a tree of another type |
| a tree whose subtree the group writes, where a change set of its Merk is of a writer that began with no node (`LigninSettled::began_empty`) | is dropped and entered again, as a tree of the element's type, if it has a node or was entered as a tree of another type |
| a tree that keeps its data flat | is dropped if it was entered as a tree of another type, and entered again if the group writes it |
| any other tree | stays |

The writer of a tree that its own batch makes begins with a Merk that has no node. That tells a tree written over a tree from the tree written again with a new root hash, which every write below it does. The store tells the two by what Merk says of the nodes it puts. With each put of a commit Merk gives the cost of the write, which says whether the node is new to the Merk as its writer has it (`KeyValueStorageCost::new_node`): a node that it did not read from the store and did not write before, whose key is charged as a key that is added, on both engines. The first change set of a Merk that was opened with a root puts that root or removes it, and a root that was read is no new node. So where the first change set of nodes that a handle stages puts nodes, removes none and puts only new ones, it begins a Merk, and its writer began with no node (`LigninSettled::began_empty`). That first change set decides it, for itself and for every later one of the handle, which are of the same writer, whatever a later one holds by itself: a segment of a partial batch can remove the root its Merk was opened with, and the operations added after it write the same Merk on; a first segment can make a tree, and what is added after it writes into the same new tree. A change set that a handle stages after it took in an application of the Merk (`LigninNodeStore::take_locations`) writes on what that application left. What a batch asks the store for by a key through the handle of the new tree, before it writes there, does not count: until the group is applied the store holds under the prefix what the tree that was there had, on both engines, and GroveDB decides alike on both what an insert of an element only where its key holds none (`GroveOp::InsertIfNotExists`) does when it finds a record there. The engine takes the writer at its word: where the first change set of nodes that a handle stages removes none and puts only nodes that came with the cost of a new node, the change sets of that handle are those of a new tree, whoever staged them.

A drop takes every subtree below with it and names none of them (`SubtreeWrite::Drop`), so of two dropped subtrees, one below the other, the upper is named. It is made with the first batch of the group. The element's node is written as one that hosts nothing where no Merk of the group takes the place of the one that leaves: where the subtree is not entered again, and where it is entered again as a tree that keeps its data flat, which has no root. Where the subtree is entered again with a Merk, the node names that Merk. Where the subtree of a tree with one Merk stays, the node names that Merk too, with the root the directory has for it: an earlier group of the transaction can have written the Merk and not the element, as the group does that removes the records of a tree before another is written over it. A subtree below a dropped one that the group writes into, under an element that the group states, is entered again with the group as a tree of that element's type: a batch that makes a tree with a tree in it, over a tree that had one under the same key, writes into both.

The drop is charged nothing, as RocksDB charges nothing for the records it leaves. It is a write of its transaction: a rollback undoes it, and so does a rollback to a savepoint before it.

The look for what a group drops can be stale when the group is applied, as the look for what it enters can ([Subtrees](#subtrees-are-entered-by-the-first-batch-that-writes-into-them)), and the group is looked for again by the same rule.

- Where the look found the subtree and a commit beside the transaction dropped it since, the transaction refuses the drop of a subtree that is not entered (`BatchError::NotEntered`) and takes nothing of the group. The engine looks again, where no batch of the group enters, drops or clears a subtree itself, or states one anew, and a commit was published since before the look, and applies the group with what that look states, which is no drop of that subtree while it is not entered. A group that writes into a subtree which leaves with it and is not entered again, as the subtree of an element that it leaves as no tree, is refused for that subtree by its own doing, whatever was published beside it, and is not looked for again: GroveDB refuses such a batch itself and applies nothing of it, and a caller of the seam gets the transaction's refusal.
- The look for what is entered comes first. A subtree that it found absent, and that the look for what is dropped finds entered and states the drop of, is entered once, as the second of the two has it.
- Where both found no subtree of a tree that the group leaves as no tree, or as a tree that it does not write into, and such a commit entered the subtree before the group was applied, by a first write into the tree, nothing is dropped and the look says nothing of the element's node. The element is written as the group states it, its node keeps what the other commit hung under it, which is a Merk where the tree's data is one, and the entry outlives the tree. A group that writes into the subtree itself meets that commit as two first writers of one subtree meet ([Subtrees](#subtrees-are-entered-by-the-first-batch-that-writes-into-them)). Where the group leaves an item over a tree whose data is a Merk, the physical checker reports that node and nothing else: an element with no Merk whose cell hosts one (`HashUnchecked`). The two transactions both wrote the element's node, and meet as a conflict on neither engine where the one that writes over the tree had not written the node before that commit; RocksDB keeps the other's records under the prefix. GroveDB's callers run one write transaction at a time, and no interleaving of one writer's calls makes this. So it is where the group writes an empty indexed tree over a tree, no drop is stated under its key, by the look or by a batch of the group itself, and such a commit wrote a child into the old tree before the group was applied: nothing is dropped, and the Merks keep the roots that the commit gave them under an element that names none. Where a drop is stated, as the look states one of the subtree of a tree of flat records, the drop takes what the commit wrote there. `a_tree_that_a_commit_writes_into_after_the_look_keeps_its_merks_under_an_empty_indexed_tree` holds three such stores by what the checker reports of them: the value hash of the element's node (`Hash(Value)`) where a sum-indexed tree is written over an ordinary tree that nothing was written into, and over a sum-indexed tree that was emptied; and each root of the commit pointed at by no cell (`HostPointer`) where the look said that the node hosts nothing, a count-indexed tree over an emptied tree of three axes.

The write over the tree, every read of an element that was written since by its key, and every proof answer and cost the same on both engines: the root hash, the bytes of a proof of the tree and what a verifier is shown by it are equal. So does every write after it that does not first read the records under the prefix as they are (below). Once such a write is made on one engine and not on the other, the two hold different groves, and what is read of them afterwards differs with that.

**A known difference, to be closed by `GROVE-03-F1` (D-227).** A read that takes the records under a prefix as they are, and not from the root of the tree, answers differently: on RocksDB the records of the old tree are still there, and on LigninDB they went with the drop. RocksDB's answers are the required ones, and the difference is no property of the engine. Two of the reads below are writes that read first, and change the root hash on one engine only: a delete that RocksDB refuses and LigninDB makes, and an insert of what is not there, which finds the old record on RocksDB and none on LigninDB. `GROVE-03-F1` keeps the nodes of a tree that was written over as records that no tree links, as RocksDB leaves them (D-133, D-106), so that all of them answer as on RocksDB. The kinds below are those that were found: each asks the store for a key or a range under the prefix, and does not walk the tree to it. Until then:

| Read | RocksDB, which is required | LigninDB until `GROVE-03-F1` |
| --- | --- | --- |
| `is_empty_tree` of a tree that stands where one with elements was written over | not empty, whatever was written into it since; the read is charged the first record under the prefix | as empty as what was written into it since makes it |
| the delete of such a tree that nothing was written into | refused: the tree is not empty | made |
| a range of a query over such a tree | the elements of the old tree among those written since | the elements written since |
| `get` of a key that only the old tree had, in such a tree that has a node | the old element | no element |
| an insert of an item only where its key holds none (`insert_if_not_exists_op`), in a later batch, under a key that only the old tree had | the insert finds the old record, and the batch is refused | the insert finds no record, and is made |
| `get` by a path through an element that only the old tree had, or under an element that is no tree any more | the element of the old subtree | no such path |

What this does not do:

- It reads the element as the group states it, and not the element that was there. An element that is written again as a tree with a root key, or whose subtree the group writes on through the handle that fetched its root, keeps its subtree, whatever tree type the entry of the subtree names.
- A tree that keeps its data flat and is written over with a tree of its own type keeps its records. The element of such a tree changes with every write into it, and nothing tells a new one from it.
- **Another element written over an indexed tree** (`GROVE-04-F1`). The primary of the old tree is the subtree of the element's own path and is looked at as the subtree of any tree is: it is dropped, and entered again where the group writes into it, by the rules above, so that its entry names the tree type of the new element. The secondaries of the old tree hang under the same key, and no element but an indexed tree hosts them: each that is entered there is dropped with the group, where the primary is looked at by these rules and not kept by the first item here. So a tree that keeps flat records, a tree of one Merk or an item that is written over an indexed tree whose last child was deleted finds nothing of it in the directory, and the first write into the new tree enters its subtree with the new tree type (`an_element_written_over_an_emptied_indexed_tree_takes_its_merks_out_of_the_directory`).
- The Merks of an indexed tree stay entered where the tree is written again as an indexed tree that names a root. What a group that writes one of them by name does to the others is said in [An indexed tree hosts several Merks](#an-indexed-tree-hosts-several-merks), and what becomes of them under an empty indexed tree is said here ([An empty indexed tree written over a tree](#an-empty-indexed-tree-written-over-a-tree)). The subtree of an element that the group removes is dropped by another rule ([A subtree leaves with its element](#a-subtree-leaves-with-its-element)), and nothing is done here for a subtree that a batch of the group enters itself, moves, or moves another subtree to, or for a node of a subtree that no handle by path wrote into with the group.

#### An empty indexed tree written over a tree

`GROVE-04-F1`. An indexed tree is made empty: a batch that writes one over a tree states an element that names no root, of the primary or of a secondary. What is entered under the key then is the subtree of the element's own path, which was the primary of an indexed tree, the Merk of a tree of one Merk or the subtree of a tree of flat records, and the secondaries of an indexed tree that was there. GroveDB removes the records of an indexed tree that a batch writes over from grove version 4 on (`apply_batch.overwrite_indexed_cleanup_inspection`), and not those of a sum tree, on any grove version. The engine looks at each of those subtrees that hangs under the key (`over.rs`, `emptied_after`), and the first of these that is true of it decides:

- **A batch of the group drops or clears it itself, and neither that batch nor a later one writes a node of it**: it is left to that batch, and the look says nothing of it. A batch applies its drops and clears before its writes, so a node of the subtree that the dropping batch still holds is written after the drop.
- **A batch of the group writes nodes of it**, the batch that puts the element or a later one ([below](#an-empty-tree-written-before-the-merks-under-its-key-are-emptied)): the last batch that writes nodes of it has to state no root for it (`LigninSettled::empties`), or the group is refused with `Error::NotSupported` and nothing of it is applied, since the element names no root (`a_group_that_leaves_a_root_under_the_key_of_a_tree_it_writes_as_empty_is_refused`). This look says nothing else of it: whether it stays entered, with no node, or leaves as a secondary of an axis that the new element has not, is the rule of [An indexed tree hosts several Merks](#an-indexed-tree-hosts-several-merks).
- **It has no node, no batch of the group writes a node of it, and it is not the subtree of a tree of flat records**, which has its records whatever its entry says of a root: it stays entered as it is. The subtree of the element's own path is stated anew with the batch, as the primary of the new tree, where it is entered as a tree that is no indexed tree: what leaves with the element later is found by the tree type of that entry ([A subtree leaves with its element](#a-subtree-leaves-with-its-element); `an_empty_indexed_tree_over_an_emptied_tree_takes_its_subtree_as_its_primary`).
- **Open (D-292): a secondary that the new element hosts has a row, and the group writes no node of it.** That is an indexed tree written over a filled indexed tree with which it shares an axis, on the grove versions that do not remove the old records, 1 to 3. RocksDB takes the batch, and `verify_grovedb` fails on its grove once the new tree is written into. The new tree is not an empty one there: with the old tree's Merks dropped on LigninDB, the first write into it had another cost and another root hash on RocksDB (`artifacts/GROVE-04-F1-evidence/over-unswept/`), as of a secondary that still holds the rows of the old tree under an element that commits to none. LigninDB refuses the batch with `Error::NotSupported`, and nothing of it is applied.
- **It holds records that the group does not remove**: it has a node, or is the subtree of the element's own path and that of a tree of flat records, and no batch of the group writes a node of it. It is dropped with the group. That is the Merk of a filled tree of one Merk, the subtree of a tree of flat records, and each Merk of a filled indexed tree on the grove versions that do not remove its records, a secondary of an axis that the new element has not among them. RocksDB keeps the records under the prefixes, where no element leads to them. A read of GroveDB can find them there: the write of a child of the new tree under a key that the old tree had loads the old record, so that write is charged more loaded bytes on RocksDB than on LigninDB, and is the same in everything else. That is the difference of a tree that is dropped (D-227, open; the table above). A group that drops such a subtree and holds a write under the key beside it, of a node or of a record in any column, is refused with `Error::NotSupported`, and nothing of it is applied (`an_empty_indexed_tree_over_a_filled_tree_is_refused_beside_a_write_under_its_key`): what it writes would go into a subtree that leaves, or beside one. GroveDB makes no such batch: it refuses a batch that writes an indexed tree over an element and a child of that tree.

Where a subtree under the key is dropped, by the look or by a batch of the group itself, the node of the element is written as one that hosts nothing (`LigninSettled::host`, with no Merk): it points at none of the subtrees that leave, and no subtree that stays under the key has a node. So it is where more subtrees are entered under the key than the new element has Merks, as where an emptied indexed tree of three axes is written over with one of one axis, and no handle of the group names the element for a subtree under its key: its cell kept the places of the element that was there. Otherwise this look says nothing of the node. The subtrees that stayed are judged where a later group writes into the new tree ([An indexed tree hosts several Merks](#an-indexed-tree-hosts-several-merks)).

`an_element_is_written_over_a_tree_of_every_kind_on_every_grove_version` holds all of it beside RocksDB, with the store closed and checked right after the batch and again after the writes that follow it.

#### An empty tree written before the Merks under its key are emptied

`GROVE-04-F1`. On the grove versions that remove them, a batch that writes an element over a filled indexed tree writes the element and then removes the records of the old tree, by the walk of each of its subtrees (`clear_subtree_storage_recursively`). Applied whole, it is one batch of the engine: the node of the element and the removals are one write, and the cell of the element comes to name no root. Applied in parts (`apply_partial_batch`), it is one batch or two of a group, by where the batch pauses. Where the element is put before the pause, it is a group of two: the element in the first batch, the removals in the second. The node of an element names the root of each Merk it hosts where it is put, and the second batch removes the root node of each Merk without putting the element's node. Where the put of the element is still to be made when the batch pauses, or comes from its callback, the element and the removals are both in the second batch, after a batch that wrote elsewhere, and are one write as in a batch applied whole. There a secondary of an axis that the old tree had not, which no batch holds a write or a statement for, is entered with the batch that puts the element's node, after what that batch drops and states anew ([node-store.md](node-store.md#the-batch-of-an-operation)): the place it takes is free by then, where a secondary which the new tree has not held it and leaves, and where one that the new element names at a later place held it and is stated anew there (`the_callback_of_a_partial_batch_writes_an_indexed_tree_over_a_filled_one`).

A cell that named those roots would point at nodes that the second batch removes. So the engine has the node of the element written as one that hosts nothing (`LigninSettled::host`, with no Merk), in the batch that puts it. It does so for a tree of one Merk where the last batch that writes nodes of the Merk leaves it with none (`LigninSettled::empties`), and for an indexed tree where the element names no root, a batch after the last one that puts the element's node writes nodes of a Merk the element hosts, and every Merk the element hosts is without a node once the group is applied: the last batch that writes nodes of it leaves it with none, or no batch writes a node of it and the directory has no root for it. The second batch takes the root out of the entry of each Merk that it empties and that stays. A Merk that the new element hosts, and every Merk under a tree of one Merk, stays entered under the element, with its tree type and with no node; a secondary of an axis that a new indexed tree has not leaves with the batch that puts the element, and what the second batch removes from it is not handed over. The trees below it leave by the nodes that the batch removes ([A subtree leaves with its element](#a-subtree-leaves-with-its-element)). The removals are charged as on RocksDB, and the directory that is left is the one that the batch leaves where it is applied whole. For a tree of one Merk the group is the one that [the rule of a Merk written after its element](#subtrees-are-entered-by-the-first-batch-that-writes-into-them) would refuse, and takes because the element names no root and nothing under its key is left with a node; a group whose second batch leaves the Merk a root, or whose first batch writes a node of the Merk too, is refused (`a_group_that_empties_a_tree_after_the_batch_that_writes_its_empty_element_is_taken`), and so is one that leaves a row in a secondary of the old tree (`a_group_that_leaves_a_root_under_the_key_of_a_tree_it_writes_as_empty_is_refused`). `an_empty_indexed_tree_is_written_over_a_filled_one_in_one_batch_and_in_parts` holds both ways beside RocksDB for an indexed tree, with the cost of the next write into the tree, and `an_element_is_written_over_a_tree_of_every_kind_on_every_grove_version` for a tree of one Merk.

### Moving a subtree on LigninDB

GROVE-03. A batch `Move` renames a key ([Moving a subtree](#moving-a-subtree)). An element that hosts no subtree is moved by a put and a delete in its Merk. For a tree GroveDB also asks the engine to move the subtree of its path, and each tree in it, to the prefix of the new path, and what that is charged on existing GroveVersions is what RocksDB's copy is charged, record by record ([cost-model.md](cost-model.md), section 15).

`LigninEngine::move_subtree(from, to, batch, &tx)` reads the entry of `from` as the transaction has it and returns a `LigninSubtreeMove`: a cursor over the nodes of the subtree's Merk, or over its flat records where the subtree is entered with no root, which a tree that keeps its data flat is. A Merk that is entered with no node has no root either, and no record but those that no node links ([node-store.md](node-store.md#unlinked-records)), which the cursor over flat records shows as the store keeps them, not as Merk's records of nodes. The call is charged the cursor's `seek_to_first`. Each `move_next` reads the record the cursor stands on, at a cursor's cost, a node as the bytes of Merk's record of it and a flat record as its bytes, shows it to `inspect`, and stages two charges in the batch and no write:

- the put of the record under `to`, with the cost `bill` gives (`LigninBatch::charge_landed`), and
- its delete under `from`, which frees nothing (`LigninBatch::charge_cleared`).

When the batch is settled the charges take their place among its own outcomes in the data keyspace, by stored key, as the puts and deletes of the copy have it in a storage batch (`cost-model.md` B1). Of a put and a delete that one operation of the batch stages for one key the put stands, and a later operation stands against an earlier one, so two trees that change places, and a tree that moves to the key another tree leaves, are charged what their copies are (`batch::move_element::walked_on_both_engines`). A batch that holds a write of its own under the stored key which a moved record is charged at is refused where it is settled: a storage batch keeps one of the two, and nothing in the batch says which. GroveDB refuses a batch that moves an element and changes anything under its key or its target before anything is staged.

A subtree that is not entered, a tree nothing was written into, has no record: its walk ends at once, as RocksDB's does, the batch is told of no move, and the move is the put and the delete of the element. Such moves, and those of elements that host no subtree, are applied, but for the one that the next paragraph refuses.

GroveDB reads the element of the tree before it asks for the walk, and a walk that ends on a subtree with no entry tells the batch that it found none (`LigninBatch::move_of_none`). Where the element that the batch puts under the new key says that its tree holds data, which is a root for a tree whose data is a Merk and a count of at least one entry for a tree that keeps its data flat, the directory does not hold what that element says: the engine refuses the batch as a conflict (`CommitError::Conflict`), with nothing of it applied (`grovedb/src/engine/lignin/moved.rs`). A commit beside the transaction that writes an item over the tree, between the mover's read of the element and the walk, makes this, and so does one writer that inserts an element which counts entries that its tree does not hold, and moves it.

The move of an entered subtree is said to the batch (`LigninBatch::move_subtree`), where the engine is asked to walk it: the subtree goes to its new prefix with every node where it is ([D5 of the tree layout](tree-layout.md)). The engine reads the entry and makes the cursor after it, and the cursor reads the committed state as it was when it was made, so a commit beside the transaction can enter the subtree after the read of the entry, before the cursor is made or during the walk. A walk that began on a subtree with no entry reads the entry again where it ends, and tells the batch of the move if the subtree is entered by then, whatever the walk showed of it. Such a walk has a cursor over the nodes of a Merk. Where it comes to a flat record, the cursor reads it by the tree type that its own version has the subtree entered with ([node-store.md](node-store.md#the-cursor)): under a tree that keeps its data flat it shows the record's bytes, as RocksDB's cursor does (`tests/over.rs`, a tree that is entered before the cursor is made). Grove versions 1 to 3 refuse every move on both engines.

Where the batch is applied, the engine states each move to the transaction (`lignindb::txn::SubtreeWrite::Move`, [section 7.5 of the transaction rules](transactions.md)), from what the subtree directory holds of the subtree then (`grovedb/src/engine/lignin/moved.rs`):

- A pair whose host is in a subtree that the batch moves too is below that move, and is named in it. Every other pair is a move of its own, under the element that the batch puts in the Merk its host is in: the node whose stated element has, at the position the directory has the subtree at, the prefix the subtree goes to. The prefix of an element's own path is worked out from the path of that Merk, which the engine told the handle that wrote it.
- The node of that element names the Merks it hosts (`LigninSettled::host`): the moved subtree among them where the directory has it as a tree whose data is a Merk, and none where it has it as a tree that keeps its data flat, whose host points at no Merk before the move and after it (MV3 of the transaction rules). A node that hosted a moved subtree and that the batch puts again, with an element that no moved subtree goes to, hosts nothing: in a swap of a tree with an item, the item.
- A move that leaves no element under the old key removes the node there, and what is entered under a removed node leaves with it ([A subtree leaves with its element](#a-subtree-leaves-with-its-element)). That look passes over a subtree that the batch was told to move, which goes to its new prefix; what else is entered under the node is dropped with the batch, as under any removed node.
- A subtree that makes room where a moved subtree goes, and that the batch does not move away, is dropped with the move. A subtree makes room where it is entered at the first position of its host, and is the Merk with no node of a tree whose data is one Merk, or the subtree of a tree that keeps its data flat with no record in its data keyspace, or the primary with no node of an indexed tree whose secondaries have none either. The secondaries that are entered under the element of such a primary are dropped with it. Such is the Merk of a tree that was written into and emptied, which GroveDB asks no walk for when a swap moves that tree away. A drop takes the records of a subtree in every keyspace, so the records that no node links ([node-store.md](node-store.md#unlinked-records)) go with it where such a Merk holds any. RocksDB's move neither reads nor deletes them: it leaves each under the prefix, unless the copy of the moved tree, which lands there, writes a record under its key. A read of GroveDB under the key of one that is left can answer with it, since Merk asks the store for a key where a link leads on from the nodes it has loaded: the difference D12 of [section 14.5 of the transaction rules](transactions.md), here under a path that an element leads to.
- The look states that drop, and the drop takes what is entered under the prefix when the batch is applied. The transaction is asked for no date of it. So where the look stated the drop of an emptied tree's Merk and a commit beside the transaction wrote a tree of leaves over that tree afterwards, and appended to it, the batch can be applied with that tree and its leaves gone. It is applied so where that commit wrote no node that hosts a moved subtree. Where it did, as it does where the node of the moved tree is above the node of the emptied one in their Merk, the date of the move refuses the batch as a conflict, and the leaves stay.
- Whatever else the look finds entered where a moved subtree goes, and that the batch does not move away, is left as it is: the engine states no drop of it, and the transaction refuses a batch that brings a subtree to a prefix where one is entered. A tree of leaves with a leaf, which a commit beside the transaction entered there before the look for the moves, is one: the transaction refuses that batch as a conflict, since a commit wrote under the prefix after the mover's read, and the leaves are where they were.
- GroveDB asks no walk for a Merk whose element names no root. Where such a Merk is entered below a moved one, with no node, the transaction takes it out of the directory with the move (MV2 of the transaction rules), and under the new path its tree is one that nothing was written into. The records that no node links leave with it, where it holds any: nothing of them is read under the new path on either engine. RocksDB's move, whose copy walks no such tree, neither reads nor deletes them: it leaves each under the old prefix, unless the copy of a moved tree lands under that prefix and writes a record under its key (D12). A Merk with a node below a moved one that no pair names refuses the batch there.

A tree that keeps its data flat is walked whatever its element says, and is a move of its batch where its subtree is entered. Its records go to the new prefix with the entry (MV1 of the transaction rules), and the node at its new key points at no Merk, as the node at its old key did.

No node is copied, and the statement of a move is charged nothing: the batch is charged for its writes and for what the walk staged. The root-key record of a moved subtree is kept outside it and stays under the old prefix, where RocksDB's move leaves it ([The root-key record of a subtree](#the-root-key-record-of-a-subtree)). The transaction reads under the new prefix what it read under the old one, and a rollback, or a rollback to a savepoint before the move, takes the move back.

The move is dated at the read of the node that hosted the subtree, as the handle of that Merk first read it (`LigninSettled::move_as`). Where the engine states the move, the transaction refuses the batch as a conflict (`CommitError::Conflict`) if a commit beside it wrote that node since, which every write into the tree does on existing GroveVersions: nothing of the batch is applied, and the transaction stays open. RocksDB takes such a batch: the difference D8 of [section 14.5 of the transaction rules](transactions.md). After the move, a commit beside the transaction that writes into the tree under its old path, or puts an element under its new key, makes the mover's commit a conflict, and the mover's commit makes the commit of a transaction that had written into the tree one, on both engines. A batch that was worked out before a commit beside it moved a tree above what it writes, so that nothing is entered under the prefix it writes, is refused as a conflict, which is the difference D9 of the same section.

A transaction that a commit beside it met serves its records by key, and while it holds a move the transaction layer refuses it every drop and every clear of a subtree (MV7 of the transaction rules). A batch of such a mover that writes an element over a tree whose subtree is dropped with it ([An element written over a tree](#an-element-written-over-a-tree)) is refused as a conflict where RocksDB takes it, and so is its delete of a tree with elements, whose subtree leaves with the element. Its clear of a tree that the move does not name and that holds no tree is taken on both engines: `Merk::clear` removes the nodes by their keys, and the engine states no clear to the transaction ([A subtree leaves with its element](#a-subtree-leaves-with-its-element)). The commit of such a mover fails as a conflict on both engines.

A batch that moves a tree can delete another tree with what it holds, where GroveDB lets it: it refuses a delete at the key a move goes to, a delete under the key a move leaves, and a delete of the tree a move is made in or of one above it. The subtree of the deleted tree is dropped and the subtree of the moved one is moved with the same batch, and the transaction makes the drops of a batch before its moves. After a batch deleted a tree in a tree, nothing of it is entered when the tree above is moved.

No operation of GroveDB states a subtree anew in the group that moves it. A conversion is stated in the storage batch of `convert_to_big_sum_tree` ([A converted tree is stated anew](#a-converted-tree-is-stated-anew)), which is told no move, and the storage batch of a batch of operations, which is told its moves, states no tree type. A batch that is made at the seam with both is refused by the transaction (`BatchError::ConvertMoved`): the engine states the move as for any other batch, and nothing of the batch's group is applied.

The look for the moves can be stale as the other looks can. A pair is said by the walk of a subtree that is entered: where that subtree has no entry when the batch is applied, the engine refuses the batch as a conflict with nothing of it applied. Between the walk and the application of one batch of GroveDB, only a commit beside the transaction takes it. A subtree that is entered then is stated as the directory has it then: under its host, at its position, as the kind of tree it is entered as. So a tree that a commit beside the transaction wrote a tree of leaves over, and appended to, after the walk is stated as a tree of leaves, and the transaction's date of the move refuses the batch as a conflict.

The engine cannot state the move of a subtree that hangs under no element, of one under an element whose Merk the batch wrote through a handle that was not opened by a path, or of one whose new prefix no element that the batch puts in that Merk has at the position the directory has the subtree at. Such a batch is refused with `Error::NotSupported`, also where a commit beside the transaction left the subtree so. GroveDB makes neither of the first two. The third is an indexed tree whose subtrees are entered at other positions than its element has them ("An indexed tree does not take over subtrees that are entered elsewhere under its key", under [Subtrees](#subtrees-are-entered-by-the-first-batch-that-writes-into-them)).

GroveDB does not ask the engine to walk a tree whose element has no root key and whose data is a Merk. Such a tree that was written into and emptied is entered all the same. Its move is the put and the delete of its element, which is applied, and no move is stated for its subtree. Where the batch leaves no element under the key the tree had, its entry is dropped with the node that the batch removes ([A subtree leaves with its element](#a-subtree-leaves-with-its-element)), and the moved tree is one that nothing was written into. Where the batch puts an element under that key, the entry is that of a tree which an element is written over, and is dropped or kept by the rules of that look ([An element written over a tree](#an-element-written-over-a-tree)): it is kept where the element that is put is a tree of the entry's own type that names no root, as where two such trees change places. Or the entry is one that is entered where a moved subtree goes, above. The records that no node links, where its Merk holds any, are dropped where the entry is dropped and stay under the prefix where it is kept. RocksDB's move neither reads nor deletes them: it leaves each under the prefix the tree had, unless the copy of a moved tree lands under that prefix and writes a record under its key (D12).

### Root-hash propagation

GROVE-02. An insert or a delete that has written its Merk carries that Merk's root hash up the grove before its batch is applied: GroveDB writes the element of the Merk's tree again in the Merk above, with the root hash, the root key and the aggregate the Merk has by then, and so on up to the root Merk. It makes these steps whether or not the write changed the root hash, inside the batch of the operation, one Merk at a time, with code that names no engine: `propagate_changes_inner` (`grovedb/src/lib.rs`) for an operation that wrote one Merk, such as an insert or a delete, `propagate_changes_with_batch_transaction` beside it for the delete of a tree that holds elements on grove versions 1 to 3, and `MerkCache::propagate_subtrees` (`grovedb/src/merk_cache.rs`) for an operation that maintains backward references. For a tree whose element hosts one Merk, each step takes the root hash, the root key and the aggregate of the Merk below (`Merk::root_hash_key_and_aggregate_data`), takes the Merk above, which it opens by its path or which the Merk cache holds, and writes the tree's element there again (`update_tree_item_preserve_flag`).

On existing GroveVersions Merk hashes every node before it hands it to the store, so each hash on the way up is the one Merk stated, and each charge is what Merk and the cost rules give for the write ([cost-model.md](cost-model.md), section 15). What the LigninDB engine does with such a step:

- **The handle of each Merk on the way, but the root Merk, names the element that hosts it.** A Merk is opened by its path, so its host is the key of the path's last segment in the subtree of the segments before (`LigninSubtree::host`). The root Merk has the empty path and no host. The batch of the operation holds the nodes of the Merk and, from the step above, the node of that element. Where the batch is applied, the element's cell is made to point at the root cell of the Merk it hosts, and at none for a Merk that has no node ([node-store.md](node-store.md#the-batch-of-an-operation), `tree-layout.md` C3).
- **The value hash that a step states for the element is the one the engine's rules make from that pointer.** For a tree whose data is one Merk a step states `combine_hash(value_hash(value), root)`, where `root` is the root hash of the Merk below, and `NULL_HASH` for a Merk with no node. The engine's rules make the same from the element's cell: `root` is the node hash of the root cell it points at, and `NULL_HASH` where it points at none ([node-store.md](node-store.md#hashes)). Given Merk's rules, the physical checker makes the hash again for the cell of every tree that has a root and compares it with the stored one. The hash that the insert of a tree states, before any step, is the insert's own: the same section has the three kinds of tree whose insert states the plain value hash on grove versions 1 and 2. On existing GroveVersions no hash is left to the engine: the commit runs with `NoStaleHashes`.
- **The engine adds no charge.** A handle by path is charged the prefix of its path, as on RocksDB. The prefix of the host's subtree and the enter of a subtree are charged nothing ([Each operation](#each-operation)).

#### The Merk cache

`MerkCache` keeps the Merks of one operation open, by path, with one batch for all of them. It is used where a write has to maintain backward references: the insert of grove version 4 and later for an element that takes them or replaces one (`insert_on_transaction` v1), the delete of such an element, or of a tree that holds one, where the delete checks for backward references, which is the default (`delete_internal_on_transaction` v2), and the code that follows a reference through the cache (`reference_path.rs`, `bidirectional_references`).

- **The cache holds one Merk for a path.** A Merk it was seeded with (`with_prepared_merk`) is the one its caller opened, and any other is opened by the first `get_merk` of its path that returns a handle. While the cache holds a Merk, a `get_merk` of its path that returns a handle returns one of that Merk. The cache lets go of a Merk when its path is marked as deleted, when a closure that may write it returns an error (the next point), and when the cache ends. A path that was marked as deleted is opened again only when a tree's element is there again in the Merk above, which the cache has to hold.
- **A closure that may write gets the Merk through `MerkHandle::for_merk`, and an error of it drops the Merk.** A Merk whose write failed may not hold the tree that its store and the batch hold: `Merk::apply` takes the tree for its walk and sets one back only when the walk succeeded, so a write that failed in its walk leaves a Merk that reads as empty, and one that failed in its commit leaves a tree that was not written. The cache marks the path as failed and lets go of the Merk. From then on a closure of a handle of that path, `get_merk` of the path and the open of a Merk through it are refused with `Error::CorruptedCodeExecution`, marking the path as deleted leaves it failed, and an end of the cache (`finish_prepared`) that is begun then fails before it opens or writes a Merk. So an operation that went on after such an error carries no root hash up, from that Merk or from another Merk of the cache. The end of the cache writes the elements on the way up through the same closures. A write that fails there ends it with that write's error, and the steps made before it are in the batch of the operation, which `insert` and `delete` do not apply after an error.
- **A closure that only reads gets the Merk through `MerkHandle::read_merk`**, as a shared borrow, and an error of it leaves the Merk in the cache. Following a reference and planning the maintenance of backward references read elements that may not be there, and go on with the same cache.

Both borrows are exclusive and mark an operation boundary in the batch (`EngineBatch::next_operation`), as `for_merk` did before the two were told apart. On RocksDB an operation that returned no error from a `for_merk` closure stages what it staged before.

A subtree of the cache is on the heap for as long as the cache lives, and from the moment it is put there the cache and every handle reach it through one pointer and through shared references made from it. The flag that says whether a closure has the subtree is beside it. A unique reference to the subtree, or a write of it, is made by a closure that holds the flag; by the cache after it has checked that the flag is not held, in a borrow that ends before anything else reaches the entry; and by the end of the cache, which has the cache to itself. So a second handle of a subtree, which a delete that maintains backward references can take while it holds the first, is made with no unique reference to the entry that the first handle points into.

**The cache knows the Merks it holds and no others.** A Merk that something else opens for one of its subtrees in the same transaction is a second Merk of that subtree. GroveDB opens one itself, to read: an insert through the cache that writes a plain reference follows the reference through Merks of its own (`follow_reference_as_stored_for_write`), which read what the transaction holds and not what the batch has staged. A caller can open one that writes: the removal callback of `delete_with_sectional_storage_function` is the caller's code and is called before the node is removed, and nothing refuses a write it makes through the same transaction into the subtree of the delete.

What this leaves to later tasks:

- **Batches** propagate through the cache of the batch, which is not `MerkCache`. The histories of `tests/batches.rs` compare the root hash after every batch with RocksDB's (GROVE-03); none of them is five levels deep.
- **Append-only trees** (GROVE-04). No chain of `tests/nested.rs` holds one. An append is carried up from a tree of each kind in the fifth and in the third of five trees by the histories `the_root_hash_follows_an_append_to_.._five_trees_deep` of `tests/append_only.rs`.
- **Indexed trees** (GROVE-04). No chain of `tests/nested.rs` holds an indexed tree. The steps of `propagate_changes_inner` for an indexed primary and its secondaries are compared with RocksDB by the histories of `tests/indexed.rs`, which are not five levels deep ([An indexed tree hosts several Merks](#an-indexed-tree-hosts-several-merks)).
- **The delete of a tree that holds elements** propagates as any delete does, and is compared with RocksDB by the histories of `tests/deletes.rs` ([A subtree leaves with its element](#a-subtree-leaves-with-its-element)).

### An indexed tree hosts several Merks

An indexed tree keeps its children in a primary Merk, at the prefix of its path, and a ranking of them for each of its axes in a secondary Merk, at `Blake3(primary prefix ‖ storage tag)`. The storage tag of an axis is its tag, but for the big sum axis, whose secondary is stored under the tag of the sum axis (`axis_storage_tag`). The value hash of the element is made of the roots of these Merks in the element's order: the primary first, then the secondaries in the order of the axes ([node-store.md](node-store.md#hashes), D-133). On LigninDB that order is the position of each Merk under the element.

GroveDB opens the primary by its path and a secondary by its prefix, and a handle by prefix cannot say whose subtree it is before the subtree is entered. So `open_indexed_secondary_at_path`, where it is given a batch, opens a secondary through a handle that names its element, and the engine works out the rest where a group of batches is applied. A handle is taken at its word: those that `Engine` opens name the element of their path, the element under which their subtree is entered as its first, or none, and a handle that a caller makes with a description of its own (`LigninNodeStore::deferred`) is the caller's statement, of which the contradictions named below are refused, and the engine looks for no other. What it works out is for a **named write**: a write that the group holds for a subtree through a handle that names an element, where no batch of the group enters that subtree itself (`LigninBatch::enter`). GroveDB's operations enter no subtree themselves through this engine. For a subtree that a batch enters itself the engine works out nothing: its host, position and tree type are what that batch resolves them to, and the element is not read for it.

- **`open_indexed_secondary_at_path` opens a secondary beside its primary** (`grovedb/src/operations/indexed_tree.rs`): `Engine::subtree_beside(path, prefix, batch, &tx)`, where `path` is the path of the element and `prefix` the secondary's. It is the one caller. The trait provides the method as `subtree_by_prefix(prefix, batch, &tx)`, so an engine for which a subtree is its prefix overrides nothing and makes the calls it made: that is RocksDB, and the engines of the tests that wrap it. LigninDB overrides it, because it is the one engine that keeps the subtrees of an element together. Opened with a batch and a path that has a last segment, its handle names the element under that segment as its host. It is charged what `subtree_by_prefix` is, nothing.
- **What the element hosts is read where a group is applied** (`grovedb/src/engine/lignin/enter.rs`), for each named write: from the last batch of the group that states a value for the element's node or removes it, which gives the element or none, and from the transaction where no batch does either. The axes are those of the element (`indexed_element_axes`), each with the prefix its secondary is stored under (`axis_storage_tag`) and the tree type its secondary keeps (`axis_secondary_tree_type`).
- **The Merks of an indexed tree are entered under its element, each at its place**, by a group that holds a named write for one of them: the primary at position 0 as a tree of the element's type, the secondaries after it. Each that is not entered is entered, if it is absent, where the group is applied. One of them that the same group also writes through a handle that names no element is entered once, as the element names it. Those of them that no batch of the group enters itself are entered with the batch of the group that enters the subtree the element is in, and with the first batch of the group where that subtree is entered already, whichever batch holds the write. One of them is entered otherwise: a Merk that no batch holds a write for is entered with the first batch that puts the element's node, after what that batch drops and states anew ([An empty tree written before the Merks under its key are emptied](#an-empty-tree-written-before-the-merks-under-its-key-are-emptied)), where that batch holds no statement of it and no batch before that one needs it entered; with the first batch of the group otherwise, and where none puts that node. A batch holds a statement of a subtree where something staged into it says that the subtree is entered, dropped, cleared, stated anew or moved away, or that another subtree is moved to its prefix. Of those, the transaction refuses an enter of a prefix in the batch that moves a subtree away from it or to it. A batch needs a subtree entered where it says that the subtree is entered, dropped, cleared, stated anew or moved away, enters a subtree under an element of it, or holds a write for, or needs entered, a subtree that is entered with the group under an element of it. A move of another subtree to its prefix is no need of it: the move brings the entry, which the enter of a later batch finds.
- **A Merk that is entered under the element at another place, or as a tree of another type, than the element names is stated anew** (`SubtreeWrite::Convert`, `LigninSettled::state_anew`; `GROVE-04-F1`), with the first batch of the group that puts the node of the element: it keeps its nodes and its records, and the cell of the element names the Merks by their places from that batch on. The conversion of an indexed tree to its 128-bit counterpart makes such a group where the element names its axes in another order afterwards: a count-and-sum indexed tree with a count, a sum and an average axis becomes one whose average axis comes before its big sum axis, whose secondary is the one of the sum axis. So does the first write into an indexed tree whose last child was deleted before its conversion: that conversion writes the element alone, and the write after it states the primary as the wide tree and the secondaries at their places. A Merk that a batch of the group states anew itself, as Merk does for the primary it converts ([A converted tree is stated anew](#a-converted-tree-is-stated-anew)), is as that batch states it. Where no batch of the group puts the node of the element, a Merk that hangs at its place keeps the tree type of its entry.
- **A secondary that hangs under the element, of an axis the element has no more, leaves with the group** (`GROVE-04-F1`): it is dropped with the first batch that puts the node of the element, and what the group removes from it is not handed over. An empty indexed tree of other axes that a batch writes over a filled one leaves such a secondary. It holds a place that a Merk of the element can take, and the cell of the element names it no more. A group that puts a node or a record into it is refused with `Error::NotSupported`. RocksDB keeps the records under its prefix; GroveDB removes them with the batch that writes the new element.
- **An axis that an element names twice has one secondary, hosted once**, at the place of its first naming (`GROVE-04-F1`). A batch on `GROVE_V4` that makes an indexed tree and fills it does not check its axes, and can write such an element. A node has one parent, so the cell of the element points at the root of that secondary once, and the value hash of the element takes its root for each naming ([node-store.md](node-store.md#hashes)).
- **Every batch of a group that holds a named write for one of the element's Merks is told what the element hosts** (`LigninSettled::host`, [node-store.md](node-store.md#the-batch-of-an-operation)). A batch of it that puts the element's node names all of the element's Merks there, whichever of them it writes and in whatever order its handles staged. A batch of it that writes a node of one of them and does not put the element's node writes that Merk anchored (`lignindb::batch`, "Hosts, and what is anchored").
- **A named write is refused** with `Error::NotSupported`, and nothing of its group is applied, into a subtree other than the one of the element's own path where the element hosts no subtree with that prefix once the group is applied; into a Merk of an indexed tree where a subtree the element hosts, and that no batch of the group enters itself, is entered under another element, or under none (the first point of "What this leaves to later tasks" in [Subtrees are entered by the first batch that writes into them](#subtrees-are-entered-by-the-first-batch-that-writes-into-them)); and into the subtree of a tree of one Merk that is entered under no element. A Merk of an indexed tree that is entered at another place under its element while no batch of the group puts the node of the element is refused the same way: nothing would name it at its place. A group is refused the same way where its handles name two elements for one subtree, or name one element with two subtrees of its own path, in the handles of one subtree or of two. A named write into the subtree of the path whose key holds no element once the group is applied follows the rule of every subtree: refused where the subtree is not entered and its writes are not left out by that rule.
- **A group that writes a Merk of the tree after the batch that writes its empty element** (`GROVE-04-F1`). Where the element as the group leaves it names no root, of its primary or of an axis, and a batch after the last one that puts the element's node writes nodes of a Merk the element hosts, the node of the element is written as one that hosts nothing ([An empty tree written before the Merks under its key are emptied](#an-empty-tree-written-before-the-merks-under-its-key-are-emptied)). Every Merk the element hosts is without a node then, once the group is applied, or the group is refused with `Error::NotSupported` and nothing of it is applied: no node would name the root that is left (`a_group_that_writes_a_secondary_after_the_batch_that_writes_its_empty_element_is_refused`).

The engine holds a write to no element where the handle names none: a handle by prefix of a subtree that is not entered or is not the first of its element, which is how the sweeps of a delete open a secondary and how state sync restores one through an immediate handle (GROVE-07), and a handle beside the path of the root.

### A converted tree is stated anew

MERK-08. The conversion of a tree to its counterpart with a 128-bit sum (`GroveDb::convert_to_big_sum_tree`, GroveDB #1063) has Merk write every node of the tree again as a node of the wide tree. Where the Merk has a node, `Merk::convert_to_big_sum_tree` then states the tree type it leaves through the handle it writes with (`NodeStore::state_tree_type`, [node-store.md](node-store.md#the-tree-type)), and the handle of this engine stages that statement in the batch of the operation (`LigninBatch::convert`): the subtree is stated anew in the subtree directory as a tree of the wide type, at the first place among the subtrees of its element. The statement is applied with the batch that writes the nodes and the element, or not at all. It is no write of a record and is charged nothing.

- **A tree of one Merk that has a node.** After the conversion the entry of the tree's subtree names the wide tree type, under the same element, at position 0, with the root key the element names.
- **A tree with no node states nothing**, and the group of its conversion is as it was before the statement existed. A tree that nothing was written into has no entry ([Subtrees are entered by the first batch that writes into them](#subtrees-are-entered-by-the-first-batch-that-writes-into-them)), and has none afterwards. A tree of one Merk that was written into and emptied has an entry with no root, which leaves with the write of its element as a tree of another type ([An element written over a tree](#an-element-written-over-a-tree)). The first write into either enters it with the tree type its element names, which is the wide one.
- **An indexed tree.** The Merk that the conversion writes again is the primary, and Merk's statement is of the primary alone: after the conversion of a sum-indexed tree that has children, the entry of its primary names the wide indexed tree type, and the entry of its secondary keeps its tree type and its host. Where the conversion names the axes of the element in another order, the engine states the secondaries that change places anew in the same batch ([An indexed tree hosts several Merks](#an-indexed-tree-hosts-several-merks); `the_merks_of_a_converted_indexed_tree_are_stated_anew_where_its_axes_change_places`). The Merks of an indexed tree whose last child was deleted have no node: the conversion writes the element alone, Merk states nothing, the engine has no named write to work anything out for, and every entry is after the conversion what it was before. The first write into the tree afterwards states the primary as the wide tree, and the secondaries at the places the element names them at (`a_tree_that_was_emptied_states_nothing_with_its_conversion`, `an_emptied_indexed_tree_whose_axes_change_places_is_stated_anew_by_its_next_write`). Until then `Merk::open_from_directory` would open the primary, which has no node, with the narrow tree type its entry names; GroveDB's own opens take the tree type from the element.
- **The group of such a conversion is one in which a batch states a subtree anew.** What that means for the look is said where the look is ([Subtrees are entered by the first batch that writes into them](#subtrees-are-entered-by-the-first-batch-that-writes-into-them), [A subtree leaves with its element](#a-subtree-leaves-with-its-element)). One test holds a conversion beside a commit that deletes its tree between the look of the group and its application: the transaction refuses the group as a conflict (`CommitError::Conflict`; `transactions.md`, CF10), the engine does not look again, and the conversion fails with that conflict.

`engine::lignin::tests::indexed::the_directory_names_the_wide_tree_type_of_a_converted_tree_of_one_merk` holds the first two: of each of the five kinds of tree that keep a 64-bit sum in one Merk, a tree with children, a tree that nothing was written into and a tree whose one child was deleted are converted on LigninDB and on RocksDB, at the same costs and to the same root hash. The entry of the first then names the wide tree type, the element, the position and the root key of the element. The other two have no entry, and after a write into each its entry names the wide tree type and a root. `a_tree_that_was_emptied_states_nothing_with_its_conversion` reads the entries of a sum tree and of the primary and the secondary of a sum-indexed tree, each with its one child deleted, before the conversion, after it and after the next write, beside RocksDB. `the_primary_of_a_converted_indexed_tree_is_stated_anew_and_its_secondary_is_not` holds the third for a sum-indexed tree with children, beside RocksDB, and the two tests named there for a count-and-sum indexed tree of three axes, with children and with its one child deleted, each with the cost and the root hash of the write after the conversion. `a_conversion_through_a_handle_that_passes_the_seam_on_is_stated` converts the trees through the handles of an engine that wraps this one, and `a_conversion_beside_a_commit_that_takes_its_tree_is_refused_after_one_look` holds the refusal beside a delete of the tree, in a transaction of the caller's, which holds no write of the group afterwards.

### A subtree leaves with its element

GROVE-05. On RocksDB the delete of a tree removes one record of the Merk above, and GroveDB removes the records under the tree's prefix itself where it means them to go: the delete of a tree that holds elements walks the tree for the trees in it (`find_subtrees`) and clears the data keyspace of each (`FlatStore::clear`), key by key, with the secondaries of an indexed tree (`clear_subtree_storage_recursively`), and from grove version 4 on a delete that keeps backward references up removes every node through the node store (`DeletionVisitor`). A flat drop removes the element alone and leaves the records to its drain. On LigninDB a subtree is in the subtree directory under the element that hosts it, and the cell of that element points at its root. So the engine drops the subtree where a group of batches is applied that removes the element (`grovedb/src/engine/lignin/gone.rs`):

- **The group removes a node** where the last of its batches that holds an outcome for the node removes it (`LigninSettled::removed_nodes`).
- **What is entered under a removed node is dropped.** The engine derives the prefix of the subtree under the node's key from the path of the subtree that the node is in, which a handle by path tells its batch (`LigninSettled::path`). It asks the directory for that prefix, and for the three prefixes beside it where it is entered as the primary of an indexed tree; the lookups are charged nothing. Each of them that is entered under the removed node is dropped, unless a batch of the group was told to move it (`LigninSettled::moves`): a move that leaves no element under the old key removes the node there, and its subtree goes to another prefix ([Moving a subtree on LigninDB](#moving-a-subtree-on-lignindb)). A drop is `SubtreeWrite::Drop` with the batch that removes the node (`LigninSettled::drop_subtree`), one page of the host and at most four directory records (`tree-layout.md` D1). The element need not be a tree: a record that is written through the path of an item enters a subtree under the item, and that subtree leaves with the item. How the node was removed does not matter: by a delete, by the removals of `Merk::clear`, or by a walk of the keyspace.
- **A drop takes every subtree below it**, by the hosts that the directory names, and names none of them. The nodes that the group removes in a subtree that is below a drop, or that is not entered, are not looked at.
- **A drop takes the records of the subtree in every keyspace** (`transactions.md` CV9): its nodes, and its aux, roots and meta records. The root-key record of the subtree is not among them: the engine keeps it outside the subtree, where it stays as it does on RocksDB ([The root-key record of a subtree](#the-root-key-record-of-a-subtree)). On RocksDB the delete of a tree removes the records of the data keyspace alone. So an aux record that was put under the prefix of a tree is still read on RocksDB under a tree that is made again at the key after the delete, and is charged where it is removed there; here there is none. That is a difference by design (D-241). No operation of GroveDB puts an aux or a meta record under the prefix of a tree; such a record is put at the seam.
- **Where the group writes an element over a tree**, what leaves is said by the look for that ([An element written over a tree](#an-element-written-over-a-tree)). Where it states a drop, this look is made again with it: a node that is removed in a subtree which that look drops, or in one below it, is not looked at, and a drop of that look which is below a drop of this one goes with it. A drop of this look comes first: what it takes is left out whatever that look says of it, and is not entered again. Of the other subtrees that are, or are below, a drop of that look, this look leaves out those that that look does not enter again and that the group holds removals for and no put, as it leaves out the two kinds below.
- **Two kinds of writes are not handed to the transaction** (`LigninSettled::leave_out`), and no enter is stated on their account. A subtree of theirs can still be entered with the group on another account, as a Merk of an indexed tree of which the group puts into another Merk. A write of a root-key record is of neither kind: it is handed over where it is kept ([The root-key record of a subtree](#the-root-key-record-of-a-subtree)). They are:
  - every write of the group into a subtree that this look drops or that is below such a drop;
  - the writes into a subtree that is not entered, where the group holds removals for it and no put: there is nothing to remove. Such are the removals of a delete whose tree another commit took since the delete read it. On RocksDB the delete of an absent key is still a write of that key: the conflict check of the commit sees it, and it removes what a commit beside the transaction put under the key before the group was applied. Here it is no write (the second open point below).
- **A look that states a drop follows the hosts above the subtrees the group writes into**, by a read of the entry of each, up to a dropped subtree or to one with no host, to tell which are below a drop. Where another open write scope of the transaction has written the Merk of one of those subtrees, the group is refused with the scope's overlap. A look that states no drop follows no host.
- **The removals that GroveDB staged for the records of a subtree that leaves are charged.** `FlatStore::clear` on a handle whose Merk has a node walks the node cursor, which shows each node as the record it is on RocksDB, and stages a removal with no cost for each key, as one change set that leaves the Merk with no root ([node-store.md](node-store.md#the-lignindb-store)). The batch is settled with them: each is charged from the committed record, two seeks and its length (`cost-model.md` D2), which is what RocksDB charges for the delete of each record. The drop takes the place of applying them. The same holds for the removals of a delete that keeps backward references up, and for the deletes of the flat records of an append-only tree.
- **A put into a subtree that is not entered** is held to the rule of every first write: through a handle that names the element, under a key whose node the group removes, it is a first write under a key that holds no element, and is refused with its group ([Subtrees](#subtrees-are-entered-by-the-first-batch-that-writes-into-them)).
- **A clear keeps the host**, and is what it is on RocksDB: `Merk::clear` removes the nodes by key, and the walk of `clear_subtree` deletes the trees in it one by one, each as above. The transaction's `Clear` is not used ([`transactions.md`](transactions.md), CV9).
- **A clear that is told to look for no tree** (`check_for_subtrees: false`) removes the elements of the trees in it with the other nodes. On RocksDB the records of those trees stay under their prefixes, where no element leads to them; here their subtrees are dropped. **Open, `GROVE-03-F1`:** two reads answer otherwise here than on RocksDB afterwards, and are to answer the same. A read by the path of such a tree that asks for no element on the way (`has_raw`) finds its records on RocksDB and none here, and a tree that is made again under the key is not empty on RocksDB (`is_empty_tree`) and is empty here; the grove's own check (`verify_grovedb`) then fails on RocksDB over the old records and finds nothing here. No drain ends that on RocksDB. The follow-up keeps the nodes of such a tree as records that no tree links.
- **What a drop leaves in the pages** is reclaimed by the background work of the database once no reader from before the drop can read it (`lignin_tree::drop`, `Db::reclaim`): the cells, the entries of the subtrees below, their flat records, and the pages that keep no cell.

A tree that is made again under the key of a dropped one starts with nothing in any keyspace of its subtrees. The root-key records that are kept for its prefixes are as the dropped tree left them ([The root-key record of a subtree](#the-root-key-record-of-a-subtree)). The entry of the one Merk of a tree stands for its element in a group of one batch: such a group, where it writes into the subtree and states no element, does not read the element ([Subtrees](#subtrees-are-entered-by-the-first-batch-that-writes-into-them)). A group of several batches does not take that way, and works out what the element hosts as for any other subtree: from the batch that states the element, and by a read of it where none does.

What this does not do:

- **A node that is removed in a subtree whose path no handle of the group was told states no drop**: the engine infers none from it.
- **A group in which a batch enters, drops or clears a subtree itself, or states one anew** leaves no write out, and is refused with `Error::NotSupported` where the look for what leaves by a removed node would state a drop for it: nothing says which of the two comes first. One operation of GroveDB makes such a group: the conversion of a tree to its 128-bit counterpart, where the Merk it writes again has a node ([A converted tree is stated anew](#a-converted-tree-is-stated-anew)).
- **Open, `TXN-03-F5`: what the look found is not judged again where the group is laid out.** The transaction refuses the drop of a subtree with no entry, and that is the one thing of these it tells. It has no drop that is made if the subtree is entered, as the enter of a subtree that is absent is; a drop does not say under which node its subtree hangs; and a removal is not stated for a subtree that may be entered by then. So, with commits beside the transaction between the look and the application:
  1. A subtree that such a commit enters under a removed node, which the look found with nothing under it, is not dropped. Where both transactions commit, the entry is left with no element, where RocksDB keeps records that no element leads to. `delete_prefix_ranges` drops such an entry.
  2. A removal that the group left out for a subtree which the look found not entered is not applied to what such a commit put there. RocksDB applies the delete.
  3. A drop that the look stated for a subtree takes the entry that such commits left in its place: one commit drops the subtree, and another enters its prefix again with no host, by a record through a handle by prefix. The records of that entry go with the drop.

  Whether the transactions commit is the conflict rule's to say, as for any two (CF2, CF2a), and that rule knows nothing of the directory. Each of the three takes two or three write transactions at once.

**The drops are of the look**, as the enters are ([Subtrees](#subtrees-are-entered-by-the-first-batch-that-writes-into-them)): what is entered under a removed node is read before the group is applied, and is stated again by each look. Where a commit beside the transaction took such a subtree after the look, the transaction refuses the drop of a subtree with no entry, and the engine looks again by the rule of every stale look. The next look states no drop of it, and the removals that the group holds for the subtrees that went are of subtrees that are not entered: the group is applied without them. Whether its commit is a conflict is the conflict rule's to say.

**The write set of such a delete** holds one removal for each record of the tree and of the trees in it until the group is applied, as the storage batch of RocksDB holds one delete for each. A removal is the key and what it is charged by; nothing of it reaches a page.

#### Flat drops and their drain

`drop_flat_subtree` removes the element of a tree and stages a pending-drop record that names the prefixes the tree owned, and `flush_pending_prefix_drops` drains the records afterwards, outside any transaction ([flat-store.md](flat-store.md#pending-prefix-drops)). The code of both names no engine. On LigninDB:

- **The subtree is dropped in the drop's own commit**, by the rule above: the group removes the element of a tree. The records of the subtree are gone for every reader from that commit on, and inside the dropping transaction from the drop on (`transactions.md` CV9, 14.5 D3). A root-key record that is kept outside the subtree is none of them, and stays until the drain ([The root-key record of a subtree](#the-root-key-record-of-a-subtree)). On RocksDB every record stays under its prefix until the drain deletes the ranges.
- **The pending-drop record is written and listed as on RocksDB**: the same record under the same key of the meta keyspace of the reserved namespace, charged the same, read by `pending_prefix_drop_records` from the latest committed state in the order of the primary prefixes.
- **What the drop leaves behind on RocksDB is marked.** Until the drain, RocksDB still holds the records of the dropped tree, and a cursor of another subtree that steps from no key comes to them ([flat-store.md](flat-store.md#a-step-from-no-key)). So the engine keeps a mark for a prefix and a keyspace: a record with no value in the aux keyspace of the reserved namespace, under one byte for the keyspace (`d`, `a` or `m`) and then the 32 bytes of the prefix (`grovedb/src/engine/lignin/behind.rs`; `left_behind_key` and `LigninSettled::leave_behind` in the store). Where a group is applied, a mark is stated for each prefix that a pending-drop record of the group names and that leaves with the group, by a drop of its subtree or of one it hangs under, and for each of the data, the aux and the meta keyspace in which RocksDB holds a record under the prefix once the group is applied: the group puts one there, or the transaction has one there that the group does not remove. The pending-drop record counts where the last batch of the group that holds an outcome for its key puts it, and one that does not decode names no prefix. The batch that puts the record is applied with the marks, which are charged nothing. A tree that nothing was written into leaves no mark.
- **A cursor counts a mark as one record beside its subtree.** Every handle that `subtree`, `immediate_subtree`, `subtree_by_prefix`, `immediate_subtree_by_prefix` and `subtree_beside` give is told where the marks are (`LigninNodeStore::left_behind_in`, [node-store.md](node-store.md#the-cursor)). A cursor of the data, the aux or the meta keyspace that steps from no key counts the marks of its keyspace under the prefixes on the side it is asked for, with the records of the subtrees there, at the version and with the writes that it reads those subtrees with: so in the dropping transaction from the drop on, for every other reader from its commit, and for nobody after a rollback. The mark of a cursor's own prefix is none of them. A mark stands for one record, whatever the tree held, so where a dropped tree held more than one, the records on that side are counted as fewer than RocksDB has. The first step from no key goes where it goes on RocksDB, which is the one GroveDB makes. Further steps away from the subtree can come to the end of that count, and stand nowhere, where the cursor of RocksDB still stands on a record.
- **`delete_prefix_ranges(prefixes)`** drops each prefix that the latest version has entered, but the prefix of the namespace of the root-key records, which stays entered, and removes the root-key record that is kept for the prefix ([The root-key record of a subtree](#the-root-key-record-of-a-subtree)) and the marks of the prefix, in one commit for each prefix that has any of the three, and writes nothing for a prefix that has none. A record whose drop went through this engine names prefixes whose subtrees left with the drop: of those the drain removes the root-key records and the marks. GroveDB passes the prefixes of a record once the path of the dropped tree leads to no element. The call itself looks at none of this: a prefix that is entered is dropped, whatever leads to it. It refuses the prefix of all `0xFF` bytes with RocksDB's words. Given the prefix of the reserved namespace itself, which the record of no flat drop of GroveDB names, it removes every record of the namespace's aux keyspace, and so the marks of every prefix, where RocksDB removes the records under that prefix and keeps what the drops left under the others.
- **`remove_pending_prefix_drop_record(prefix)`** is one write with no transaction.
- **A drain reports what it reports on RocksDB**: the liveness check, the order and the counts are GroveDB's. A step that fails ends the pass with its error, the record stays, and the next pass takes it up; the records that the pass reclaimed before stay reclaimed.

What differs between a flat drop and its drain is the reads `transactions.md` 14.5 D3 names: a read of the dropped prefix made directly, and a tree that is made again at the dropped path before the drain, which finds the old records on RocksDB and, of them, the root-key records alone here. A drain skips the record of a path that is live again, and the marks of its prefixes stay with it, as the old records stay on RocksDB, until a drain reclaims a record that names them.

What else holds of the marks:

- **The root-key record of a dropped Merk has no mark, and needs none.** It stays under its prefix until the drain ([The root-key record of a subtree](#the-root-key-record-of-a-subtree)), and the roots keyspace has no cursor at the seam ([flat-store.md](flat-store.md#a-step-from-no-key)).
- **The trees that a flat drop leaves behind against its caller's word have none.** The pending-drop record names the prefixes of the dropped tree alone, RocksDB keeps the records of a tree under it for ever, and the engine drops that tree with the one above it (`transactions.md` 14.5 D3).
- **A state sync copies none.** It follows the trees that elements lead to, and no element leads to a dropped tree or to the reserved namespace: a synced grove holds no record of a tree that its source dropped, on either engine, and no mark.
- **A checkpoint holds them**: it is the store of one version, and the namespace is of it. A checkpoint that was made between a drop and its drain holds the pending-drop record and the marks, as one of RocksDB holds the record and the dropped records, and its own drain removes them.
- **`lignin dump --all` holds them**, as records of the namespace, and a load of that dump puts them back. A dump of one subtree holds none, unless the namespace is the subtree that is dumped.
- **The physical checker** holds a mark to the rule of every flat record: it stands under a prefix that the subtree directory has an entry for (`tree-layout.md` D6), here the namespace's. The checker knows nothing of what the mark says.
- **A wipe takes them** with the namespace.
- **At the seam, the aux keyspace of the namespace is the engine's.** A cursor of that keyspace shows the marks as its records, where RocksDB shows none, and a record that is written there under a key which begins with `d`, `a` or `m` is counted as a mark. A cursor of the aux keyspace of another subtree does not count the marks as records of the namespace. GroveDB writes no aux record under that prefix.
- **The marks are one unit of exclusion with each other**, the aux keyspace of the namespace, as the pending-drop records are one in its meta keyspace: two flat drops that each leave a mark write both. A cursor that steps from no key reads that unit where the subtrees beside its own do not fill the count it asks for, and then as it reads those subtrees: in a write scope such a step is refused where another open scope holds the unit for writing (`transactions.md` SC3). GroveDB opens no write scope before GROVE-12.
- **The look is the group's.** What stays under a prefix is read in the transaction before the group is applied, with the look that states the drops, and is not judged again where the group is laid out ([A subtree leaves with its element](#a-subtree-leaves-with-its-element), the point that is open there with `TXN-03-F5`).

### The root-key record of a subtree

D-289, D-291. A Merk that is opened with no root key given (`Merk::open_base`) asks its store for the key of its root node (`NodeStore::root_key`, [node-store.md](node-store.md#the-root-key)), and for the node under that key where the store has a record of one (`Merk::load_base_root`). Its commit puts the record of that key where the root is another node than before, and removes the record where it leaves the Merk with no node. A restore puts the record for every Merk it hands over, also for one that is opened with the root key its element names, and reads it back ([node-store.md](node-store.md#chunks-and-restore)). GroveDB opens with no root key: the root Merk; the secondary of an indexed tree whose element names no root for its axis, where it reads or writes the tree (`open_indexed_secondary_at_path`) and where a session restores it; and a Merk that a chunk request names with no root key (`open_transactional_merk_by_prefix`). Outside a restore, a Merk that is opened with the root key its element names reads no such record, and its commit writes none.

**On RocksDB** the record is in the roots column under the prefix of its subtree. GroveDB's delete of a tree, its clear of a tree and its move of a tree remove and copy records of the data keyspace under the prefixes of the tree, and write nothing in the roots column under them. So the record that an insert into a secondary puts while the element names no root stays under the secondary's prefix when the rows of the tree are deleted, when the tree is deleted and when the tree is moved away, and a move brings no record to the prefixes that the tree goes to. The next open under such a prefix with no root key reads the record and then asks for the node it names. Against an open under a prefix with no record, that is charged the bytes of the key in the record more, and the fetch of that node, which is one seek where the store holds no node under the key. The record goes where a write of it puts another or removes it, which the commit of a Merk that is opened there with no root key and a restore make; where the range delete of a drained prefix (`delete_prefix_ranges`) takes it; and with a wipe.

**On LigninDB** a drop takes the records of a subtree in every keyspace and a move takes them to the new prefix ([A subtree leaves with its element](#a-subtree-leaves-with-its-element), [Moving a subtree on LigninDB](#moving-a-subtree-on-lignindb)), so a root-key record that was a record of its subtree would leave with a deleted tree and go with a moved one. The engine keeps it outside the subtree. Each handle that `subtree`, `immediate_subtree`, `subtree_by_prefix`, `immediate_subtree_by_prefix` and `subtree_beside` give, but a handle of the root Merk's subtree and one of the namespace's own prefix, keeps its root-key record in the roots keyspace of the namespace of the pending-drop records, under the 32 bytes of its own prefix and then the record's key (`keeping_its_root_key` in `grovedb/src/engine/lignin/mod.rs`; `LigninNodeStore::root_key_kept_in`, [node-store.md](node-store.md#opening-a-merk)). A handle of the namespace's own prefix keeps its record in the namespace as the record of its own subtree, under the record's key alone, and what follows is not of it. The record of the root Merk is in the roots keyspace of the root Merk's own subtree.

- **It is charged as the record of its subtree that it is for Merk**: a read, a put and a removal by the record's own key and its value (`cost-model.md` R1, W3, D1, D2), and a removal that comes with no cost from the committed record, which is read where it is kept. A batch charges it in the place that its own stored key has among the records of the roots keyspace, the prefix of its subtree and then its key, as a storage batch has it (B1): the order is in what a batch is charged before a put that is refused for its cost, and in the sum of the bytes that its removals free. Where it is kept, and the key it has there, are in no charge.
- **A drop and a move of the subtree leave it.** It is none of the subtree's records for the transaction: an immediate handle hands a write of it to the transaction where it is kept, and a batch stages it there ([node-store.md](node-store.md#opening-a-merk)). It is still read under the prefix of a subtree that a group dropped or that a batch moved away. A move brings none to the prefix that the subtree goes to: what is read there is the record that was put under that prefix before, where one was.
- **A write of it is taken whatever the group does with the writes of its subtree.** In the batch it is a record where it is kept and a write into no subtree, neither into its own nor into the namespace (`LigninSettled::written`, `LigninSettled::put_into`): the looks of a group find no write of a subtree in it, and no subtree is entered on its account. A handle that stages nothing else names no element and no path for its subtree to the group. Where the group hands the transaction none of the writes of that subtree, because it drops the subtree or because nothing is entered there and it holds removals alone ([A subtree leaves with its element](#a-subtree-leaves-with-its-element)), the write of the root-key record is handed over all the same. Through an immediate handle the write is taken whether or not the subtree is entered.
- **The namespace has to be entered for the record to be written.** The engine enters it where it opens a database that does not have it, and its wipe enters it in the commit of the wipe ([Subtrees](#subtrees-are-entered-by-the-first-batch-that-writes-into-them)). A drain does not take it away (below). No look enters it on account of a root-key record that is kept there for another prefix, and the transaction refuses a write of one that reaches it while the namespace is not entered. A write through a handle of the namespace's own prefix is a write into the namespace, its root-key record as any other, and the looks treat it as a write into any other subtree that no element hosts ([Subtrees](#subtrees-are-entered-by-the-first-batch-that-writes-into-them)).
- **The drain of a prefix removes the record** (`delete_prefix_ranges`, [Flat drops and their drain](#flat-drops-and-their-drain)), in the commit that drops what is entered under the prefix where something is, and in a commit of its own where nothing is. **A wipe removes every record**: it drops the namespace and enters it again with nothing in it. A drain that is given the prefix of the namespace itself does not drop the namespace. In one commit it removes the records of the namespace's data, aux and meta keyspaces, the pending-drop records among them, and of its roots keyspace the namespace's own root-key record. The root-key records that are kept there for other prefixes stay, as on RocksDB, whose range delete of that prefix takes what is under it and nothing that is under another. The transaction refuses the removal by range of the data keyspace of a subtree whose Merk has a root (`BatchError::NotFlat`), so that drain fails while a Merk under the namespace's prefix has a node. The record of a flat drop names prefixes of paths and of their secondaries, and the prefix of the namespace is made to be none of those (`storage/src/flat.rs`).
- **The engine finds no node by the record.** It finds a node by its key from the root that the Merk's entry in the subtree directory names ([node-store.md](node-store.md#opening-a-merk)). It reads the record in three places: `NodeStore::root_key`, which is Merk's read of it where it opens a Merk with no root key given, on both engines; the settling of a batch, for the charge of a removal of the record that came with no cost; and the drain, to remove it. Merk then asks its store for the node under the key that the record holds, and where the store holds no node under that key the Merk is opened empty, on both engines.
- **A record stays under its prefix** until a write of it puts another or removes it, until a drain names the prefix, or until the grove is wiped, as on RocksDB. A grove that a state sync made has one for each Merk that its restore handed over.
- **Every kept record is in one unit of exclusion**, the roots keyspace of the namespace (`transactions.md` SC2, SC3), where a record in its own subtree was of that subtree's unit. The record of the root Merk is of the unit of the root Merk's own roots keyspace. The namespace's own root-key record is of the unit of the kept records, and is as one of them in the rest of this. Any number of open write scopes of one transaction read kept records. A scope is granted the write of one only where no other open scope has read or written a kept record, of whatever subtree, and from then until that scope ends every other scope is refused a read and a write of one (`WriteScopeError::Overlap`). A scope that is refused keeps no claim by it. The conflict rule of two transactions goes by the key (CF2), and a kept record has a key of its own for each prefix. GroveDB opens no write scope before GROVE-12.
- **A state sync copies none.** A chunk holds nodes. A synced grove holds the records that its own restore put, whatever engine it was synced from and whatever engine it is on, and none that the history of its source left. A restore puts one for each Merk that it hands over, also for one under an element, and hands over no Merk that has no node. So a call can be charged otherwise on a synced grove than on its source, and that is so on both engines.
- **A checkpoint holds them**: it is the store of one version, and the namespace is of it.
- **`lignin dump --all` holds them**, as records of the namespace, and a load of that dump puts them back. A dump of one subtree holds the records of that subtree and of those below it. Of the root-key records that are kept under the namespace it holds none, unless the namespace is the subtree that is dumped; the dump of the root Merk's subtree holds the root Merk's own record.
- **The physical checker** holds a kept record to the rule of every flat record: it stands under a prefix that the subtree directory has an entry for (`tree-layout.md` D6), here the namespace's. The checker knows nothing of what the record says.
- **A database that an earlier build of this engine wrote** has the root-key record of each subtree in the roots keyspace of that subtree, where this engine reads the root Merk's and the namespace's own and no other, and has none of those that a drop took or that a move carried away: nothing puts those back. Version 1 of the format is not frozen before the first release ([format.md](format.md), U10), and no migration of such a database is made: it is charged as one that holds no root-key record but those two and those written since.
- **A migration from RocksDB** (OPS-02) copies the root-key record under every prefix of its source, also under a prefix where no tree is, through a handle of this engine, which keeps the root Merk's in the root Merk's own subtree and every other under the namespace (D-291).

`tests/root_keys.rs` holds the records and the charges against RocksDB ([How the LigninDB engine is checked](#how-the-lignindb-engine-is-checked)).

### What differs on grove versions 1 to 3 under a tree that keeps flat records

RocksDB keeps the nodes of a Merk and the flat records of a tree in one keyspace of the subtree, and a node's read is shown either as bytes under a key. The store shows a node of a Merk's tree as a node under every entry, and reads a flat record by the tree type of the subtree's entry ([node-store.md](node-store.md#unlinked-records), last point; D-197, D-280). Two histories of GroveDB write under one key as a tree that keeps flat records and as a tree whose data is a Merk. In the first the entry and what is under it are not of one kind; in the second the engine keeps them of one kind. Each is held by a test of `tests/append_only.rs` that runs it on both engines and takes RocksDB's answers as the required ones.

- **A keyed child under a tree that keeps flat records.** On grove versions 1 to 3 a batch that makes such a tree and inserts an element under it is taken, and the level of the child is a Merk under the prefix of the tree. Its node is a cell of that Merk: the node cursor of the subtree shows it with RocksDB's bytes at RocksDB's charges, and every answer of the history is RocksDB's (`a_keyed_child_under_a_tree_of_flat_records_is_walked_as_on_rocksdb`: the MMR tree, the bulk-append tree, the dense tree and the commitment tree). The close of a debug build finds nothing: the cell of the tree's element hosts that Merk, and the checker's rule for such a tree has a place for the one Merk of its keyed children (D-287; [node-store.md](node-store.md#hashes)), which the test asserts. A typed append after the batch is taken as well: the store applies each of its batches with the tree types that keep flat records, and under such a tree the transaction takes a flat record beside the nodes of a Merk where the batch is laid out on its pages (`transactions.md` ST1; D-282, D-311). In a transaction that a commit has met, the store's batches are taken by key, and one that is refused there as a batch with no tree types is (`NotFlat`, `NotMerk`) is told a conflict in its place (`BothByKey`), which the store and the engine report as the conflict of the seam. The three orders, with the child before the appends, after them and with no append, are RocksDB's from the first step through the delete of the tree, in every answer, cost and root hash (`a_keyed_child_under_an_mmr_tree_is_held_to_what_rocksdb_answers` and its three siblings), and the store is sound at a close that finds both kinds under the prefix (`tests/both_kinds.rs`, `a_store_with_nodes_and_flat_records_under_one_tree_is_sound_at_its_close`). The child and the appends in one transaction answer as on RocksDB too, for the four kinds (`a_keyed_child_and_appends_in_one_transaction_answer_as_on_rocksdb`). **One call is not taken: an append that goes under the key of the child's node.** Those grove versions hold the key of the child to nothing, so it can be a key that the tree writes a record of its own under. What the four kinds write: an MMR tree, its nodes under eight-byte keys, the position with the first bit set; a dense tree, its values under two-byte keys, the position, and its path records under three-byte keys, `h` and the position; a bulk-append tree, the keys of a dense tree, the nodes of its chunk MMR under four-byte keys, the position with the first bit set, and the one-byte key `r`; a commitment tree, the keys of a bulk-append tree and `__ct_data__`. RocksDB keeps one record for a key, the one written last. So does LigninDB, but it does not let a flat record take the place of a node (`transactions.md` ST1, `RecordUnderNode`): with the child made first, the append that would write the tree's record under the child's key fails with `NotSupported` ("lignindb: batch: a flat record is written under a key of data of … that a Merk node is under: a tree that keeps flat records has a child under a key of one of its records"). Nothing of the call is kept: the root hash is the one before it, every later answer and cost is the one RocksDB gives where the append is not made, and the store is sound at its close. On RocksDB the append is taken and overwrites the child's node. Those answers are held as the required ones, and LigninDB's as an open difference (D-311; `tests/both_kinds.rs`, `lignindb_does_not_yet_take_an_append_under_the_key_of_a_keyed_child`, on an MMR tree with the child under the key of its first node). With the child made after the append nothing is refused: its node takes the record under its key on both engines, the tree has lost the record of its first node, and the two typed reads that need it differ. RocksDB decodes the child's node as a node of the tree and fails ("deserialize node at pos 0"), and here no record is found, so the read of the value answers that there is none and the read of the root hash fails ("Inconsistent store"). Every other step is equal, the delete of the tree among them (`a_child_made_under_the_key_of_a_record_of_its_tree_takes_the_record_on_both_engines`).
- **An MMR tree written over an emptied indexed tree.** On grove version 3 a batch writes an empty MMR tree over a sum-indexed tree that was written into and emptied, whose Merks are entered with no root. The engine takes them out of the directory with the batch ([An element written over a tree](#an-element-written-over-a-tree)), and the append enters the subtree as the MMR tree's. The node cursor shows the MMR's record with its bytes, as RocksDB's does, every answer of the history is RocksDB's, and the close of a debug build finds nothing (`a_flat_tree_over_an_emptied_indexed_tree_is_walked_as_on_rocksdb`).

**What a check of the database holds of this.** `LigninEngine::new` gives the checks of its database the tree types that keep flat records (`grovedb_merk::store::lignin::keeps_flat_records`, `lignindb::Db::check_kinds_by`), in every build, and `lignin verify` gives them as well. A check then holds the data keyspace of every subtree in use to the tree type of its entry (`lignindb::verify`, "The data column by the tree type of the entry"):

- **Under an entry of a tree type that keeps flat records**, a key holds a node of the Merk of the keyed children or a record of the tree, and not both; and an entry that names an element as its host is hosted in its first place, and no other entry in use names that element. `a_store_with_nodes_and_flat_records_under_one_tree_is_sound_at_its_close` closes with both kinds under one prefix, and the check finds nothing.
- **Under every other entry**, a record of the data keyspace is a node that no node links ([node-store.md](node-store.md#unlinked-records)), in the form the engine keeps one in and under a key of no node of the subtree's Merk. The history of the second point above ends with the record of the MMR tree under an entry that states the MMR tree's type, and the check finds nothing. A flat record that is no such node under an entry of a Merk's tree type, which is what that history left before the engine took the entry of the indexed tree out, is a finding: the store's test of that state asserts it ([node-store.md](node-store.md#unlinked-records), the last point).
- **An entry that states no tree type** is held as every other entry is. A subtree has such an entry where it was entered under no element ([Subtrees are entered by the first batch that writes into them](#subtrees-are-entered-by-the-first-batch-that-writes-into-them)). A flat record in its data keyspace is a finding, which `a_range_delete_of_a_prefix_drops_what_is_entered_under_it` asserts of the record it puts there through a handle by prefix.

### The value hash that a delete leaves on grove versions 1 to 3

On `GROVE_V1` to `GROVE_V3` the delete of a tree that holds elements opens the Merk the tree is in again as a tree of the deleted tree's type (`delete_internal_on_transaction` v0, GroveDB #686, frozen for the chains built with it), and `Merk::root_hash` goes by the type a Merk was opened with. Where the node hashes of that Merk take their aggregate (the provable kinds) and those of the deleted tree's type take none, and the Merk still holds an element, the root hash that goes up is made with no aggregate, and the element of the Merk is put with a value hash made from it. `GroveDb::verify_grovedb` reports the path of that element. An insert below the element puts the hash Merk's rules make.

The engine does nothing about it: the stored hash is the one RocksDB holds, and the delete has RocksDB's answer, cost and root hash. Only the check of a close is concerned, which goes by Merk's rules. Those rules can say from what is stored that a value hash which differs is this one ([node-store.md](node-store.md#hashes)), and `LigninEngine::new` gives the check of a close the rules that do (`MerkHashRules::naming_left_hashes`), since the engine does not know which grove versions wrote its database. So such a database closes in a debug build with no panic, and the report of a check counts the hash apart (`Report::other_hashes`), with its cell, the prefix of its Merk and its key. A caller whose grove was written on later versions only asks for the close to fail on it (`LigninEngine::check_closes_with_no_left_hashes`), and a check with `MerkHashRules::for_check` alone reports it as a finding.

State sync of such a grove is refused by the session at the chunk of that Merk (`invalid chunk proof: chunk doesn't match expected root hash`), on RocksDB as on LigninDB and between them. A session that commits once, at its end (`RestoreCommitMode::Atomic`), has committed nothing then, which is the session the test runs. One that may commit before its end keeps what it committed before that chunk, with the mark of an incomplete restore ([State sync](#state-sync)).

By the same open, on those versions and on both engines, the delete panics in Merk (`TreeNode::hash_for_link`, "the node's feature_type is inconsistent with its tree_type") where a tree of one of the four provable kinds those versions make is deleted with what it holds from a tree of another of their nine kinds that keeps an element, and where a count indexed tree with rows is deleted from a plain tree that keeps an item. `tests/legacy.rs` holds all of it ([How the LigninDB engine is checked](#how-the-lignindb-engine-is-checked)).

### Queries and proofs

GROVE-06. A read of GroveDB (`get`, `get_raw`, `has_raw`, `follow_reference`, `query`, `query_raw`, the readers of values, sums and optional keys, `run_path_query`, the aggregate readers and the walk that adds sum items) and a proof (`prove_query`, `prove_query_many`, the trunk and the branch chunk) are code that names no engine. They open each Merk by its path, and the secondary of an indexed tree by its prefix beside its primary, read elements through it, walk a range with a cursor of the subtree's handle, and prove through Merk's provers, which read through the node store ([node-store.md](node-store.md#proofs)). The histories of [How the LigninDB engine is checked](#how-the-lignindb-engine-is-checked) hold each of them on the LigninDB engine to the answer, the proof bytes and the `OperationCost` it gives on RocksDB, but for the reads named under "What this leaves to later tasks" below. Three things were needed for that, one in the engine and two in GroveDB's own code:

- **A cursor of a write transaction is pointed at another subtree** ([One state across subtrees](#one-state-across-subtrees), and choice 6 below). A page by count under a subquery (`element/local_offset_read.rs`) reads the element of its tree in one subtree and its rows in another through one cursor, and so does a ranking of an indexed tree's axis that starts from an offset (`operations/indexed_tree.rs`): the element in the Merk above, then the nodes of the secondary. A trusted read whose query holds an offset of that kind also walks the query's own path, where it has one, through one cursor that is pointed at each Merk of the path in turn (`refuse_non_merk_on_offset_path`). Grove versions 1 to 4 refuse such a query. GROVE-01 refused such a cursor, so a read of either kind through a write transaction of the caller's failed on LigninDB with a storage error where RocksDB answers: the corpus case `legacy-subquery-offset` on grove version 5, and the path queries that the corpus traces `indexed-writes`, `wide-ranks` and `conversions` read through the block's write transaction.
- **A scan asks its cursor how the walk ended.** A move of a cursor returns no error, and a cursor whose engine did not make the move stands on no record, as one at the end of its records does. [node-store.md](node-store.md#cursor) has the scans of GroveDB and what each does now before it concludes anything from the end of its walk: it asks its cursor's `status`, and where that is an error it fails with it. A clear that checks for subtrees and may not delete them answers from the first tree its scan finds, without asking. The reads of a page by count do the same where they fetch a node by its key and find no record under it, and after they point their cursor at another subtree, where a cursor that could not be pointed there shows what the cursor of an empty subtree shows. On RocksDB nothing changes unless its iterator reports an error.
- **A walk of elements passes over a key whose record went under the cursor.** `ElementsIterator::next_element` took a key with no record under it for the end of the walk. A cursor of LigninDB stands on a key, not on a record ([node-store.md](node-store.md#the-cursor)), so it shows such a key where the transaction removed the node after the cursor came to the key and before the cursor was asked for its record; a record it has read it keeps until it moves. The walk goes on behind the key, as `KVIterator` does. No walk of elements in GroveDB removes a record under its own cursor through the transaction: the walks that remove what they find stage the removal in the batch of their operation, which no cursor shows.

#### How long a cursor's pin holds back reclaiming

A cursor of the LigninDB store that was opened with no error reads one committed version from the moment it is opened, also while nothing moves it ([node-store.md](node-store.md#the-cursor)), and the engine reclaims nothing that a pinned version still reads. A cursor of a snapshot reads under the snapshot's pin and holds none of its own. A cursor of a write transaction, or of the view of a write scope, that was opened with no error holds a pin of its own: it goes when the cursor is dropped, and before that only where the cursor could not be pointed at another subtree, which ends its walk. `Element::iterator` and `ElementsIterator` keep a cursor from one call to the next, and so do `KVIterator` and the pinned views of the reads by count.

**The rule: a cursor lives no longer than the operation of `GroveDb` that opened it.** Each of these walks is a local of the function that makes it. None is kept in a value that outlives the call, and none is handed to the caller of an operation. So the pin of a cursor holds reclaiming back for the length of one read, query, walk or proof, whatever the transaction it is made through lives for: a block's write transaction that stays open for seconds holds no version pinned through a cursor between two of its operations. The types hold a cursor to the life of its transaction and to no less: a cursor borrows the view its handle was opened on.

A read with no transaction is made through a snapshot, which holds its version pinned for the length of the operation ([What a transaction is](#what-a-transaction-is)), and so is a proof, but for the proof of a trunk chunk on grove versions 1 and 2, which opens a write transaction of its own for its length. What a write transaction that stays open holds back by itself is the engine's own rule and no cursor's ([transactions.md](transactions.md)). A caller that takes a cursor through the seam itself (`Engine::subtree`, then `NodeStore::cursor`) holds its pin for as long as it keeps the cursor.

`no_operation_keeps_a_version_pinned_once_it_has_returned` holds the rule by the engine's own count of pins (`DbStats::pins`), beside a write transaction that stays open: after reads by key, queries and walks, through that transaction and through none, and after proofs, which take no transaction, the count is what it was. A cursor that is opened through the write transaction and sought is one pin more, until it is dropped. `a_read_of_an_axis_keeps_no_version_pinned_once_it_has_returned` holds the same for the reads of an indexed tree's axes.

What this leaves to later tasks:

- **A band of an axis that is read in descending order and has no value above it in the ranking.** The read seeks to the end of the band and steps back from past the last record of its subtree, where RocksDB's answer depends on what follows the subtree in its column family. The cursor of the store answers the same ([flat-store.md](flat-store.md#a-step-from-no-key)), and the histories of the rows read such ranges (`QueryItem::Range`, `RangeTo` and `RangeAfterTo` that end past the last key, read right to left, in `tests/queries.rs`); the history of the axes (`tests/axes.rs`) reads no such band.
- **A grove that batches made.** The histories here write with `insert`, `delete` and the entry points of the indexed trees. `tests/batches.rs` compares the root hash after every batch, and the proofs of the trees that a batch wrote over others.
- **Fewer reads** (PERF-01, PERF-05). A proof on LigninDB reads the root of each Merk it opens whole, `Merk::branch_query` walks its path three times, and a cursor's value is a record that is built for it. The charges are RocksDB's all the same.

### State sync

GROVE-07. A node that serves a state sync answers `fetch_chunk`, and a node that syncs runs a session: `start_snapshot_syncing`, `apply_chunk` for each answer, and `commit_session` (`grovedb/src/replication`). The code names no engine. A grove on LigninDB syncs from one on RocksDB and the reverse, and each ends on the root hash of its source: the histories of [How the LigninDB engine is checked](#how-the-lignindb-engine-is-checked) run the four directions on every grove version.

**Serving.** `fetch_chunk` reads through one transaction: the caller's, or one it starts for the read (`start_read_transaction`), which is a snapshot on LigninDB and on RocksDB reads the latest committed state at each read ([Transactions](#transactions)). The first request of a session is the root hash of the grove, alone, and stands for the root Merk. Every other request holds chunk ids, and a chunk id is what it is on RocksDB: the 32 bytes of a subtree's prefix, then the root key and the tree type of its Merk and the ids of the chunks asked for. `fetch_chunk` opens the Merk a chunk id names by that prefix, with the root key and the tree type of the id, and has Merk's chunk producer make the chunk ([node-store.md](node-store.md#chunks-and-restore)); it reads the page of an append-only tree as flat records of the prefix, and the header of an indexed tree from its primary and its secondaries by their prefixes.

**What is held of the answers.** The requests that a session makes are answered by LigninDB with the bytes RocksDB answers them with: the histories of the sessions that commit once compare every request of the four directions with its payload. A request that no session makes is not held to that. One such request is a request that names a subtree of flat records as a Merk, which no session makes because a session asks for a subtree by the type of its element. RocksDB reads the flat record under the root key the request names as a node, where the record has a node's bytes, and then refuses the request or serves a chunk made of such records. The store reads a flat record of such a subtree by its key as RocksDB does ([node-store.md](node-store.md#reads-1)), which a test of the store holds; no history here makes the request. A session that is given an empty chunk in the place of a subtree that holds data is refused it, on both engines: where the parent commits to a Merk with nodes, where a tree of an append-only kind owes a page and where an indexed tree owes its header. A session that is given, for an indexed tree with children, a header that gives the hash of an empty Merk for the primary and for each axis with an empty root chunk of the primary, and after it an empty chunk for each secondary, is refused where the roots of the tree's Merks are held against what its element commits to.

**Restoring.** A session writes through one write transaction of its own and immediate handles. It restores the root Merk first and then, for every tree it finds in a restored Merk, the subtrees of that tree: a Merk from its chunks (`Restorer`), a tree that keeps its data flat by the replay of its entries, and an indexed tree as its primary and the secondary of each axis. On LigninDB a `Restorer` stages its chunks in memory and hands the store the finished Merk when it is finalized ([node-store.md](node-store.md#chunks-and-restore)).

An immediate handle enters nothing, and a Merk that one hands over is written alone, so its host does not name it ([Subtrees are entered by the first batch that writes into them](#subtrees-are-entered-by-the-first-batch-that-writes-into-them)). The session therefore says which subtrees it writes, with `Engine::adopt_restored_subtrees(path, &tx)`, where `path` is the path of the element that hosts them. The trait provides the call as one that does nothing, which is right for an engine to which a subtree is its prefix. On LigninDB (`grovedb/src/engine/lignin/restore.rs`):

- **A restore's subtree is entered right before the restore first writes into it, and the Merks of an indexed tree before the first of them is written.** For a Merk that is when its last chunk has arrived and it is about to be handed over (`apply_decoded_chunks`, before `finalize_with_grovedb_elements`). For a tree that keeps its data flat it is the first page that holds an entry or a frontier (`NonMerkRestorer::apply_page`). The engine reads the element under the last segment of the path from the transaction, which holds it because the Merk above was handed over, and enters those of the subtrees the element hosts that are not entered: each under the element at its position, with its tree type. For an indexed tree these are the primary and the secondary of every axis. So a Merk of an indexed tree is entered when the first of its tree's Merks that has a node is about to be handed over, which can be calls of `apply_chunk` before its own hand-over, and it is entered there also where it has no node itself. Of a tree with one subtree, a subtree the restore writes nothing into is not entered: a Merk with no node, or an append-only tree with no entry. Of an indexed tree with no child, no Merk is entered. The root Merk has no element: the engine enters it with the database and after a wipe.
- **Its host names it right after its hand-over**, in the same call of `apply_chunk` and before the session looks at another subtree. The session calls the engine again with the path of the element that hosts the Merk, which for a secondary is the path of its primary. Where the directory holds a root for a subtree of the element, the engine puts the element's node again with the value, the feature, the hashes and the links the transaction holds for it, and with every subtree the element hosts, by position (`LigninNodeStore::name_hosted`). The cell of the element then points at the root of each. A tree that keeps its data flat has no root, and nothing is named for it.
- **The enter, the hand-over and the naming are writes of one transaction.** For a tree with one Merk they are made in one call of `apply_chunk`. For an indexed tree they are spread over the calls from the first hand-over of one of its Merks to the last, and for a tree that keeps its data flat the enter and the pages over the calls that bring its pages. The session takes no commit between them: a session that commits once, at its end (`RestoreCommitMode::Atomic`), has one transaction, and a session that may commit before its end (`RestoreCommitMode::Incremental`) commits only at a point where no subtree is in flight and no indexed tree is part restored. So every Merk that a commit of a session holds is entered and named by its host in that commit.
- **The call is charged nothing and changes nothing a read shows**: no value, no hash and no root. Made again, it enters nothing more and puts the element's node with what it has. It begins with its reads of the element and of the entry of each subtree the element hosts, before any enter. A read of them that the transaction refuses is the error of the call, with nothing entered, and is not taken for a subtree that is not entered. An element that is no tree, a key with no element, and a subtree that is entered under another element or at another position are refused there, with `Error::NotSupported`. An error after those reads, of an enter that the subtree directory refuses or of the put of the element's node, is the error of the call, and what the call entered before it stays in the transaction.

**The directory of a synced grove.** Of the subtrees that the elements of a grove host, a synced grove has an entry for those its restore entered: a Merk that has a node, an append-only tree that has an entry, and every Merk of an indexed tree of which one has a node. A grove that batches wrote has an entry for each subtree that a batch wrote into and that has not left since, whatever the subtree holds now. A subtree leaves where a group removes the node it is entered under and states its drop ([A subtree leaves with its element](#a-subtree-leaves-with-its-element)) or writes an element over the tree and drops it ([An element written over a tree](#an-element-written-over-a-tree)), and stays where a tree is written again over the node and its subtree is kept, or the element is converted (MERK-09). So such a grove has entries that a grove synced from it has not, where a subtree was written into and holds nothing now: under a tree that was emptied, and under a tree that nothing was written into which was written over a tree that was written into. No chunk says which it is: an empty Merk is the same bytes whatever its prefix held before. So a write that the engine refuses because of such an entry, into an indexed tree written over an element that left its subtrees entered, is refused in the one grove and taken in the other, as RocksDB takes it. After the delete of the earlier element nothing is entered under the key in either grove, and both take the write.

**The root-key records of a synced grove** are those its own restore put, and none that the history of its source left: [The root-key record of a subtree](#the-root-key-record-of-a-subtree).

**What a session leaves that does not commit.** A session that commits once gives up its transaction when it is dropped, whether or not a chunk of it was refused: nothing of it is in the database, on either engine, and the database starts another session. A session that may commit before its end leaves the commits it made. From the first of them on the database says that it holds an incomplete restore (`has_incomplete_restore`) and starts no session: it is discarded and not read. Such a database can hold a tree whose element commits to a Merk the session had not restored, and the value hash of such an element is what the physical checker reports in the databases of the histories below, and nothing else. The owner of a database that holds the mark does two things with it and no other: it reads the mark, and it closes the database, to discard its directory. The check that the close of a database makes in a debug build would report those value hashes, so the engine leaves a database that holds the mark out of that check when the engine is dropped (`Drop` of `LigninEngine`, `Db::unchecked_at_close`). It reads the mark through a snapshot of the latest version, and takes the close out of the check only on a mark that it read: where the read fails, the engine changes nothing of the close. For a database with no mark it changes nothing of the close either, and so for one whose session committed at its end, which takes the mark away: such a database is closed as any database is.

**A refused chunk ends the session.** An error inside the application of a chunk (`apply_decoded_chunks`: a chunk that its restore refuses, a chunk for a subtree that is not in flight, a hand-over that fails) marks the session as failed, and from then on `apply_chunk` and `commit_session` are refused by the session itself. So a `Restorer` is given no chunk after one it refused, and a restore that a refused chunk left unable to finish ([node-store.md](node-store.md#chunks-and-restore)) is not met through a session, on either engine. An error before that, of the protocol version or of the packing of a request and its payload, reaches no restorer and leaves the session as it was.

**A session into a database that holds a grove** fails at the root Merk on LigninDB, and leaves the database as it was. A restore over a Merk that holds nodes is refused where the Merk is handed over. Where the root Merk of the source has no node, nothing is handed over, and the session fails where it finds the root Merk of its target not empty. A caller wipes first (`GroveDb::wipe`). RocksDB writes the chunks of a restore over what is there.

**Memory.** On LigninDB the chunks of the subtrees in flight are staged in memory, and the transaction's write set holds every node it was handed until it commits ([node-store.md](node-store.md#chunks-and-restore)). Spooling the staging and a load that does not hold its values until the commit are not built (TXN-10).

What this leaves to later tasks:

- **An entry that outlives the element it was entered for**, where another was written over it or it was converted (GROVE-03, MERK-09), above.
- **The call for a restore reads the entry of a subtree and then enters it**, which is one transaction's read and write. It does not state the enter as one that is made if the subtree is absent (`SubtreeWrite::EnterIfAbsent`).
- **The layout of a restored Merk by the bulk loader, and its memory** (TXN-10).

### Checkpoints

GROVE-08. `GroveDb` has three checkpoint calls, written for any engine (`grovedb/src/checkpoints.rs`): `create_checkpoint(path)`, `open_checkpoint_with_engine(path)` and `delete_checkpoint_with_engine(path)`, the last two also as `open_checkpoint` and `delete_checkpoint` on the default engine. Each is the engine's call of the same name. On LigninDB they are in `grovedb/src/engine/lignin/checkpoint.rs`. What a checkpoint is in the engine's files, how one is made beside commits, and what a creation or a deletion leaves that fails or that the power cuts, is `lignindb`'s to say: the module documentation of `lignindb::checkpoint`, and `Db::checkpoint`. What follows is what a caller of GroveDB has on this engine.

**`create_checkpoint(path)`** is `Db::checkpoint(path, CheckpointOptions::default())`.

- The checkpoint holds the grove as one committed version has it: a version that was the latest during the call, with nothing of a write transaction that had not committed. When the call returns `Ok` it is as durable as the directory above `path`, whose own name is the caller's to have made durable (`lignindb::checkpoint`, "Durability, and a creation that fails").
- A `path` that is there when the call is made is refused and left as it is: a checkpoint, a file, and an empty directory. A creation at a `path` whose directory above is not there fails too, and makes no directory for it: the caller makes that one (P-14 of [platform-requirements.md](platform-requirements.md)).
- `path` can be inside the directory of the database it is made of, as Platform's `checkpoints/<height>` is (P-14): the database opens again with it there.
- The engine makes a checkpoint with the default `CheckpointOptions`: a creation that finds more than 1 MiB of log held for the first open of the checkpoint to replay asks write-back to catch up first (`CheckpointOptions::catch_up_above`). What the catch-up reaches changes how much log that first open replays, and nothing of the state the checkpoint opens to. A caller that wants another amount makes the checkpoint with `Db::checkpoint`, on `LigninEngine::database()`.
- A creation that fails has put nothing at `path`, with one exception that `lignindb::checkpoint` names ("Durability, and a creation that fails"): where the name of the whole checkpoint could not be made durable and could not be taken back either, the whole checkpoint is at `path` when the error is returned.

**`open_checkpoint(path)`** is `Db::open` with the default `Options` and `create_if_missing` off, and then what `open` does ([Each operation](#each-operation)).

- A checkpoint is a database like any other: nothing in its directory says that it is a checkpoint. So this call does not tell a checkpoint from another database of this engine, and `open(path)` opens a checkpoint (P-15). The one difference between the two calls is that `open_checkpoint` makes no database: where `path` has nothing, or is an empty directory, it fails, and nothing is made there.
- The checkpoint gives the root hash, the stored records and the answers of its source at the moment it was made, with the `OperationCost` and the proof bytes the source gave then (P-16).
- It takes writes, and they are its own: its source does not show them, and it does not show what its source writes after it was made. A checkpoint is made of a checkpoint as of any database.
- Platform's `platform_state.bin`, put into the directory beside the engine's files before the checkpoint is opened (P-17), does not keep it from opening and stays as it is. Which entries of a directory keep it from opening is `lignindb::db`'s to say.

**`delete_checkpoint(path)`** is `lignindb::checkpoint::delete` on the file system of the default `Options`, and that function's documentation is its contract. `GroveDb` refuses a path of fewer than two components before it asks the engine. The checkpoint is not opened. **The call can remove more than a checkpoint**: another closed database of this engine, an empty directory, a directory with an empty `LOCK` file alone, and a directory whose name ends in `.creating`, whatever else it holds. The documentation of `GroveDb::delete_checkpoint_with_engine` warns of what it can remove and says when it looks for the directory that a creation left beside `path`; the rule is `lignindb::checkpoint::delete`'s.

A caller can remove the directory of a checkpoint itself instead, as Platform does while a handle has the checkpoint open (P-18). The module documentation of `lignindb::db` says what such a handle does from then on, and that its close makes nothing at the path. It also says ("Background work") what a session does about the files that its threads would make in the directory meanwhile: the open makes turns of write-back for what its recovery replayed before it returns, and leaves to write-back's thread what those turns did not write; and the cleaner's thread and the reclaimer's make no turn until the session is asked for its first commit, which nobody asks of a checkpoint that is only served. A session that keeps a reserve (`Options::reserve`; the default keeps none) and is asked for no commit makes neither file of the reserve once its open has returned, and can remove both, `RESERVE` and `RESERVE.new`, where it is given an error for room. The database the checkpoint was made of shares links with it and nothing else, and is as it was.

**The file system.** `open_checkpoint` and `delete_checkpoint` have no database to ask, and work on the file system of the default `Options`. A checkpoint of an engine that was opened on another one (`LigninEngine::open_with`) is made on that one: it is opened and deleted through `lignindb`, with those options.

#### The names the engine keeps

- **`<path>.creating`** is the directory a checkpoint at `path` is built in. It gets the name `path` when the checkpoint is whole. A creation that failed, or that the power cut, can leave it, with a part of a checkpoint in it or a whole one. It is no checkpoint. `open` and `open_checkpoint` refuse a path whose last name, as it is given, ends so, in any case of its ASCII letters, and a creation that `lignindb` refuses for such a name of its target is `Error::NotSupported`. The refusal of an open goes by the last name of the path as it is given, and by nothing else: a path that leads to such a directory under a last name that does not end so, as a link can and as another spelling of the name can, is opened as any other path. So a caller opens such a directory through no other name. It keeps the disk space of its files until it goes: a creation at `path` that gets as far as building takes it over, and `delete_checkpoint` says when a deletion removes it.
- **`MANIFEST.deleting`**, in a directory, is the name a deletion gives the manifest before it removes a file. A directory that holds an entry of that name, of any kind, is opened by neither open. `delete_checkpoint` finishes a deletion that was cut short. It goes by what the files hold and not by the name: where the manifest is whole under its own name, beside a file of that name which something else made, it removes that whole database too. Whoever wants to keep such a database removes that file and nothing else.

**GroveDB keeps no directory of checkpoints, and lists none.** A caller that does (Platform, OPS-03) keeps to two rules, both from `lignindb::checkpoint` ("What the looks do not tell"):

- An entry whose listed name ends in `.creating`, in any case of its ASCII letters, is no checkpoint: it is not opened and not counted. Platform opens the directories of `checkpoints/` whose names are numbers (P-19), which passes over it.
- A file system can list a name in another spelling than the one it was given. The open of a checkpoint goes where the file system leads the path it is given. A deletion, and the take-over of what a creation left, go by the name as the directory above lists it, byte for byte: given another spelling, a deletion refuses a checkpoint that is there, and finds no directory that a creation left beside it. A caller whose names a file system may list otherwise deletes under the listed spelling.

**Errors.** An error of `Db::checkpoint`, of `Db::open` or of `checkpoint::delete` is `Error::StorageError` with the engine's words, with two exceptions ([Errors](#errors)): `CheckpointError::ReservedName`, the refusal of a target for its name, is `Error::NotSupported`, and the words of a creation that was refused because the commit path of the session has stopped, or whose own sync of the log failed, say that the database has to be opened again.

### Choices made here that the plan left open

1. **Scopes map to operations one to one in iteration one** (SC1): a scope for each application, opened and merged inside the call. The alternative, one scope that a transaction keeps for its life, would have to be merged and opened again around every savepoint and before the commit, and a transaction would be a value that borrows itself.
2. **Subtrees are entered by the engine, lazily**, as above. The alternative is a call in the seam with which GroveDB names each subtree where it writes the element; GROVE-05 did not take it for drops either: the engine says a drop where a group removes the element of a tree ([A subtree leaves with its element](#a-subtree-leaves-with-its-element)). For the Merks of an indexed tree the engine reads the element (item 9).
3. **`settle_batch` reads the committed state through a write transaction of its own**, because the seam gives it none, and writes nothing into it: such a transaction reads the latest committed state at each read (RD3), so each delete that came with no cost is charged from the record as it is committed when the delete is come to, as RocksDB does between `continue_write_batch` and the write.
4. **A read with no transaction is pinned** (RD2, `transactions.md` 14.5 D1), which the seam allows and the `pinned-reads` engine of the suite has held GroveDB to.
5. **`Error::NotSupported` in `grovedb_storage::Error`**, mapped by `From` to `grovedb::Error::NotSupported`: a limit of the engine is told apart from a fault of the storage, as the node store does for a write (`node-store.md`, "A Merk too deep for the directory").
6. **A cursor is retargeted under the pin it took when it was opened** (GROVE-06; GROVE-01 retargeted in a snapshot only and refused a cursor of a write transaction). GroveDB retargets for local count offsets and for the paginated reads of an indexed tree's secondary. A cursor of a write transaction keeps its version and its lease, and opens the other Merk through the subtree directory of that version. So the element of a page's tree and the nodes the page is counted through are of one committed state beside the transaction's writes, as on RocksDB, whose iterator keeps the state of its creation. What a page of an indexed tree's entries resolves afterwards, the primary item of each row, is read through the transaction once the cursor is dropped, on both engines. The alternative, a second cursor opened on the other subtree, would pin the version that is the latest then, and a commit between the two opens would give a page its element from one state and its rows from another.
7. **`lignindb` gained five things for the engine**: a node of a Merk read by key through a reader's opened subtree (`Opened::node`); cursors over nodes and over flat records that a reader keeps from one operation to the next (`NodeWalk`, which refuses an operation of another reader, by its version and its lease, and `RecordWalk`, which refuses one of another database or version and takes any reader of the same); three variants of `ReadError` for them; the physical checker on an open database (`Db::verify` and `Db::close_and_verify`, which took the place of `Db::check`); and what a resolved batch enters and holds for a key (`Resolved::enters`, `Resolved::held`). GROVE-06 added a sixth: `MerkCursor::retarget`, with `Resumed::retarget` for a parked cursor, which points a cursor of a write transaction at another Merk of the version it keeps pinned. MERK-05-F1 added a seventh: the count of the records beside a subtree (`Cursor::beside`, `Resumed::beside`, `Operation::beside`, over `Directory::rooted_beside` of `lignin-tree`), which the store's cursors ask for a step from no key ([node-store.md](node-store.md#flat-records)). MERK-05-F2 added an eighth: the same count with keys of one unit standing for records of other subtrees (`StandIns`, `Cursor::beside_with`, `Resumed::beside_with`, `Operation::beside_with`), for the marks of [flat drops](#flat-drops-and-their-drain).
8. **A subtree that is owed an enter is entered if it is absent** (D-181 item 2). Whether a subtree is owed one is read before the group is applied, in the transaction's view, to state nothing for a subtree the transaction holds as entered: this look changes nothing of the entry of such a subtree, whatever its element is now. For the Merks of an indexed tree the same reads also say where each is entered, and a group is refused where the last read of one of them finds it entered elsewhere ([An indexed tree hosts several Merks](#an-indexed-tree-hosts-several-merks)). What is stated is judged by the transaction where the write is laid out, so a commit that enters the subtree after the look, with the tree type and the host that are stated, refuses nothing. The look is several reads and the application an operation after them, and a commit can come between any two: a group that the transaction refuses for an entry which the look had found otherwise is looked for and applied again, where no batch of the group enters, drops or clears a subtree itself, or states one anew, and a commit was published since before that look. A bound on the applications was the alternative: it would answer a caller with the transaction's refusal, where RocksDB takes the write, once commits had come between that many looks and their applications. To look again after every refusal, and to apply again where the two looks differ, was another: it answers the refusal where a second commit puts back what the first took, and it applies a group again that is refused for a cause of its own. For this `lignindb` gained `SubtreeWrite::EnterIfAbsent`, beside the enter of a subtree that is new, and `Db::wipe_entering`, with which the wipe and the two subtrees every grove has are one commit. The alternative for a subtree that is entered otherwise, to take it as entered without a word, would hide a caller that names one subtree as two; it stays an error.
9. **The seam names the element of a secondary, and the engine reads what the element hosts** (GROVE-04): `Engine::subtree_beside`, provided as `subtree_by_prefix`, and the engine's reading of the element where a group is applied. The alternative is a statement of GroveDB's own at each place that writes an indexed element, which the batch, the direct inserts and the repair each do in their own way. The engine knows the element as the group leaves it, which no handle does: a handle is opened before the operation knows the element's new roots. What it costs is that `grovedb::engine::lignin` knows which elements host more than one Merk and how their secondaries are named.
10. **A restore tells the engine which subtrees it writes** (GROVE-07): `Engine::adopt_restored_subtrees`, which the trait provides as a call that does nothing. The engine reads the element, as it does for a batch (item 9), so the session states no tree type and no axis. Two alternatives were not taken. An immediate handle that enters its subtree by itself and names its Merk in its host when it commits knows one subtree, so the secondaries of an indexed tree would be entered apart from their primary and at no position, and a handle of one Merk would write a node of the Merk above. A restore through a batch is refused by the batch, which holds one outcome for a key and cannot say that a Merk is whole.

## Choices this task made

The plan left these open. Later tasks build on them.

1. **The blanket `impl<S: StorageContext> NodeStore for S` stays.** The RocksDB engine's handle is the storage context itself, so `Merk<PrefixedRocksDbTransactionContext>` is still the Merk type on RocksDB and no `KvNodeStore<S>` wrapper is needed. The price is the one SEAM-02 measured: a `NodeStore` that is not a storage context has to be a type Merk defines, so `LigninEngine::Subtree` is `LigninNodeStore`, in `merk::store::lignin`.
2. **One handle is a `NodeStore` and a `FlatStore`**, and the caller names the trait. The alternative, two handle types and two ways to open them, would have asked every call site which one it wants at the open, where the element is often not read yet.
3. **Errors are `grovedb_storage::Error`**, with the engine-neutral outcomes as variants of it (`Commit`, `WriteScope`), next to `SnapshotReadOnlyTransaction`, which is the engine-neutral `ReadOnly` already. It is the error that crosses all three seams, so a scope's `Overlap` can come out of a `FlatStore::put`. This put two variants and two types into `storage/src/error.rs`, outside the location the register names.
4. **A conflict is a class of error, not a new error on RocksDB.** `commit_error()` reads the class off the value RocksDB returns.
5. **A write scope lends a view that has the type of a transaction.** GROVE-12 may want more than that, such as a scope that owns a Merk cache. RocksDB is removed before scopes are used, so its part of the choice is small.
6. **The RocksDB engine cannot roll back a scope**, and says so with a typed error.
7. **No `Send` bound** on `NodeStore`, `FlatStore`, the handles, the batch or the transaction.
8. **The pinned view is a cursor that can be retargeted**, not a view type of its own. [node-store.md](node-store.md#call-sites-outside-merk) sketched "a pinned read view from which a cursor for any subtree can be taken". On RocksDB the view is one iterator, which serves one subtree at a time, and that is what the function says.
9. **Two fee rules are stated by the RocksDB engine's code** until SEAM-05 moves them: the removal of a moved record from its old prefix is staged as a delete with an empty cost (one seek, nothing freed), and what `settle_batch` charges is `continue_write_batch`'s rule.
10. **Static functions that name no engine stay on the default engine** (rule 2 above). They would otherwise need an engine written out at every call, in Platform too.
11. **Savepoints are operations of the engine and of `GroveDb`**, so that an engine can refuse one while a scope is open. `Tx::set_savepoint` and `Tx::rollback_to_savepoint` stay, and Platform calls them.
12. **`GroveDb`'s lifetimes in generic code** are as described under [Lifetimes](#lifetimes).
13. **`merk/src/test_utils` is unchanged.** SEAM-06 decided what it becomes: the harness of [`test-engines.md`](test-engines.md#merk).
14. **A read that is given no transaction starts one of its own kind**, `start_read_transaction`, so that an engine can tell it from a write and pin it (RD2). Which operations read was decided by one rule: an operation that never commits the transaction it started. A read starts exactly one, and hands it on. This changed how many transactions a read starts on RocksDB, from one for each part of the operation to one, and nothing a caller can see.
15. **A test that reaches under GroveDB names the RocksDB storage**, through `RocksDbEngine::storage()`. It reads or damages records as RocksDB stores them, and no other engine has those.
