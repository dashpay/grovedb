# Unsafe code in LigninDB: the audit

The rule is DEC-07 of the plan (dashpay/grovedb#1052): unsafe code is confined to the file layer (`lignin-io`) and the buffer pool (`lignin-store::cache`), which carry Miri and loom coverage, and every other LigninDB crate forbids it. This document is the audit of that rule (task VER-06, and for the direct I/O path task IO-03): where the unsafe code is, what each piece of it rests on, which test reaches it, and what keeps all of that true after the audit.

A test reads this document and the sources and fails when they differ: `lignin-store/tests/unsafe_audit.rs`. Four tables below are its input, each between a pair of markers (`frame`, `trusted`, `allocators` and `ring`), so they are changed with the code, in the same commit.

## 1. Where the unsafe code is

| Place | Unsafe code | Lint |
| --- | --- | --- |
| `lignin-store/src/cache/frame.rs` | All of the buffer pool's: 40 blocks, 5 unsafe functions, 5 `unsafe impl` of `Send` and `Sync`, and 2 `unsafe extern` blocks, which declare the system's `mmap` and `munmap`. | `lignin-store` has `#![deny(unsafe_code)]`, and `cache/mod.rs` has the one `#[allow(unsafe_code)]`, on `mod frame`. |
| `lignin-io/src/linux/ring.rs` | All of the direct I/O path's, which is built on Linux with the feature `direct_io`: 15 blocks, 1 unsafe function and 3 `unsafe impl` of `Send`, and 7 blocks in the tests of the file, where a model stands for the system's side of a ring (section 8). | `lignin-io` has `#![deny(unsafe_code)]`, and `linux.rs` has the one `#[allow(unsafe_code)]` of the crate, on `mod ring`. |
| The rest of `lignin-io` | None. The file layer is written against `std`, and against the safe functions of `rustix` where `std` has none. | The crate's `#![deny(unsafe_code)]`. |
| `lignin-format`, `lignin-tree`, `lignindb`, `lignin-tools`, `lignin-testkit` and its `cost-model-storage` | None. | `#![forbid(unsafe_code)]` in each library. |
| `merk/src/store/lignin` | None. | Merk's own lints; the scan below covers the directory. |
| `grovedb/src/engine/lignin` | None. | GroveDB's own lints; the scan below covers the directory. |
| Nine test targets (section 5) | A counting allocator each: one `unsafe impl GlobalAlloc` that hands every call to `System`. | A test target is a crate of its own, which the library's lint does not reach. The scan below does. |

## 2. What keeps it so

`lignin-store/tests/unsafe_audit.rs` runs with the crate's tests, so in CI on every platform the LigninDB crates are tested on. It reads every `.rs` file under every workspace directory whose name begins with `lignin`, and under `merk/src/store/lignin` and `grovedb/src/engine/lignin`, with comments and string and character literals blanked, and checks:

1. **The keyword `unsafe` is in the files this document lists and in no other.** This holds for every target (libraries, binaries, tests, benches, build scripts), which a lint in a library does not. It holds for the code of documentation tests as well, which is read from the `///` and `//!` comments; a block documentation comment (`/** */`), which the reader does not take apart, is refused.
2. **Every library forbids unsafe code** as an attribute of the crate itself, the two of section 1 deny it, and the lint `unsafe_code` is named nowhere else but in the two `allow`, which are on `mod frame` and on `mod ring`.
3. **Every unsafe block, every `unsafe impl` and every `unsafe extern` block has a comment directly above its line, one of whose lines begins `// SAFETY:`**, and every `unsafe fn` that is not a trait's method has a `# Safety` section. Only attributes may stand between, and no two blocks share a line. `lignin-io` and `lignin-store` also deny `clippy::undocumented_unsafe_blocks`, so CI's clippy run says the same of the blocks and the `unsafe impl` of their libraries.
4. **The unsafe code of `frame.rs` is, site for site and in order, the inventory of section 4, and that of `ring.rs` the inventory of section 8.** A block that is added, removed or moved to another function fails the test until the inventory is changed, which is the moment to read the section again.
5. **Every test an inventory names exists**, is the one function of its name in its file, and has `#[test]`. Nothing on it, on a module that is written around it in its file, or on its file ignores it or leaves it out of a build, but for the build of a loom model, where every test but the models is left out. The test does not read the declaration of a module that is a file of its own (`mod tests;`), where a condition can stand as well. For the inventory of `ring.rs` there is one exception more, `#[cfg_attr(miri, ignore = "…")]`, and a rule that bounds it: every row names first a test of the model in `ring.rs` itself with no such attribute, but the rows of what Miri does not have, which the test lists by name (section 8.3).
6. **The places that hand out a way to reach a frame are as many as section 4.3 counts.** They are safe code that the unsafe blocks trust.
7. **Each counting allocator is, line for line, the shape of section 5**: the four methods, each the one call of `System`'s method of the same name with the same arguments.
8. **Every file a crate compiles is one the scan read, or is held to the lint by the compiler**: a module with a `path` attribute names a file among those that were read, or is in a library that forbids unsafe code (the cost model's stand-in for `grovedb-storage` takes three of that crate's files this way), and no file is brought in with `include!`.

What the scan is and is not. It reads source text with a small reader of its own, which knows comments, literals, attributes, modules and the headers of `impl` and `fn`. It was tried on 47 changes that it must notice and on one that it must not (the task's report lists them). It is a tripwire for the forms this code is written in, not a proof about every form Rust allows: it does not expand macros, so code that a macro of another crate expands to (`thread_local!`, for one) is that crate's and is not seen, and the counts of section 4.3 are of the spellings the file uses. Where the reader meets something it does not understand, the inventory or the counts stop matching and the test fails. The engine's crates depend on two crates outside the workspace on every platform, `crc32c` and `lz4_flex` (with its safe encoder and decoder), both in `lignin-format`. `lignin-io` depends on a third, `rustix`, for calls that `std` does not have: on Linux and on macOS for the hint of a read (`posix_fadvise` and `fcntl(F_RDADVISE)`), on macOS for the plain `fsync` of a set that is synced together (both in `lignin-io/src/std_fs.rs`, through safe functions of `rustix`), and on Linux, with the feature `direct_io`, for the calls of the direct I/O path (section 8.4).

What "a test that exercises it" means here. For an unsafe block or an unsafe function, a named test executes its line; each such row names, first, a test that is deterministic and runs on one thread. Section 6 says how that is measured for `frame.rs`, and section 8.2 how it was checked for `ring.rs`. An `unsafe impl` has no line to execute: the tests named for the five of `frame.rs` send and share the pool and its handles between threads, which is what those declarations allow, and the tests named for the three of `ring.rs` send memory, and a ring of the system, to another thread, which uses and drops it. One block, `Frame::attached`, names a second test, of three readers at once (finding 6 of section 4.4). All the tests that the inventory of `frame.rs` names run under Miri as well (section 3), where executing the line is what lets Miri check it; section 8.3 says which of the ring's do.

## 3. Miri

Miri is `cargo +nightly-2026-02-24 miri` (the newest toolchain the project's machines have with Miri). It interprets the tests and reports undefined behaviour: a read or write outside an allocation or after it was freed, a use of memory that was never written, a reference used against the borrow rules, a data race, and a mismatched deallocation. It also reports memory of the allocator's that is still allocated at the end; a mapping that is never unmapped it does not report (section 4.5).

| Run | Command | What it shows |
| --- | --- | --- |
| The buffer pool, Stacked Borrows | `cargo +nightly-2026-02-24 miri test -p lignin-store --lib cache::` | Every test of the pool but three, which it ignores: the test of a mapping too large to have, which Miri stops on (section 4.5), and the two measurements of `cache/tests/measure.rs`, which no run includes unless it asks for them. |
| The buffer pool, Tree Borrows | the same with `MIRIFLAGS=-Zmiri-tree-borrows` | The same tests under the other model of the borrow rules. |
| The races, many schedules | `MIRIFLAGS=-Zmiri-many-seeds=0..64 cargo +nightly-2026-02-24 miri test -p lignin-store --lib cache::tests::races`, under both borrow models | Each race of `cache/tests/races.rs` under 64 of Miri's random schedules, with its data-race detector and its emulation of weak memory. |
| The buffer pool, stricter | the first with `MIRIFLAGS="-Zmiri-strict-provenance -Zmiri-symbolic-alignment-check"` | No pointer is made from an integer, and no access relies on an alignment that an address only happens to have. |
| The pool measured at the allocator | `cargo +nightly-2026-02-24 miri test -p lignin-store --test cache_alloc` | The pool under a counting allocator, which is unsafe code of the tests (section 5). |

| The ring of the direct I/O path | `cargo +nightly-2026-02-24 miri test -p lignin-io --features direct_io --lib linux::`, under both borrow models | The unsafe code of `linux/ring.rs` on a model of the system's side of a ring, and the safe code of `linux/aligned.rs` (section 8.3). |
| Another production platform | the first run and the file layer's with `--target aarch64-unknown-linux-gnu` | The same code as the other platform of DEC-06 compiles it. |

Miri ignores the tests of `lignin-io` that need what it does not emulate: hard links, inode numbers, `/dev/full`, a second filesystem, spawned processes, and a read at an offset beyond the largest file some file systems allow (Miri's `pread` is a seek, which fails there with `EINVAL` where `pread` reads nothing; the case is skipped under Miri on every file system). Each has `#[cfg_attr(miri, ignore = "...")]` with the reason, and they run in every normal test run. Under Miri the std backend opens a directory without `O_DIRECTORY`, a flag that Miri's `open` stops on as unsupported, and tells that it is one by a look at the open file, as it does on a system whose number for the flag it does not have (`open_dir` in `lignin-io/src/std_fs.rs`). Without its feature `direct_io`, `lignin-io` has no unsafe code, so what Miri checks in that run is `std`'s use of the system and the crate's threads. The unsafe code of the feature is the ring's, and section 8.3 says what Miri runs of it.

Results at the audited commit are in the task's report (the commands above, their test counts and their logs). The numbers of tests change as tests are added; what has to stay for the pool is no error, and no test ignored but those three.

**What Miri does not show.** It runs the schedules it draws, not all of them, and it does not find an atomic order that is too weak unless a schedule it draws happens to show it. Rule A6 of `frame.rs` rests on `SeqCst` orders in `frame.rs` and `lanes.rs` (seven kinds of step, as STORE-04's second unit counted them). They are held by the loom models of `cache/tests/races.rs` (`RUSTFLAGS="--cfg loom" cargo test -p lignin-store --release --lib cache::tests::races`), where a weakened order fails a model. No test on real threads fails for one (STORE-04's planted faults), and a Miri run would only by the luck of its schedule. That is VER-05's ground, and section 4.4 says how far this audit went into it.

## 4. The buffer pool

### 4.1 The rules

The rules that make the unsafe code sound are stated once, at the top of `lignin-store/src/cache/frame.rs`, as the access rules A1 to A6, with the two arguments for an announced pin. They are not repeated here. In short: a frame is reached through its bucket's lock, through a pin, or by its owner (A1); a frame that is linked or pinned is not freed or given away (A2); ownership is exclusive and has a fixed list of beginnings (A3); content is written only with exclusive access (A4) and read only while it cannot be written (A5); and a pin is a count on the frame or an announcement in a lane (A6).

Every unsafe block names the rule it relies on. The types of the file stand for the ways of being allowed to reach a frame (`ChainRead`, `ChainWrite`, `Entry`, `Pinned`, `Frozen`, `Shared`, `Exclusive`, `OwnedFrame`), and the rest of the pool is safe code over them.

### 4.3 The safe code the unsafe blocks trust

An unsafe block is as sound as the claim of its caller. In `frame.rs` the claims are made by values of types that only this file can make, so the places that make them are part of the audit though none of them is unsafe code. The test counts them; a new one fails it.

### 4.4 What was read, and what was found

Every unsafe block was read against the rule it names, together with the callers that make its claim true: all of `cache/frame.rs`, `lanes.rs`, `sync.rs`, `pool.rs`, `guard.rs`, `write.rs` and `flush.rs`.

No block was found that is unsound as the pool uses it. Four things were found in the safe code around the blocks, where the soundness of a function that is safe to call was its caller's to keep, or a claim was made that nothing needs. Each is changed:

1. **`Chain::take_all` took its caller's word for the arena.** It makes every frame of a chain owned on the ground that pins borrow the arena, which is borrowed mutably; that says nothing of a frame of another arena. It now refuses a chain that holds a frame of another arena, before it unlinks anything (`frame::tests::a_chain_is_not_emptied_for_another_arena`). `Arena::announces` took its caller's word in the same way: asked of another arena it looked in the wrong lanes, and a frame that a reader had announced would have been found free to take. It refuses now (`frame::tests::a_frame_is_not_taken_out_for_another_arena`), and so does `ChainWrite::unpin_linked`. The pool always passes its own arena, so nothing went wrong.
2. **The last step on the count of a frame beside the arena was taken through a reference to the frame.** `Frame::unpin(&self)` and `Frame::retire(&self)` hold that reference until they return, and from the moment the count says so another thread can own the frame and free it. The pool keeps the two apart with the lock of the frame's bucket, which both sides take, so nothing was freed under a live reference; but `ChainWrite::unpin_linked` is safe to call with any bucket's lock, and with the wrong one a frame could be freed while the other thread was still inside the step that gave it up. That is undefined behaviour by Rust's borrow rules as Miri models them. For a frame beside the arena those two steps are now taken on the count alone (`Frame::unpin_count` in `unpin_linked`, `Frame::retire_count` in `ChainWrite::retire`), as the last `drop` of an `Arc` takes its own, and nothing of such a frame is read after them. An arena frame is never freed while the pool lives, so `Arena::bury` goes on reading its header after it has retired it. `frame::tests::a_frame_beside_the_arena_is_freed_once_whichever_lock_its_last_pin_goes_under` runs the two sides under different locks; under Miri the code as it was fails that test, and the code as it is passes it.
3. **`unsafe impl Send for Frame` was needed by nothing.** A frame is never moved by value to another thread: it stays at its address and is shared, which `Sync` covers. A pool that changes threads takes its frames along, and for that the arena has an `unsafe impl Send` of its own, whose comment now gives the reason itself and no longer leans on the frame's. The three engine crates build without the frame's, so it is removed: one claim fewer to keep true.
4. **`Send` and `Sync` of the pool's handles were stated by no test.** The five `unsafe impl` are what lets a pool and its handles cross threads, and a removed one shows only as a build error far from the cause. `tests::basic::the_handles_of_the_pool_can_go_to_other_threads` states it for each public type, and sends and shares them.

What was found in the tests:

5. **A frame's bytes are read before they are written**, by design: a `Blank` is a slice from its first moment. That is sound only because the block and every frame beside it are zeroed when the pool comes by them: by the allocator, which is asked for them zeroed, or by the system, for a block that is a mapping (section 4.5). No test read a frame first, so a change to plain `alloc` passed every test and every Miri run. `tests::basic::a_frame_can_be_read_before_anything_is_written_to_it` does now, for a fixed frame and for one beside them, and Miri fails it on memory that was not zeroed. `tests::basic::the_frames_of_a_large_pool_are_mapped_zeroed_and_side_by_side` reads the frames of a mapping first.
6. **The attached values of one page were never read by two threads at once**, which is what A5 allows of them, as of the bytes. Miri sees a reader that does more than read only beside another reader, so a planted fault of that kind (the list handed out to write under a shared access) passed every run. `tests::basic::threads_read_the_attached_values_of_one_page_at_once` reads them from three threads, under the shared latch of a private copy and with no latch once the page is published, and Miri fails it on that fault.
7. **One branch was reached by accident only**: taking a dead frame from behind another dead frame (`Arena::take_dead`, block 2) was executed by one deterministic test, which is about something else. `tests::basic::a_dead_frame_is_made_free_while_another_still_waits` is the test for it.
8. **The counting allocators of nine test targets had no safety comment.** Each has one now (section 5).
9. **Binaries, integration tests, build scripts and documentation tests are crates of their own**, which a library's `#![forbid(unsafe_code)]` does not reach. The scan of section 2 does.

What this audit did not do, and where it is done:

- **The `SeqCst` orders of A6.** The arguments in `frame.rs` ("why an announcement holds", "why what the announcer found is so") were read and followed step by step, and hold as written, on the orders the code has. That each order is needed is shown by the loom models and the planted faults of STORE-04's second unit (a weakened order fails a model). Exhaustive models and a ThreadSanitizer run are VER-05's.
- **The planted faults of this audit are of memory, not of the rules.** Each breaks what one unsafe block needs (a length, a layout, a free, zeroed memory) and Miri has to report it; the task's report lists them. That the pool keeps A1 to A6 in every interleaving is what the loom models and STORE-04's planted faults show.

### 4.5 The mapping of a large arena

An arena with a megabyte of frames or more does not take them from the allocator on the systems where `frame.rs` declares the system's call for a mapping: Linux on x86-64 and on AArch64, and macOS, each with 64-bit pointers. Its block is then a mapping of no file, private to the process (`Mapped`). The system gives such a mapping zeroed, so the arena does not write its frames to make them. A smaller block, every block on another system, and a block the system refuses to map is the allocator's (`Allocated`), which is asked for it zeroed. `BufferPool::mapped_memory` says which a pool has. Either kind of block is owned by a value whose drop frees it or, a mapping, asks the system to unmap it, and the arena holds that value.

What this adds to the unsafe code, and what it rests on:

- **Two declarations of functions of the system's C library**, `mmap` in `Mapped::new` and `munmap` in `Mapped::drop`, each beside the one call it serves. The crate depends on no binding to that library, so the signatures and the numbers of the flags are written out in the file, and the module is compiled for the systems above and no other: on any other `Mapped` is a type with no value. The compiler takes a declaration on trust, and so does Miri, which emulates the two calls by their names. What the declarations rest on is their agreement with the bindings of the `libc` crate (0.2.191) for these targets: the two signatures, with `usize` for `size_t` and `i64` for `off_t`; the names of the two symbols; and the numbers of `PROT_READ`, `PROT_WRITE`, `MAP_PRIVATE` and `MAP_ANONYMOUS`, and the address of all ones that `mmap` returns for a refusal. The tests run the two calls on the systems themselves with the arguments the pool passes. That shows that those calls work, not that a declaration is right in a part those arguments do not use: the offset, for one, is always zero.
- **A frame's bytes are read before they are written** (finding 5 of section 4.4). For a mapping this rests on the system's own description of one: the manual pages of `mmap` on Linux and on macOS both say that a mapping of no file is zero-filled. `tests::basic::the_frames_of_a_large_pool_are_mapped_zeroed_and_side_by_side` reads every frame of such a pool first, for each page size (under Miri, the frames at the two ends of the block and one inside it).
- **The block is aligned as a block of frames is asked to be**, which is to 4,096 bytes for every page size of a store (`layout`). A mapping starts at a multiple of the system's page size, which is 4,096 bytes or more on these systems. `Mapped::new` checks the address against the layout it was given and panics otherwise, in which case its value's drop asks for the unmapping.
- **The system is asked to unmap the mapping once, whole, after the last use of a frame.** `Mapped` owns the mapping and asks in its drop. The arena holds the `Mapped` as a field, so it is dropped after `Arena::drop` has run, which has dropped the headers by then; and nothing can reach a frame once the arena is dropped, as for a block of the allocator's. The system can refuse: Linux does when the range is the middle of one of its own mappings, which it has joined with a neighbour, and the process is at its limit of mappings. The mapping then stays the process's until the process ends. That loses memory and breaks none of the rules, since nothing uses the mapping any more. A build with debug assertions panics on a refusal that the system reports.
- **A panic while an arena is made hands back what was made**, a mapping with the exception just named. `Arena::make` makes the lanes, the lock of the dead frames and the block before the headers, and each is owned by its value, as the headers are by the collection they are made in and then by the boxed slice it becomes, until that is turned into the raw pointer the arena keeps. Nothing between that and the arena's being made can panic, and from then on the arena's drop frees them.

What Miri sees of it. Miri emulates a mapping of no file and its unmapping, for the targets of Linux on x86-64 and on AArch64 and of macOS on AArch64. It gives the memory zeroed, and it reports an access outside the mapping, a use after the unmapping and an unmapping of a part of it. **It does not report a mapping that is never unmapped**, and it stops when it is asked for a mapping too large to have, so the test of a mapping the system refuses (`frame::tests::a_mapping_the_system_refuses_is_none`) is left out of its runs. What an arena does when it gets no mapping is tested with an arena that may not ask for one (`frame::tests::an_arena_that_gets_no_mapping_takes_its_block_from_the_allocator`), which Miri runs.

That a mapping is unmapped is held by the test of `lignin-store/tests/cache_mapping.rs`, the only test of its file, on the systems that map. On Linux it reads the ranges of addresses the process has mapped, once while the pool lives and once after it is dropped, and finds the frames' own range covered the first time and untouched the second. Between the drop and the end of the second reading the test's thread allocates nothing and opens nothing. On macOS it reads no list of ranges but the size of the process's address space, through `ps`, before a pool is made, while it lives and after it is dropped, and allows for an eighth of the frames. That is a looser test: a mapping that stays whole fails it unless the rest of the process's address space shrinks by seven eighths of the mapping or more in the same time.

The pool's account of its memory is held by `a_large_pool_allocates_its_fixed_memory_less_the_frames_it_maps` in `lignin-store/tests/cache_alloc.rs`: what the allocator gave, counted at the allocator, and the mapping together are `fixed_memory()` exactly.

## 7. Adding unsafe code

The plan allows it in two places.

- **In the buffer pool**: in `cache/frame.rs`, under the access rules, with a `SAFETY:` comment that names the rule, a row in the inventory of section 4.2, and a test that executes it and runs under Miri. A new way to make an `OwnedFrame`, a `Pinned`, a `Frozen` or a latch changes section 4.3.
- **In the direct I/O path**: in `lignin-io/src/linux/ring.rs`, under the rules at the top of that file, with a `SAFETY:` comment that names the rule, a row in the inventory of section 8.2, and a test that executes it: on the model, so that Miri runs it, where it is not a system call. A second file of `lignin-io` with unsafe code needs what `ring.rs` has: an `allow` on its module that the test of section 2 is told of, and an inventory.

Anywhere else, the answer is no (DEC-07), and the test says so.

## 8. The direct I/O path: its memory and its ring

`lignin-io::linux` is the file layer that opens the files it reads with `O_DIRECT` (task IO-03; Linux, feature `direct_io`). What decides a single read is safe code: `O_DIRECT` is a flag to `std`'s open, the alignment comes from `rustix`'s `statx`, the aligned ranges and the read loop are `linux/aligned.rs`, and the read is `std`'s `pread`. The unsafe code is of two kinds, both in `linux/ring.rs`. The memory a direct read reads into is a mapping of its own that a fork does not share with the child (`Memory`), since the system's manual warns against direct I/O into the heap beside a fork. And a batch of reads needs an io_uring instance, whose two queues are memory that the system shares with the process, and to which reads are handed with the address of memory that the system writes into later.

### 8.1 The rules

They are stated once, at the top of `lignin-io/src/linux/ring.rs`, and are not repeated here. In short: a `Memory` is a private mapping of no file that its value owns, zeroed by the system, no longer than a slice may be, and unmapped by nothing but the value's drop (M1); the memory a read is given is the ring's own, never the caller's, and is not freed, moved or looked at from when the read is handed over until it is answered (R1); a count of reads in flight stands from before the system can take the first, a batch that is dropped while it is not zero gives its memory up without freeing it, and the bytes of a read are given out only once that read is answered (R2); the submission queue is written by this process alone, and a ring is used in the address space it was made in and in no copy of it, such as the child of a fork has (Q1); the completion queue is read only below a tail that was loaded, with heads and tails as atomics (Q2); and every offset the system reports is checked against the length of the mapping before anything is read or written there, and every index is masked (Q3).

The types of the file keep the unsafe code apart from what decides when it runs. `Memory` is a mapping and the two slices of it. `Owner` is safe code over a `Memory`: a byte that the child of a fork finds wiped. `Queues` and `Batch` carry the lifetime of the memory the queues are in: a ring's are its own mappings, and in the tests the blocks of a model, which the batch borrows. `Queues` is the pointers into the shared memory and the three steps on them (write entries, read where the system's head is, take answers). `Batch` is safe code over `Queues`: it owns the memory of the reads, counts what is in flight, decides when to call the system, and says what became of each read. `Mapping` owns one mapping of a ring. `Ring` puts them together with the ring's descriptor and makes the system call. `linux.rs` uses a ring through `Ring::read`, `Ring::outcome`, `Ring::calls` and `Ring::is_usable`, which are safe to call: a caller cannot reach the memory of a read that is not answered. `linux/aligned.rs` uses `Memory` through its two slices.

### 8.3 What Miri runs, and what it cannot

Miri has no io_uring, no mapping of a descriptor, no `madvise` and no `O_DIRECT`. It has a mapping of no file and its unmapping. So the unsafe code is in two parts, and the tests are too.

- **The memory, the queues and what a batch does with them** (`Memory`, `Queues`, `Batch`) are tested under Miri. `Memory` is mapped, read, written and unmapped there as on a system, but for the advice, which a build for Miri leaves out. The queues are tested on a model: the tests of `ring.rs` lay out a ring in memory of their own, as the system's parameters describe one, and a model of the system takes entries from the submission queue through its array of indices, writes the bytes of each read through the address the entry holds, and puts answers in the completion queue. The model is in a module of its own (`ring::tests::model`), and its functions are how the tests use it: `Model::batch` gives one batch for a model, `Model::read` and `Model::free` take that batch and refuse another model's, and `Model::free`, through which a test unmaps memory under the model, has it forget what it holds and take no further call. That is a fence for the tests as they are written, not a proof about every test that could be: the test module is inside `ring.rs` and can reach the fields of `Queues` and `Batch` as the code under test does. The model can take fewer entries than it was given, hold reads back and answer them in a later call and in another order, fail a held read, fail a call for a time or for good, answer short, answer a read twice, and answer a read that was not given. Miri runs these tests under both borrow models, in CI on every pull request (`lignin-ci.sh miri`): `cargo +nightly-2026-02-24 miri test -p lignin-io --features direct_io --lib linux::`. It checks every pointer the queues make against the block it points into, and the write of the model against the memory of the batch.
- **The system calls of a ring and the advice** (`io_uring_setup`, `mmap` of a ring, `munmap`, `io_uring_enter`, `madvise`) run in the tests that make a ring of the system, which have `#[cfg_attr(miri, ignore = "…")]`, in the tests of `linux/tests.rs`, which are left out of a build for Miri as a whole (the module is declared for `not(miri)`), and, for the advice, in every test that makes a `Memory` in a build that is not Miri's. They run on Linux in a test run that builds the feature (`--features direct_io`, or `--all-features` as CI's runs have it). Where the system gives no ring the tests of a ring fail: a test that passes without a ring would say nothing of this code. Whoever runs the tests on such a system says so with `LIGNIN_IO_URING=absent`; the tests of a ring then check that the system does refuse one, and end there.

What the model cannot show is what the system does that the model does not: an answer while this process is between two steps of `Batch::read` on another processor, and a read still under way after the call that took it failed. R1, R2 and the orders of the atomics are argued for those in `ring.rs`, and the tests on a ring of the system run them without choosing the moment.

**That a batch with reads in flight is not unmapped** is held by `ring::tests::a_batch_that_is_dropped_frees_its_memory_unless_a_read_is_in_flight`, which counts the `Memory` values that are dropped when a batch is, the drop being the one place that asks the system to unmap one: all of them where every read was answered or none was taken, and none where the system took reads and did not answer them. It counts the drops, not what the system did with the call. Miri runs it: a mapping that is never unmapped is no error to it (section 4.5), and the batch frees the list of them, which is the allocator's.

**That a ring's mappings are unmapped** is held by the test of `lignin-io/tests/ring_mapping.rs`, the only test of its file: it reads the ranges of addresses the process has mapped, and finds two mappings of a ring after a batch and none after the file layer and its files are dropped.

**That the child of a fork finds the mark wiped** rests on the system's description of the advice and on `kernel/fork.c`, and on one run by hand, which the task's report has: no test of the crate forks. The tests put a ring in the state the child finds (`Ring::foreign`: the mark wiped) and check that it is given up with no entry in a queue and none of its reads in flight (`ring::tests::a_ring_whose_mark_is_wiped_is_given_up_and_handed_nothing`). That the mark is asked before a queue is read is not something a test sees: it is the first statement of `Ring::read`.

### 8.4 What the unsafe code trusts

- **`rustix`** (1.x, with its features `fs`, `io_uring` and `mm`). From it come the declarations the compiler takes on trust: the layouts of a submission entry, of a completion entry and of the parameters of a ring, the numbers of the system calls and of the advice, and the offsets at which a ring is mapped. The tests run them against the system: a ring that was laid out differently from what the system has would answer no read.
- **What the system reports of a ring** is checked before anything is read or written through it: its offsets and numbers of entries against the length of each mapping (`Region::at`, `Queues::over`; `ring::tests::queues_that_do_not_fit_their_memory_are_refused`). An answer names a read only if it is one of the batch that has no answer yet, and the bytes of an answer are never more than the read asked for.
- **That the system writes into the memory of a read only until it has answered it, and takes a submission entry only inside the call that submits, in the order of the entries** (a ring is made with no flag, so with no thread of the system that polls the queue; `io_submit_sqes` in `fs/io_uring.c` of v5.6 and `io_uring/io_uring.c` of v6.12 stores the head behind the entries it has consumed before it returns, and where it returns early it has consumed none). R1 and R2 are built on the first. The second is what lets a batch that is given up say what is in flight and which reads were never made (`Batch::given_up`): the entries the system took are those before where the head of the submission queue stands after the last call returned.
- **That a mapping with `MADV_WIPEONFORK` is not shared with the child of a fork** (`dup_mmap` in `kernel/fork.c` of v6.12 leaves out `copy_page_range` for it, lines 745-746; the advice is taken for a private mapping of no file only, `mm/madvise.c` 1067-1072). The system's manual page for `open` names two kinds of memory that direct I/O may use beside a fork, a shared mapping and one with `MADV_DONTFORK`; this advice is neither by name, and does what the second does for the parent: the fork leaves the parent's pages alone. It is chosen over `MADV_DONTFORK` because the child then has the mapping, zeroed, where with the other it would have values that point at no memory. Tasks that share one address space, as `clone` with `CLONE_VM` makes them, share the mark, as they share the ring's memory and every value of this code. One of them that does not share the table of descriptors as well must not use the file layer, which says so: an entry names its file by the number of a descriptor. And a fork from a signal handler that returns into a call of the file layer in the child is ruled out there too: the mark is asked where a call begins.
- **That a call which takes fewer entries than it was given does not wait** (Linux since 5.5: `io_uring_enter` in `fs/io_uring.c` of v5.5 and v5.6, `io_uring/io_uring.c` of v6.12). A ring is made only on a system that reports the features of Linux 5.6. This is not a matter of memory safety: without it a batch could wait for an answer that never comes.
- **The safe code around it.** `Batch::read` is what keeps R2. The count is set to the whole batch before the entries are written and is set to zero when every read has its answer. Where the batch is given up after a call that failed or did nothing, `Batch::given_up` sets it to the entries the system took less the answers this process took from the queue; on every other way out after the count is set, an answer that fits no read and a panic of the system call among them, it stays the whole batch; a panic of one of the checks a batch begins with comes before the count is set. A batch that is refused before an entry is written, for want of memory or in a copy of the address space (`Batch::refuse`), keeps the count it had, which is zero for a batch that was not spoiled before. A batch that is given up is marked so that `Batch::read` refuses it from then on, before it writes an entry or makes a call (`ring::tests::a_spoiled_batch_makes_no_system_call_again`). `Batch::outcome` gives the bytes of a read only if that read has its answer. `linux.rs` drops a ring that is spoiled (`tests::a_ring_that_breaks_is_given_up_and_its_reads_are_made_one_by_one`), and it has copied out the reads a ring brought whole, and dropped a spoiled ring, before it calls a file of the list, whose read is code this layer does not know (`tests::the_ring_is_done_with_before_a_file_of_the_list_is_read`). `Ring::read` is what keeps the part of Q1 that a fork could break: it asks the ring's `Owner`, and in a copy of the address space the ring was made in it spoils the ring before it touches a queue. A file's descriptor is in an entry as a number: the files of a batch are borrowed for the whole call, so the number is the file's when the system takes the entry.

### 8.5 What a spoiled batch costs

A batch is given up when the ring's system call fails with an error that is not a request to try again, when the system neither takes a read nor answers one in sixteen calls in a row that no signal interrupted, when it answers a read it was not given or one twice, when it gives no memory for the reads, or when the ring was made in another address space. The ring is then closed. If the count of R2 is not zero then, the memory of the ring's reads is not unmapped while the process lives: 128 KiB and 4,095 bytes, rounded up to the system's pages, for each read of the largest batch that ring made, which is 4,224 KiB at most with pages of 4 KiB and 6,144 KiB with pages of 64 KiB. The count is not zero where the system took reads whose answers this process had not taken from the queue when it gave up, and after an answer that fits no read. It is zero, and the memory is unmapped with the ring, where the system took no read or this process had the answer to each one it took and no answer that fits no read came, where no memory was given, and where the ring was made in another address space. `DirectVfs::stats` counts the rings that were given up, and after three rings that could not be made or were given up a file layer makes no further one (`tests::after_three_rings_that_failed_no_further_ring_is_made`).
